# oom-sites: classification vocabulary

How to write one inventory row (the seven columns of templates/inventory.tsv) for each site of migration/inventory/sweep/oom-sites.tsv: each raise, test, case label and initialization of `OB_ALLOCATE_MEMORY_FAILED`, or of the parser's `OB_PARSER_ERR_NO_MEMORY` (both -4013), that the sweep keeps; each raise and test of a memory-limit code; the query memory tracker's check calls and functions; and the lines of the micro block cache's FIFO (definition and measured counts: migration/inventory/sweep/summary.tsv, row `oom-sites`). A classifier who reads this file, the rules it cites and the site can decide every value. Rows go to the shard the orchestrator names; section 10 gives the check every shard must pass, section 11 three worked rows, section 12 the values a script may propose before a classifier reads a row, and section 13 the review's sample.

## 1. What a row decides

RULEBOOK section 5 gives this list's rows one answer: "`allocation-guard` or `precondition-guard`, and for a budget owner its formula and check point (2.2)". The rules that decide it:

- Decision 12 (migration/decisions.md): a general out-of-memory aborts the process; typed errors stay only at the named budget owners and for the logical -4013 errors. ARCHITECTURE §3.2 and s3-memory.md 3.7 spell it out.
- RULEBOOK 2.2: its rows on -4013 (removed after a general allocation; kept for a size of 0 or less; unchanged at a named owner or logical limit, when injected by a tracepoint, or when a kept library maps to it; comparisons kept as written) and its rows on object pools and `deep_copy`. RULEBOOK 2.10: the error-recovery rule, by which every guard row records `allocation-guard` or `precondition-guard`, and the UNKNOWN rule. s2-errors.md 2.4 rules 2 and 9, and 2.13 item 5.
- The design as amended (migration/design/AMENDMENTS.md). A1-7: the SQL work area's -4013 with dumping off is a precondition-guard of the work-area owner, kept as written, not the UNKNOWN rule. A1-10: of the micro block cache, only the multi-block path draws on the 4 GiB FIFO; the other paths are plain allocations. Both are applied in s3-memory.md 3.7.2 and 3.7.3.
- Where two design files disagree, the higher one wins (RULEBOOK section 0 ranks ARCHITECTURE.md above the section files, and both above RULEBOOK.md): ARCHITECTURE §9.2 keeps the parser's `check_mem_status` and `try_check_mem_status` as the C core's weak no-ops, over s3-memory.md T4 and T5; RULEBOOK section 3 (the sql-parser-sys row) says the same (finding F3).
- Pilot rows are cited by the number design amendment A1 gives them (migration/design/AMENDMENTS.md): row N is line N+1 of migration/inventory.pilot.tsv. Row 2 is the micro block cache callback's `allocator_`, row 16 the fulltext parser's status mapped to -4013, row 17 the work area's -4013 with dumping off. Under this vocabulary row 16 is `LIBRARY_MAPPING` and row 17 `BUDGET_OWNER`, both `precondition-guard` as the pilot has them.

So:

- `classification` says what the line is under Decision 12 (section 4); the value fixes the tag the evidence carries.
- `target_translation` gives the Rust for the line: the branch removed, the line kept as written, the owner's form, or nothing (section 5). For a budget owner it names the owner, its formula and its check point.
- `evidence` shows what makes the condition true, where the code goes, and the tag (section 6).

The sweep's `construct` labels come from text patterns and decide nothing; several are wrong (finding F1). Read the site.

## 3. Reading the site

Find five things before choosing a value.

1. **The unit.** Search the three lists for the file as an input: `grep -nP '(^|[\t,])src/share/io/ob_io_manager\.cpp([\t,:]|$)' migration/core-manifest.tsv migration/manifest.tsv migration/not-translated.tsv`. An entry may give line ranges (`file:a-b`); it covers the row only when the row's line is inside one. A split file repeats its `source` on every piece: the unit is the piece whose `inputs` range holds the line. A file on core-manifest.tsv is a core unit (section 5.2). The three lists are being edited while the inventory is built (finding F7): take their line numbers when you write the row, and confirm them with `cite_check.py <shard> show`.
2. **The kind of line.** A raise (an assignment, a return, a ternary, an argument of `OV`, `OX`, `OZ` or `CK`, an argument of a macro or function that raises it); a test (a comparison, a `case` label, a term of a predicate); the initialization of a variable; a tracker check call; a declaration or definition of a tracker check function; or a line of an owner's allocator (its limit, its init, its hand-out, its retry).
3. **The governing condition** of a raise or initialization: the if/else-if arm whose body holds it, and the condition of the branch around that chain. Name what makes it true: an allocation (which allocator: find its declaration and its init, and whether the init sets a limit), an owner's check, a limit's formula, a tracepoint, a library's status, or a callee's result (read the callee far enough to list every way it can fail).
4. **The producer** of a tested code: the call or assignment that puts the code in the tested holder, as ret-compare.md section 3 item 3 reads it, and what can still produce the memory code there in Rust.
5. **Where the code goes**, for a code the Rust keeps: the callers that receive it and what they do with it.

A null test on something that is not an allocator does not make the -4013 a general out-of-memory. The sweep's rule treats every null test in the governing condition as one, so it drops raises whose NULL comes from a free list, a ring buffer or a pool (finding F2). Read what returns the NULL.
