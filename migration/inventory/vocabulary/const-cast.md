# const-cast: classification vocabulary

The classifiers of the const-cast sweep list fill one inventory row per sweep line with this file. It fixes the values of the `classification` column, the `target_translation` each value implies, what `evidence` must show, and when a row is `unknown`.

- **The list.** migration/inventory/sweep/const-cast.tsv, columns `file`, `line`, `symbol`, `construct`, `text`. Its definition is the `const-cast` row of summary.tsv: code lines with `const_cast<` or `const_pointer_cast`, plus C-style casts to a non-const pointer or reference that a heuristic found dropping const; `(adds const only)`, `[not built]` and `[vendored]` marks; one row per body line of a `#define`, and no rows for the macro's uses.
- **What a row decides.** RULEBOOK section 5: "the `&mut` path that replaces each cast write". Rust has no `const_cast`. A write needs a `&mut` the borrow checker accepts, so each row says whether anything is written through the cast and, if so, where that `&mut` comes from.
- **The rules that decide rows**, as design amendment 1 left them (migration/design/AMENDMENTS.md, A1-1 to A1-11).
  - RULEBOOK section 0 (the statements a translation may add), 2.1 (output parameters stay `&mut`), 2.2 (`ObString` and `ObObj` bytes are borrows; frees and handoffs; reference counts and the counts that stay), 2.3 (overload numbering, variadic templates, visibility, type punning), 2.4 (ids, including objects the C++ points to from more than one place and the plan and execution objects; a slot copied out and written back), 2.5 (frames, batches, `MEMMOVE`; the hash-map ports' `get`), 2.7 (locks own their data; how long a guard lives; `ObRecursiveMutex`; atomics and links), 2.10 (the UNKNOWN rule), section 3 (the `TODO(port)` marker), section 4 (every member of a split type is `pub(crate)`).
  - s4-sql-front.md 1.3 (`&mut ParseTree`; a write into a node's bytes), 2.1 rule 4 (the hash-map ports' `get` forms; an element whose address escapes), 2.2 and 2.3 (which objects are ids, and `ObExpr`'s `ExprIdx`; `&` or `&mut` factory), 3.2 (contexts; the session is a shared reference), 3.3 (`&self` and `&mut self` methods).
  - s5-execution.md rules 2.2, 2.6 (datums and `BufTable`), 3.1 (the plan is immutable; per-run state moves into the frame or the operator), 3.3, 3.5 (result bytes through `split_mut`), 3.10 (an `ObExpr` built outside every table), 4.3 (batches), 4.4 (stored rows), and part 4's `ObBatchRows`, which owns its skip vector.
  - s3-memory.md R1, R2, R3, R4, R5 (reference counts become `Arc`, and the counts that stay; a last release that routes the object somewhere is a handle; pools; the schema guard's getters take `&mut self`; a KV-cache handle is an `Arc` of its entry); ARCHITECTURE §3.1 rules 2, 5 and 9, §3.2; s6-storage.md 10.1 rule 1.
  - s8-numerics-platform.md 4 rule 5 (a link of a linked structure moves inside the lock of its structure) and 5 rules 5, 6 and 8 (a guard lives as long as the C++ holds the lock; `ObRecursiveMutex` holds no data).
  - migration/not-translated.tsv and the two manifests (which code gets Rust at all).
- **Pilot rows.** "Pilot row N" is the Nth data row of migration/inventory.pilot.tsv; the rows the amendment settled are confirmed there, and this file cites them where they decide a form.

## 1. The columns of a const-cast row

| Column | Content |
|---|---|
| `file` | the sweep row's `file`, unchanged |
| `symbol` | the sweep row's `symbol`, unchanged (`-` stays `-`) |
| `source_construct` | the sweep row's `construct`, then ` (line N)` with the sweep row's `line`: `const_cast<ObBatchRows *> (line 1761)`. The line is needed: the merge dedupes on (`file`, `symbol`, `source_construct`), and without it 229 keys repeat, covering 750 rows (`awk -F'\t' 'NR>1{print $1"\t"$3"\t"$4}' const-cast.tsv \| sort \| uniq -c \| awk '$1>1{k++; s+=$1} END{print k, s}'` prints `229 750`), while (`file`, `line`) never repeats |
| `classification` | one value of section 2 |
| `target_translation` | the form section 3 gives for the value, written for this site |
| `evidence` | starts `sweep: const-cast.tsv:<line in the tsv> (data row <line - 1>)`, then what section 3 asks for the value |
| `status` | `confirmed`, or `unknown` exactly when `classification` is `UNKNOWN` |

- **A line with several casts** (the sweep lists several target types, separated by `; `): classify each cast, write each one's answer in `target_translation`, and give the row the value that comes latest in section 2's order.
- **A `#define` body line**: the test must hold for every use of the macro; the evidence lists the uses (`grep -rn '<MACRO>' src` and the number of lines it printed). If the uses need different values, take the latest in the order, or `UNKNOWN`.
- **`[not built]` and `[vendored]`**: see `NOT_TRANSLATED`.
- **How the list splits by unit** (each row's file and line matched to not-translated.tsv, manifest.tsv and core-manifest.tsv, using the line ranges of split units): 632 rows in Step 3 stems, 544 in Step 3 split units, 490 in core units, 206 in island units (all of src/share/geo but src/share/geo/ob_geo_mvt.cpp), 10 in dropped units, 4 in dead units, 2 in vendored zstd sources that no list names.

## 2. The values

**Read the operand's type first.** Many casts remove nothing. Overload resolution picks a non-const accessor whenever the object it is called on is not const, even when the code wraps the call in a cast: `comment.ptr()` on a non-const `ObString` calls `char *ptr()` (src/oblib/lib/string/ob_string.h:288), not the const overload (src/oblib/lib/string/ob_string.h:287). Three rows of the first sample were misread this way (section 6.1, lines 182, 1450 and 1749). Name the declaration of the operand, and the overload its call resolves to, before tracing any write.

Apply the tests in this order; the row takes the first value whose test holds. Four kinds of write never take the general values `ALREADY_MUT`, `LOCAL_COPY` or `PARAM_TO_MUT`, because a design rule speaks to them: a write into an `ObBatchRows` that is not `OWN_BATCH` is `UNKNOWN` (Q3; s5-execution.md rule 4.3); a write into the session, or into state reached through it, that is not `LOCK_OR_ATOMIC` is `UNKNOWN` (Q2; s4-sql-front.md 3.2); an execution-time write into the cached plan that is not `PLAN_FIELD` is `UNKNOWN` (Q5; ARCHITECTURE §3.1 rule 2); a write into a datum's bytes that is not `DATUM_BYTES` is `UNKNOWN` (Q7; s5-execution.md rule 2.6). A value earlier in the order still applies to these writes: a lock or atomic operation is `LOCK_OR_ATOMIC`, and a cast that removes nothing is `NO_CONST_DROPPED`.

| # | Value | Meaning | Test that decides it (section 3 has the detail) |
|---|---|---|---|
| 1 | `NOT_TRANSLATED` | no Rust is written for this code | the row's unit is in not-translated.tsv, or the row is `[vendored]` and no manifest lists its file |
| 2 | `REPLACED` | the statement belongs to a mechanism the design replaces as a whole | a cited design rule replaces the mechanism, and its words cover the enclosing function |
| 3 | `ADDS_CONST` | the cast only adds const | every cast on the line is marked `(adds const only)`, and none with a two-level target turns const slots writable |
| 4 | `NO_CONST_DROPPED` | the cast removes no const that protects the object | the operand is already non-const (a non-const overload was chosen), only a pointer value's top-level const goes, only the const of what pointer slots point to goes while the writes go to the slots, or the heuristic's C-style cast has a non-const operand |
| 5 | `IR_ID` | the object is an IR object with an id | the target type gets an `Id<T>` in s4-sql-front.md 2.2's table (its `ObExpr` row gives `ExprIdx`, a table position and not an id, so `ObExpr` is not this value) |
| 6 | `LOCK_OR_ATOMIC` | the only writes are lock operations, atomic operations (reference counts included), writes under a held lock, or writes of a link the design moves inside the lock of its structure | every write through the cast is one of those five kinds |
| 7 | `FREE_OR_HANDOFF` | the cast only feeds a free, a reallocation, a destructor, or a callee that takes the object over | every use of the result is such a call, and nothing reads the object after a free |
| 8 | `NO_WRITE` | nothing writes through the result | every use, in the function, in every callee it reaches and in every reader of a copy that escapes as the object's own pointer, is a read; a stored view is a shared borrow in Rust, or its borrowed-views.tsv row's form where the viewed data sits inside a lock; not a forwarding overload |
| 9 | `OWN_BATCH` | the write goes to a batch the operator owns | on every path to the write the batch pointer holds `&` of the operator's own member |
| 10 | `PLAN_FIELD` | an execution-time write into the cached plan, read only by the same execution | the written object is part of the plan and every reader runs in the same execution |
| 11 | `DATUM_BYTES` | the write goes to the bytes a datum refers to | the written memory is what an `ObDatum` or `ObStorageDatum` points at, and the writer is the buffer's producer |
| 12 | `NEW_BYTES` | the write goes to bytes just allocated or copied | the bytes' origin is an allocation or copy in this function, a callee's fresh return, or every caller just before the call, with no other reference before the write |
| 13 | `ALREADY_MUT` | the function already holds the owner mutably | the owner is the function's non-const `this`, a non-const parameter, a local or its own allocation, and Rust can reach the field for writing |
| 14 | `LOCAL_COPY` | the write can go to a local copy because nobody else sees it | the object is a cheap value, every read of the written state is in this call, and the old value is restored or never read again |
| 15 | `PARAM_TO_MUT` | a const receiver or parameter becomes `&mut` | every caller up to the owner holds the object mutably, and no other thread, `Arc`, cache or plan holds it |
| 16 | `UNKNOWN` | the design or the trace leaves the row open | section 4 |

## 3. Each value: the translation, the rules and the evidence

Every row's evidence, whatever the value: the sweep reference; the declaration that makes the operand const (a const accessor's signature, a const parameter or member, a literal), with file and line, and for a call on an object, the overload the call resolves to; each use of the cast's result, marked read or write, and for each callee it is passed to, the callee's lines that read or write that parameter; where a copy of the pointer is stored (member, out-parameter, return value) and its readers, or "escapes: none"; the threads that touch the object; and any other sweep row that decides part of the answer (lock-guards.tsv, atomic-fields.tsv, refcount.tsv, borrowed-views.tsv, arena-handoff.tsv, memmove.tsv, pointer-identity.tsv, subclassed-bases.tsv, frame-internals.tsv), by `<file>.tsv:<line>`, or the pilot row that settled it. A value whose translation writes a field through a `&mut` (`ALREADY_MUT`, `LOCAL_COPY`, `PARAM_TO_MUT`) also needs Rust to reach that field for writing, by `ALREADY_MUT`'s third test; where Rust cannot, the row is `UNKNOWN` (Q9). The extra requirements per value follow.

**Plan expressions (`ObExpr`).** An `ObExpr` is not IR and never `IR_ID` (s4-sql-front.md 2.2), so a cast to `ObExpr *`, `ObExpr **` or `ObExpr &` takes another value by the tests below. The plan's expressions are immutable and shared (s5-execution.md rule 3.1): an `ObExpr` method that takes the evaluation context writes the frame, not the expression (`locate_expr_datum(ctx)` and `set_evaluated_projected(ctx)` are `const`, src/query/api/query/engine/expr/ob_expr.h:364, :568), so a use through it is a read of the `ObExpr`, and the frame is written through `&mut EvalFrame`. In the translation, an `ObExpr` pointer the C++ stores (an `args_` slot, a spec's array or a view of one, an out-parameter, a setter's field) is its `ExprIdx`, a position in the expression table, and one the code only evaluates is `&ObExpr` (s4-sql-front.md 2.2's `ObExpr` row). An `ObExpr` the C++ builds outside every table and reaches by a pointer (the datum caster's two cast expressions, a values operator's stack copy of a plan expression, which it hands to the caster) has the `ExprIdx` past the table's end that s5-execution.md rule 3.10 gives, and a copy that nothing points to is an owned value (design amendment A1-1): `cast_expr.args_[0] = const_cast<ObExpr*>(&src_expr)` (src/sql/engine/expr/ob_datum_cast.cpp:13070; const-cast.tsv:1058) is `NO_WRITE`, since the cast expression's evaluation only reads its argument, and `setup_cast_expr` takes `src_expr` as the `ExprIdx` it stores.

### NOT_TRANSLATED

- **Test.** The row's file (for a split unit, the unit whose line range holds the row) is a unit in migration/not-translated.tsv: an island, dead, dropped, deferred, generated or data unit. Or the sweep marks the row `[vendored]` and no manifest lists the file: zstd 1.3.8's sources are a C library the product keeps (RULEBOOK section 1, "C libraries in the product"). Of the 3 `[vendored]` rows, src/oblib/easy/util/easy_buf.h:74 is in a dropped unit (not-translated.tsv:26) and the two zstd rows are in no list. The `[not built]` rows are checked the same way; the list's 4 are in dead or dropped units.
- **Translation.** `none: <reason>`. An island stays C++, compiled from its src/ path (RULEBOOK section 0; s7-islands-unsafe.md 7.1), so its cast stays as written; a dead or dropped unit has no code.
- **Evidence.** The not-translated.tsv line with its unit and reason (`not-translated.tsv:55`, island), or the `[vendored]` mark and the RULEBOOK row. Nothing else is traced.

### REPLACED

- **Test.** The statement belongs to a mechanism a design rule replaces as a whole, and the rule's words cover the function the row sits in:
  - the OB allocator's own internals (chunk, block and object headers, object sets, malloc hooks), replaced by jemalloc and bumpalo (ARCHITECTURE §3.2; RULEBOOK section 1's Memory row; RULEBOOK 2.2);
  - the definition of an OB lock, or of a guard class whose constructor and destructor only lock and unlock (the constructor that stores the lock at src/oblib/lib/lock/ob_spin_rwlock.h:69; `MemMgrRLockGuard`, src/storage/ob_i_memtable_mgr.h:175), replaced by ob-base's `sync` module and its guards (RULEBOOK section 1's Locks row; RULEBOOK 2.7). A class that does other work while it holds the lock is translated, and its lock calls are `LOCK_OR_ATOMIC` (a): `ObGlobalMergeManager::ObGlobalMergeMgrGuard` stores the lock (src/rootserver/freeze/ob_global_merge_manager.cpp:413), copies data to a shadow under a read lock (ob_global_merge_manager.cpp:418, :420), and copies it back under a write lock in its destructor (ob_global_merge_manager.cpp:430, :432);
  - encoding and decoding the plan, its `ObExpr`s or its frame info to move them to PX workers inside the process, replaced by workers sharing the plan as `Arc` (s5-execution.md rule 3.1);
  - pools that only reuse memory (s3-memory.md R3);
  - the lookups of ob-base's `ObHashMap` and `ObHashSet` ports, whose Rust forms s4-sql-front.md 2.1 rule 4 gives (design amendment A1-4): `get_refactored`, `exist_refactored` and the `const` `ObHashMap::get` take `&self`, the other `ObHashMap::get` is `get_2(&mut self, key) -> Option<&mut V>`, and `ObHashSet::get` is `get(&self, key) -> Option<&K>`, since a stored key is never written in place. The casts in their C++ bodies, which let a `const` lookup call the inner table's non-const one (const-cast.tsv:358-359, :361, :363) or hand out a non-const pointer (the non-const `get` casting its twin's result, src/oblib/lib/hash/ob_hashmap.h:259; `ObHashSet::get`, src/oblib/lib/hash/ob_hashset.h:151), have no Rust counterpart. A caller's cast of what `get` returns is not this case: see `NO_CONST_DROPPED`.
- **Translation.** `none: replaced by <construct> (<rule>)`. The statement has no Rust counterpart.
- **Evidence.** The enclosing function's definition line and the words of the rule that cover it; for PX, the call path that shows the code only hands the plan to a worker thread of the same process.

### ADDS_CONST

- **Test.** Every cast on the line is marked `(adds const only)` in the sweep's `construct`. The mark says only that the target type starts with `const`, which settles a one-level target (`const T *`, `const T &`). A two-level target (`const T **`, `const T *&`) adds const only when the operand's slots are writable (`T **`, `T *&`); where they are const (`T *const *`), the cast removes that const despite the mark, and the row takes the value of the later tests: `*(const_cast<const char**>(&name_)) = N_MID` (src/sql/engine/expr/ob_expr_mid.h:34) overwrites `name_`, declared `const char *const name_` (src/query/api/query/engine/expr/ob_expr_operator.h:734).
- **Translation.** `none: the cast only adds const; in Rust a &mut converts to & where needed, or the value is used as it is.` Nothing is written, so there is no `&mut` path for RULEBOOK section 5's question.
- **Evidence.** The sweep reference; for a two-level target, the operand's declaration too.

### NO_CONST_DROPPED

- **Test.** The cast removes no const that protects the object it reaches:
  - the operand already has the target type: the object is not const, so overload resolution chose a non-const accessor or overload even though the code wraps the call in a cast (`comment.ptr()` on a non-const local `ObString`, src/oblib/lib/string/ob_string.h:288; `buffer_.ptr()` on a member of the object a constructor builds, src/oblib/lib/string/ob_string_buffer.h:62), or the operand is a non-const object, reference or pointer (a non-const member such as `ObDatumRowkey::datums_`, src/storage/blocksstable/ob_datum_rowkey.h:111);
  - only a pointer value's top-level const is removed (`T *const` to `T *`, as when an element is read from a `const ObIArray<T *> &`), so the object it points to was never const;
  - the cast drops only the const of `T` behind a pointer to a pointer (`const T **` to `T **`, `const T *&` to `T *&`) so that a callee can store new pointers into the slots, and nothing writes a `T` through them: the slots themselves were never const (a local such as the end pointer `ob_atof` passes to `ob_strtod`, src/oblib/lib/charset/ob_dtoa.cc:411, or an operator's own array such as `batch_rows_from_dump_`, src/sql/engine/aggregate/ob_hash_groupby_op.h:617). A cast from `T *const *` to `T **` does remove the slots' const and is not this case;
  - the heuristic's C-style cast has an operand that is not const (a function that returns `char *` called on a const object).

  Judge by the Rust form of the object the write reaches: where the design makes a C++ pointer member an owned field, a write through the member is a write into the object that holds it. `ObBatchRows::skip_` is a pointer in the C++ but the batch's own `ObBitVector` in Rust (s5-execution.md part 4), so `const_cast<ObBatchRows *>(b)->skip_->reset(n)` removes a const that protects the write.
- **Translation.** `No cast.` The access follows the operand's own form: a shared borrow when nothing writes through it; when something does, the `&mut` comes from where the C++ operand's non-const access comes from, which the evidence names (for pointer slots, the slots' owner: `&mut self` for a member array, `&mut` of a local). The cast is not what makes the write possible, so the rules for the object's own type decide the rest (RULEBOOK section 2), and a write through a view is the view type's question (borrowed-views.tsv).

  A cast of what `ObHashMap::get` returns, on a map the function holds mutably, is this case: `get` resolves to the non-const overload (src/oblib/lib/hash/ob_hashmap.h:252), which is `get_2(&mut self, key) -> Option<&mut V>` in Rust, and the write goes through that `&mut V` before the next call on the map or on its owner (s4-sql-front.md 2.1 rule 4, design amendment A1-4; `*count += 1` after `c1_map.get`, src/sql/engine/expr/ob_expr_operator.cpp:2668, :2673). Where the C++ keeps the pointer past such a call, the site copies the value out at the `get` and writes it back with `set_refactored(key, value, 1, 0, 0)` under one hold of the map's lock, on a map whose `EXTEND_RATIO` is 1 (with a larger ratio the value is an `Arc` or an id). Where it stores the address elsewhere (links it into a list, keeps it in a member, hands it to a caller that keeps it), the map holds the element as an `Arc` or an id, the other holders get clones, and nothing is copied: `get_group` links the group `group_map_.get` returned into `groups_` and hands it to its caller (src/observer/ob_uniq_task_queue.h:597, :601).
- **Evidence.** The declaration that shows the operand is not const (the non-const accessor's signature and why the call resolves to it, the variable's or member's declaration); if the object is written, its owner and how the function holds it; for a `get` result, how long the C++ keeps the pointer and where it stores the address, if anywhere.

### IR_ID

- **Test.** The cast's target is a pointer or reference to an object s4-sql-front.md 2.2's table gives an id: `ParseNode`; `ObRawExpr` and its subclasses; `ObDMLStmt` and its subclasses (`ObSelectStmt`, `ObInsertStmt`, `ObUpdateStmt`, `ObDeleteStmt`, `ObDelUpdStmt`, `ObExplainStmt`, `ObLockTableStmt`); `TableItem` and `JoinedTable`; `SemiInfo`; the `ObRawExprSet`s of equal sets; the `ObLogPlan`, `ObLogicalOperator` and `Path` families; `ObJoinOrder`; `ObConflictDetector`; `ObRangeNode`; `ObPLBlockNS`. Not covered: a pointer to an array of such pointers (`ObRawExpr **`), which is classified by whether its slots are written; the bytes a node points to (`str_value_`), which are `NEW_BYTES` or `UNKNOWN` (Q7); `ObExpr`, the plan's expression, which is not IR: s4-sql-front.md 2.2 names it by `ExprIdx`, a position in its table, and one the C++ builds outside every table follows s5-execution.md rule 3.10 (design amendment A1-1); a cast to it takes another value (the paragraph on plan expressions above). `ObTempExpr` and `ObTempExprCtx` get ids (`TempExprId`, `TempExprCtxId`) but no sweep line casts them (`grep -c ObTempExpr` on const-cast.tsv prints 0).
- **Translation.** The id (`NodeId`, `ExprId`, `StmtId`, `TableItemId`, `SemiInfoId`, `ExprSetId`, `LogPlanId`, `OpId`, `PathId`, `JoinOrderId`, `ConflictDetectorId`, `RangeNodeId`, PL's namespace id). `const T *` and `T *` are the same id (s4-sql-front.md 2.3). When the function or a callee writes the object after the cast, the function reaches the arena owner mutably: `&mut ParseTree` (s4 1.3), `&mut ObRawExprFactory` (s4 2.3), `&mut ObStmtFactory` (s4 2.4 and 3.2's table), the optimizer context's arenas (3.2's table), PL's arenas (2.2's table); otherwise by `&`. A member function that follows another IR pointer takes `this: <Id>` (s4 3.3). An overload pair that differs only in const becomes two functions returning the same id, and neither needs the cast.
- **Evidence.** The object's type; each write after the cast, or "no write"; the arena owner the function reaches (`params_`, `ctx_`, `optimizer_context_`, `expr_factory_`, or an added parameter).

### LOCK_OR_ATOMIC

- **Test.** Every write reached through the cast is one of:
  - (a) a lock, unlock, try-lock or guard construction on an OB lock (`ObLatch`, `TCRWLock`, `SpinRWLock`, `ObSpinLock`, `ObRLock`, `ObWLock`, `MemtableMgrLock`, `ObRecursiveMutex`, a template `LockType`), including those a class that works under the lock makes (see `REPLACED`);
  - (b) an `ATOMIC_*`, `__sync_*`, `__atomic_*` or `std::atomic` operation on a field that is not a link of (e);
  - (c) a reference-count change (`inc_ref`, `dec_ref` and the other names refcount.tsv lists);
  - (d) a plain write to a field that a lock held at that moment guards: the lock's lock-guards.tsv row puts the field in its `T`, or, where that row is not written yet, the evidence shows every access to the field is made with that lock held;
  - (e) a write, atomic or plain, of a link of a linked structure whose links the C++ reads or writes with `ATOMIC_*` (a list's or version chain's head and `prev_`/`next_`, a hash bucket's row pointer or chain link, a tree's root and child links): s8-numerics-platform.md 4 rule 5 moves such a link inside the lock of its structure (design amendment A1-11 (a)). The shared hash join's buckets and chains are the case (`atomic_set`, src/sql/engine/join/ob_hash_join_op.h:485-529; pilot row 10), and so is the same table's single-thread `set` (src/sql/engine/join/ob_hash_join_op.h:459-481), since every worker's table sits behind that lock. A single published pointer that links no structure (a lazily created object, one replaced as a whole) is (b).
  The definition of a lock, or of a guard class that only locks and unlocks, is `REPLACED`.
- **Translation.** No cast.
  - (a) The `sync` lock's `lock`, `read` and `write` take `&self` (RULEBOOK 2.7; `T` from the lock's lock-guards.tsv row). The guard is bound to a named local or a `match` arm and lives exactly as long as the C++ holds the lock, calls made under it included (IO, inner SQL, other crates); work the C++ runs after unlocking stays after the guard drops. Where the C++ takes the lock in one function and releases it in another, the guard is the `sync` module's owning guard (`lock_arc`, `read_arc`, `write_arc` on an `Arc` of the lock), returned by the function that locks and dropped where the C++ unlocks (s8-numerics-platform.md 5 rules 5 and 6, design amendment A1-8). An `ObRecursiveMutex` keeps its C++ calls (`lock`, `trylock`, `unlock`, the guard) on the `sync` module's type, which holds no data (s8-numerics-platform.md 5 rule 8, design amendment A1-3).
  - (b) An `Atomic*` field, whose methods take `&self`, with the ordering RULEBOOK 2.7 gives (the atomic-fields.tsv row); a single published pointer is an `ArcSwap` or an arena id in an atomic (s8-numerics-platform.md 4 rule 8).
  - (c) An `Arc` clone and drop (RULEBOOK 2.2; s3-memory.md R1; the refcount.tsv row). A last release that routes the object somewhere is a handle whose `Drop` calls `Arc::into_inner` (s3-memory.md R2). A test that the caller holds the only reference left is `Arc::get_mut` where no `Weak` of the type exists; where one can, or where the C++ tests the count inside the object, the C++ count stays beside the `Arc` for the test and decides no free (s3-memory.md R1, design amendment A1-11 (b)). A count of references to an on-disk object named by an id stays a count, released where the C++ releases it (s3-memory.md R1, design amendment A1-2).
  - (d) The write goes through the guard's `&mut T`. For a field an `ObRecursiveMutex` guards, the guard is that of the `Mutex<T>` beside it, bound to a named local for the access, dropped before any call that can take the reentrant lock again and kept across one that cannot (s8-numerics-platform.md 5 rule 8, design amendment A1-3).
  - (e) The link lives inside the lock over its structure, as an id or a row id (pilot rows 10 and 13), and the write goes through that lock's write guard, taken as the structure's rows say (for the hash join table, `Arc<sync::RwLock<PartHashJoinTable>>`, whose write lock the shared build takes for each row it inserts, pilot row 10). A reader the C++ lets skip the lock takes it for each step, marked `PERF(port)` (s8-numerics-platform.md 4 rule 5).
- **Evidence.** Each operation with its line and the sweep row that decides its primitive; for (d), the line that takes the lock and the path showing it is still held at the write; for (e), the structure, the lines where the C++ touches its links with `ATOMIC_*` and their atomic-fields.tsv rows, and the lock s8-numerics-platform.md 4 rule 5 gives it. A write that the pointer's later holders make into the structure's other fields is traced like any other write (6.2, line 1215).

### FREE_OR_HANDOFF

- **Test.** The cast's result goes only to (a) a call that frees or reallocates the object (`free`, `ob_free`, `ob_realloc`, an allocator's `free` or `realloc`, `OB_DELETE*`) or an explicit destructor call (`~T()`, `call_dtor`), or (b) a callee that takes the object over: it keeps the pointer after returning, then frees it or passes it to another thread, task, timer, queue, channel or cache. Nothing reads the object after a free.
- **Translation.** No cast. The owner drops its owned value at that statement (RULEBOOK 2.2: `OB_DELETE*` and `ob_free` become a drop; an explicit destructor call becomes `Drop`), grows it for a reallocation (an owned `Vec`), or moves it into the receiver as owned data (RULEBOOK 2.2's row for memory handed to another thread, task, timer, queue, channel or cache; ARCHITECTURE §3.1 rule 5). The owner is the one the object's arena-handoff.tsv or borrowed-views.tsv row names, where one exists; where the allocator is an arena, that owner decides whether the free becomes a drop or goes with the arena's reset (RULEBOOK 2.2's arena rows).
- **Evidence.** The free or take-over call; where the object was allocated or who owns it; for (b), where the receiver keeps the object and where it frees or passes it on.

### NO_WRITE

- **Test.** All of these hold:
  - In this function every use of the result is a read: a member read; a comparison, a pointer difference or an offset computed from the address (`key < (unsigned char *)end`, `(unsigned char *)end - key`, the base `unswizzling` subtracts); an address used only for identity or as a key; a conversion back to a const pointer or reference; a call of a member function whose body writes no member (a `mutable` member written in a const function is a write).
  - Every callee the result is passed to only reads through that parameter; where a callee passes it on, follow it.
  - A string literal cast to `char *` counts as read when nothing writes through it.
  - A copy that escapes as the object's own pointer or reference (an output parameter such as `StoredRow *&`, a return value, a member of a non-const pointer type) is followed to every reader, callers included: a write there needs no cast, so no other row of this list would find it. The evidence names each reader and what it does.
  - A copy stored in a view (`ObString`, `ObObj`, `ObDatum`, `ObRowkey` or `ObDatumRowkey`, an `ObNewRow`'s cells, an array helper, a decoder or bit stream) is followed through this function and its callees, and the view's Rust type is a shared borrow: RULEBOOK 2.2 (an `ObString` is `&[u8]` or `&'q [u8]`, `assign_ptr` is a borrow, an `ObObj` holds `Cow<'q, [u8]>`) or s5-execution.md rule 2.2 (a datum refers to a `BufTable` entry). A later write through the view elsewhere needs no cast in the C++ (`ObString::ptr()` hands out `char *`, src/oblib/lib/string/ob_string.h:288), so it has no row in this list; in Rust it does not compile against the shared borrow, and the implementer handles it as a site missing from the inventory (RULEBOOK section 5). Where the viewed data sits inside a lock in Rust (a field of a `sync` lock's `T`, or of the `Mutex<T>` beside an `ObRecursiveMutex`, s8-numerics-platform.md 5 rule 8), a borrow cannot outlive the guard, so a view the function returns or keeps past the lock takes the form its borrowed-views.tsv row gives, and that row answers for the view's later readers and writers.
  - The row is not a forwarding overload: a const member function whose body calls its non-const twin through `const_cast<X *>(this)`, or a non-const one that casts its const twin's result, is `UNKNOWN` (Q1) even when nothing is written, unless it is `IR_ID`.
- **Translation.** No cast: a shared borrow of the same object, `&T`; `&[u8]` or `&'q [u8]` for bytes; `b"..."` (a `&'static [u8]`) for a literal, since text is bytes (RULEBOOK section 1); `Cow::Borrowed` inside an `ObObj`. A callee parameter the C++ declares non-const but only reads is `&T` or `&[u8]`. A non-const member function called through the cast that writes nothing is called through its const overload where the C++ has one, and otherwise takes `&self`. A function takes `&mut` only of what it or a callee writes (s4-sql-front.md 1.3, 2.3, 3.3). Where the cast also changes the pointee type to read the bytes as another type (`*(uint64_t *)(buf + pos)`, a struct read from page bytes), the read is RULEBOOK 2.3's type-punning row (`u64::from_le_bytes`, `f64::from_bits`) or, for a stored format, that format's decoder. Where the copy is kept in a handle the design turns into an `Arc` of the object (a KV-cache handle's `value_`, s3-memory.md R5; the handle's refcount.tsv row), the reads go through that `Arc`. A view of data inside a lock that the C++ returns or keeps past the lock is its borrowed-views.tsv row's form: for the session's `MultiThreadData` strings, which sit in the `Mutex<MultiThreadData>` beside `thread_data_mutex_`, an owned copy taken under that mutex and marked `PERF(port)` (`get_current_query_string`, src/sql/session/ob_basic_session_info.h:1861-1866; pilot row 5, design amendment A1-3). An `ObExpr` pointer the C++ stores is its `ExprIdx` (the paragraph on plan expressions at the start of this section).
- **Evidence.** Every use of the result, marked read; each callee's lines that read the parameter; each reader of an escaped copy, or the escape into a view and the rule that makes it a borrow, or "escapes: none"; for a long function, the command that lists the uses and what it printed.

### OWN_BATCH

- **Test.** The write goes through a `const ObBatchRows *` (or a `const ObBatchRows *&` out-parameter) that, on every path reaching the write, holds `&` of a batch the operator itself owns (a member such as `child_brs_` or `dumped_batch_rows_`), because the operator assigned it on that path. If the pointer can hold a child's own `brs_` at the write, the row is `UNKNOWN` (Q3).
- **Translation.** Write the operator's own member through `&mut self` (`inner_get_next_batch` and its helpers take `&mut self`, RULEBOOK 2.5). The batch pointer becomes s5-execution.md rule 4.3's small enum naming whose `brs_` it reads: a child's, read through `child.brs()` at each use, or the operator's own. It is set to the own-batch value where the C++ assigns `&member`; an out-parameter is `&mut` of that enum (RULEBOOK 2.1). Rule 4.3 gives this form for hash join's substitution (src/sql/engine/join/ob_hash_join_op.cpp:3365-3368). Rule 4.3 gives the enum for the 11 members that keep a batch pointer across calls; this list uses it as well for a local or an output parameter that can name either batch, which is an extension of the rule for the developer to confirm, as `LOCAL_COPY` and `PARAM_TO_MUT` are.
- **Evidence.** The member's declaration; the assignment of `&member` on each path to the write; the write; the pointer's later readers and writers (a write through `skip_` needs no cast in the C++; see Q3).

### PLAN_FIELD

- **Test.** At execution time, the write lands in an object of the cached plan (an `ObExpr` field, not a datum in the frame; an operator spec reached as `spec_`, `MY_SPEC` or `get_spec()`; a DAS ctdef; the `ObPhysicalPlan` or its `ObExprFrameInfo`), and every reader of the written field runs in the same execution (the same operator, frame or PX worker). A write while code generation builds the plan is not this: the generator owns what it builds, so that is `ALREADY_MUT`. A field that another execution or another PX worker reads is `UNKNOWN` (Q5).
- **Translation.** The field moves out of the plan into per-run state (s5-execution.md rule 3.1): expression state into the frame (the expression's slot or its `expr_ctx` entry in the `FrameState` its `EvalFrame` evaluates over: the run's, or for a temporary expression, `ObRTDatumArith` or a PL routine the kept state of s5-execution.md rule 3.9, design amendment A1-5); spec or ctdef state into the operator, as a field of the operator struct under the spec member's name, written through `&mut self`. Readers read it there. The plan stays immutable and shared (ARCHITECTURE §3.1 rule 2).
- **Evidence.** How the plan object is reached; the write; every reader of the field and that each runs in the same execution.

### DATUM_BYTES

- **Test.** The write lands in the bytes an `ObDatum` or `ObStorageDatum` refers to (`datum.ptr_`, `cells()[i].ptr_`, a datum's string bytes), in expression code, a row store or a storage decoder, and the writer is the producer of that buffer.
- **Translation.** Through the datum API (s5-execution.md rules 2.2 and 2.3): a value of 8 bytes or fewer is written into the datum itself (its setters, or its `loc` bytes); a longer value is written into the buffer the datum refers to, through `&mut` of that buffer, by its producer: `BufTable::split_mut(id)` on the expression's own result entry (rules 3.3, 3.5), or on the entry a scan or an operator registered for its own current batch (rule 2.6: each entry has one producer, its only writer), or the row store's own block through the store's `&mut self` for a stored row's cells. A copy whose source may overlap the destination is `copy_within` (RULEBOOK 2.5).
- **Evidence.** Where the datum's `ptr_` was set, that is, the buffer's origin (`get_str_res_mem`, an allocation, a store block, a decoder's output); the value's size class (8 bytes or fewer, or longer); the write; that the writer is the buffer's producer and no other reader keeps the old bytes, or the row is `UNKNOWN` (Q7).

### NEW_BYTES

- **Test.** The written bytes were allocated or deep-copied by this function, returned newly allocated by a callee it called, or copied by every caller of the function just before the call; and until the write nothing but views made on that path refers to them.
- **Translation.** Write through the `&mut [u8]` the allocation gives (`alloc_slice_copy`, a `Vec<u8>`, a `Box<[u8]>`; RULEBOOK 2.2) before the bytes are stored as a shared view. Where the C++ writes after it stored the view, copy the bytes into the statement bump with the change and assign the view to the copy (s4-sql-front.md 1.3, the row for a write into a node's bytes).
- **Evidence.** The allocation or copy, the write, and every view that points at the bytes between the two; where the copy is in a caller, each caller, with the command that lists them.

### ALREADY_MUT

- **Test.** All of these hold:
  - The written object belongs, directly or through members, to something the function already holds mutably: its non-const `this`, a non-const reference or pointer parameter, a local, or memory it allocated.
  - The const comes only from how the object was reached: a const accessor, a `const T *` member or out-parameter pointing into the function's own object, or a view the function built over its own memory.
  - Rust can reach the field for writing: the C++ has a non-const accessor for it, or the function can name the field in Rust. It can when the field is public; when the function is in the Rust file that declares the struct (Rust privacy is per module); when the struct is a split type, whose members are all `pub(crate)`, and the function is in the same crate (RULEBOOK section 4); or when RULEBOOK 2.3's `friend` or `protected` row opens it. If none holds, the row is `UNKNOWN` (Q9).
  - No view of the object that the function reads again after the write is alive at the write. A view here is a value the design keeps as a borrow (an `ObString`, `ObDatumRowkey` or `ObNewRow` over the object's memory; borrowed-views.tsv). A pointer to an object the design names by an id, because the C++ points to it from more than one place (RULEBOOK 2.4), is not a view: an id borrows nothing. If a view is alive, the row is `UNKNOWN` (Q6).
- **Translation.** Write through the `&mut` the function already has: the field through `&mut self` or the `&mut` parameter (the accessor's non-const overload where the C++ has one, named by the declaration index), a `let mut` local, or the `&mut` its own allocation gave. A method that writes its own fields takes `&mut self` (s4-sql-front.md 3.3).
- **Evidence.** The owner and the line that shows the function holds it mutably (a non-const signature, a local's declaration, an allocation); the path from the owner to the written object; how Rust reaches the field; the write.

### LOCAL_COPY

- **Test.** All of these hold:
  - The written object is a value Rust copies cheaply: a byte-slice view, an `ObObjMeta`, an `ObNewRow` or rowkey header, a number descriptor, a plain struct of numbers and views.
  - Every read of the written state happens in this function, or in callees it passes the object to, before it returns.
  - No reader outside sees the write: the C++ restores the old value on every path before returning, or nothing reads the original afterwards. No other thread reads it meanwhile.
  - Rust can reach the written fields (`ALREADY_MUT`'s third test); if not, the row is `UNKNOWN` (Q9).
- **Translation.** Copy the object into a local where the C++ casts (a read into a local is a statement RULEBOOK section 0 allows, and RULEBOOK 2.4 uses the same copy-out form for slots), write the local, and pass the local wherever the C++ passes the object after the cast. Restore statements stay and write the local.
- **Evidence.** The writes; every read between the first write and the return, including each call that receives the object; the restore on each path, or the original's later readers (none); the thread.

### PARAM_TO_MUT

- **Test.** All of these hold:
  - The written object reaches the function only through a const receiver (the `this` of a const member function) or a const reference or pointer parameter, including a `const X &` that is really an output.
  - Following the callers up to the object's owner, every call site holds the object mutably, or is itself made mutable by this row's evidence.
  - No other thread, `Arc`, cache or cached plan holds the object.
  - For a virtual function, every override and every call through the base pass the same test.
  - Rust can reach the written field (`ALREADY_MUT`'s third test); if not, the row is `UNKNOWN` (Q9).
- **Translation.** That receiver or parameter becomes `&mut` (`&mut self`, `&mut T`, `Option<&mut T>` where it can be NULL), each caller on the chain passes `&mut`, and the cast becomes a use of that `&mut`. A function takes `&mut` of what it or a callee writes (s4-sql-front.md 1.3, 2.3, 3.3; RULEBOOK 2.1's output-parameter row). A schema guard reached through `const ObSchemaGetterGuard *` is this case, because its getters take `&mut self` (s3-memory.md R4).
- **Evidence.** The write; each caller up to the owner, with its line; the command that lists every caller and the number of lines it printed.

## 4. When a row is unknown

A row is `UNKNOWN`, status `unknown`, when:
1. it matches an open question below (Q1 to Q9);
2. no value's test can be finished: a callee inside an island, a virtual call whose targets cannot be listed, a pointer stored where its later uses cannot be followed, too many callers to trace (Q0, with the question written out);
3. a skeptic reviewer refutes the value with evidence and the one revision is still contested (prompt 02).

A row that matches more than one question names each, in list order, in its one marker (`// TODO(port): const-cast Q5, Q8: ...`), explains each in its evidence, and stays unknown until every one is answered.

**The translation is fixed:** the UNKNOWN rule (RULEBOOK 2.10) applied to a write through const.
- Keep the C++ access path and make each step on it mutable. A const member function on the path takes `&mut self`. A const parameter or const member pointer on the path is `&mut T` (`Option<&mut T>` where it can be NULL). A const accessor is replaced by its non-const overload where the C++ has one (its Rust name from the declaration index), otherwise by the member itself. The write stays at the C++ statement.
- Add no `unsafe`, `Cell`, `RefCell`, `OnceCell` or lock, and copy nothing.
- On the line above the cast's statement: `// TODO(port): const-cast Q<n>: <the question> <file>:<line>`, the question ending in its own `?` (RULEBOOK section 3's marker form).

Why this is the conservative form: the borrow checker enforces, at compile time, the exclusive access the C++ assumed; nothing is added at run time (a `RefCell` can panic, a lock can wait); and the write lands on the same object. RULEBOOK 2.10 lists an owned copy among the conservative forms, but for a write through const a copy is not conservative: the write would land on the copy, and later readers of the original would miss it, a change the judge can see. So this list copies nothing; the developer may want RULEBOOK 2.10 to say so. When the path cannot be `&mut` in Rust, the build fails at that line, and the row comes back when its question is answered.

An unknown row's `target_translation` starts with "Conservative:", describes this form at the site, and ends with the `TODO(port)` text. Its evidence says what was traced and ends with "Why unknown:" and the design gap.

**Open questions.** Each names the design gap. The developer's answer turns every row that cites the question, and no other open question, into a confirmed row.

- **Q1. Overload pairs that share one body through a cast.** A const member function whose body calls its non-const twin through `const_cast<X *>(this)` (src/data_plane/api/data_plane/access/ob_tablet_scan.h:478), or a non-const one that calls its const twin and casts the result (src/sql/optimizer/ob_sharding_info.h:94-95), in a class that is not IR. RULEBOOK 2.3 numbers the two overloads, section 0 lets no call be replaced by the callee's body, and `&self` cannot call `&mut self`. Question: may the forwarding overload take its twin's body in place of the call (reading through `&self`, or writing through `&mut self`) when the twin writes nothing? When the twin does write, the row is `PARAM_TO_MUT` if that test holds, else Q4. Not a question for the hash-map and hash-set ports: s4-sql-front.md 2.1 rule 4 (design amendment A1-4) gives their `get` forms (`ObHashMap::get` as `get(&self) -> Option<&V>` and `get_2(&mut self) -> Option<&mut V>`, `ObHashSet::get` as `get(&self) -> Option<&K>`), so the casts inside src/oblib/lib/hash/ob_hashmap.h:259 and ob_hashset.h:151 are `REPLACED`, and a caller's cast of what `get` returns follows that rule (`NO_CONST_DROPPED` when the caller holds the map mutably).
- **Q2. Writes to the session, or through it.** Code that holds the session as `const ObSQLSessionInfo *` writes it (the cached-config refresh in `is_enable_decimal_int_type`, src/sql/session/ob_sql_session_info.h:798; `set_stmt_type`, src/sql/resolver/expr/ob_raw_expr_util.cpp:3681) or reaches the current exec context mutably through `get_cur_exec_ctx()` and writes it (example 4). s4-sql-front.md 3.2 needs the session only as a shared reference, and no design text names `cur_exec_ctx_` (`grep -rn cur_exec_ctx migration/design/*.md migration/RULEBOOK.md migration/decisions.md` prints nothing). The sweep has 49 lines containing `type_ctx.get_session()` (`grep -c`); those that only read are `NO_WRITE`. They need no `&mut`, though how the Rust session reaches the current exec context even for reading is just as undesigned, which is not this list's question. Question: how does Rust code that holds the session as `&` write session state, and reach the exec context mutably during type deduction (a parameter, a field of `ObExprTypeCtx`, a session field that allows writes through `&`)?
- **Q3. A parent that writes its child's batch.** For example the group join buffer sets `end_ = false` on its left child's `brs_` (src/sql/engine/basic/ob_group_join_buffer.cpp:377, after `batch_rows = &left_->get_brs()` at :361). s5-execution.md rule 4.3 covers only the operator's own batch. The same question comes with no cast at all when a parent writes a child's skip vector: `skip_` is a pointer member in the C++, so a const batch hands it out writable, and those sites have no row in this list. `group_child_batch_rows` sets bits through its `const ObBatchRows &` parameter (src/sql/engine/aggregate/ob_hash_groupby_op.cpp:2161), which is the child's batch after src/sql/engine/aggregate/ob_hash_groupby_op.cpp:1747; `ObMergeGroupByOp::process_batch` does the same (src/sql/engine/aggregate/ob_merge_groupby_op.cpp:733) to the batch its child returned (src/sql/engine/aggregate/ob_merge_groupby_op.cpp:386, :437). In Rust the skip vector is part of the batch (s5-execution.md part 4), so a classifier that meets such a write names it in the evidence. Question: may a parent write a child's batch flags and skip vector, or must the child reset its own (for example on rescan)?
- **Q4. Single-thread state written behind `&`.** A const member function, or a function with a const parameter, fills a cache, creates a member on first use or bumps a counter through the cast; `PARAM_TO_MUT` fails because some caller holds the object only through `&`; no other thread sees the field. The design uses `Cell` only in its closed thread-local list (s8-numerics-platform.md section 5, thread-locals rule 2) and rejects `RefCell` for the IR (ARCHITECTURE §4.1, "Rejected"); it says nothing about a `Cell` field elsewhere, and RULEBOOK 2.7 covers fields shared between threads. Question, per field: make the callers `&mut`, or allow a `Cell` or `OnceCell` field?
- **Q5. Writes to shared objects.** The written object is reachable from another thread, or is held through an `Arc` of a value the design makes immutable (a schema from the schema guard, s3-memory.md R4; the cached plan beyond `PLAN_FIELD`'s per-run state, ARCHITECTURE §3.1 rule 2; a tablet snapshot, s6-storage.md 10.1 rule 1), and no atomic-fields.tsv or lock-guards.tsv row covers the written field. RULEBOOK 2.7 says such a field is atomic or inside a lock, not which. A link of a linked structure is not this question: s8-numerics-platform.md 4 rule 5 puts it inside the lock of its structure (`LOCK_OR_ATOMIC` (e), design amendment A1-11 (a)). A field beside such a link that the structure's readers write still is: the hash join's probe sets `is_match_`, which shares a word with the chain link, in rows of the table the workers share (6.2, line 1215). Question: atomic, which lock, or a new version of the object?
- **Q6. A view over owned memory, written through the view and read again.** `ALREADY_MUT`'s first three tests hold, but the function reaches the memory through a borrow-typed view it built over its own datums or bytes (an `ObDatumRowkey`, `ObNewRow` or `ObString`), writes through a cast on the view's const accessor, and reads the view again after the write. In Rust the view's shared borrow is alive at the write. Mind the operand's type: src/storage/compaction/ob_partition_parallel_merge_ctx.cpp:506-516 has this shape, but its cast removes nothing (`multi_version_endkey` is a non-const local, ob_partition_parallel_merge_ctx.cpp:473, and `datums_` a non-const member, src/storage/blocksstable/ob_datum_rowkey.h:111), so that row is `NO_CONST_DROPPED` and the view's Rust form decides it. Question: rebuild the view after the write (a statement section 0 does not list), or give the view a mutable form?
- **Q7. Bytes that other readers see, written in place.** s4-sql-front.md 1.3's copy form holds only when nothing else sees the bytes. Here other views (parse-tree nodes, schema strings, cached blocks) read them after the write, or a writer that is not the buffer's producer writes them. Question: copy (the other readers keep the old bytes), or give the bytes' owner a `&mut` path?
- **Q8. Intrusive links written into objects another container owns.** An `ObDLinkBase` link written into an element a hash set owns: `ObUniqTaskQueue::add` links the task `task_set_.get` returned into its group's list (src/observer/ob_uniq_task_queue.h:335, :351), and the task type is an `ObDLinkBase<Task>` subclass (src/observer/ob_uniq_task_queue.h:67). Design amendment 1 settles two neighbouring cases. On the container's side, an element whose address the C++ stores outside the container is held as an `Arc` or an id, the other holders get clones of it, and it is never copied (s4-sql-front.md 2.1 rule 4, A1-4, which names `ObUniqTaskQueue`). A chain pointer that the C++ writes into stored rows of a structure whose links it touches with `ATOMIC_*`, as the hash join's `atomic_set` does, is `LOCK_OR_ATOMIC` (e) (s8-numerics-platform.md 4 rule 5, A1-11 (a)). What stays open is the intrusive link's own form, which subclassed-bases.tsv's row for the `ObDLinkBase` subclass decides (RULEBOOK 2.3, 2.8), a row not written yet. Question: does that row keep the link inside the element (and then how is it written through the container's `Arc` or id), or does the list hold the clones itself? The row cites the subclassed-bases.tsv row once it exists.
- **Q9. A written field that Rust hides from the writer.** The function holds the object mutably, or could (`ALREADY_MUT`, `LOCAL_COPY`, `PARAM_TO_MUT`), but the C++ reaches the field only through a const accessor with no non-const overload, and the field is private to another Rust file or crate. For example the execute-packet decoder sets a parameter's collation through `const_cast<ObObjMeta &>(param.get_param_meta())` (src/observer/mysql/obmp_stmt_execute.cpp:2345); `param` is its own `ObObjParam &` (src/observer/mysql/obmp_stmt_execute.cpp:2322), but `get_param_meta()` is const only (src/oblib/common/object/ob_object.h:3709), `param_meta_` is private (src/oblib/common/object/ob_object.h:3729), the setter writes only under a condition (src/oblib/common/object/ob_object.h:3703-3707), and the type is in the core crate ob-values (core-manifest.tsv:242) while the decoder is in observer (manifest.tsv:2388). RULEBOOK section 0 gives one Rust function per C++ function and 2.3's visibility rows keep the field private, so no rule adds an accessor. Question: may the port give the type a non-const accessor (under which name, since RULEBOOK 2.3 numbers only the C++ overloads), or widen the field?
- **Q0. Anything else.** The row writes its own question.

## 5. Worked examples

All four rows pass `python3 -B migration/scripts/cite_check.py` with no flag, and `show` prints the construct on each cited line.

**Example 1: `NO_CONST_DROPPED`, a cast that looks like it removes const.**
- `file`: src/sql/resolver/ddl/ob_ddl_resolver.cpp
- `symbol`: ObDDLResolver::resolve_generated_column_attribute
- `source_construct`: const_cast<char *> (line 2421)
- `classification`: NO_CONST_DROPPED
- `target_translation`: No cast: comment is a non-const local, so comment.ptr() is already the non-const overload returning char *, and the cast removes nothing. Seen while sampling, and why the tests are worded as they are:

Lines 182, 1450 and 1749 were first classified as if the cast removed const.
- The sweep's C-style heuristic has false positives (line 560); check what the cast's operand really is.
- Many `char *` casts only build a view or feed an API whose signature lacks const; read the callee before calling it a write.
- A non-const getter called through a cast may still write (line 1316's cache refresh); read its body.
- A pointer that leaves the function as a non-const output parameter, return value or member can be written later with no cast; follow it to its readers (6.2, line 1238).

## 7. Checks before a shard is handed in

- `python3 -B migration/scripts/cite_check.py <shard.tsv>` prints nothing; `... <shard.tsv> show` prints, for each cited line, the construct the text claims (the cast, the write, the declaration), not a neighbouring `if`, declaration or comment.
- Every line number names its file, unless the same clause already names it; a file name that is not unique is cited from src/ (src/query/api/query/engine/expr/ob_sql_expression.h, not ob_sql_expression.h).
- Every count comes from a command given beside it. Unused locals are not listed as writers, and functions with no caller are not listed as callers.
- The operand's declaration, and the overload its call resolves to, are named before any write is traced (section 2).
- (`file`, `symbol`, `source_construct`) is unique in the shard; `source_construct` ends in ` (line N)`.
- `classification` is `UNKNOWN` exactly when `status` is `unknown`, and every unknown row names its questions (Q0 to Q9) in its `TODO(port)` text.
- A row whose value a script proposed (section 8) carries the same evidence as any other row.

## 8. Pre-classification

A script can give some rows a value before anyone reads code, from the sweep row alone (`file`, `line`, `symbol`, `construct`, `text`), the next source line where a cast's operand starts there, and the unit lists. It applies the patterns below in this order, which follows section 2's, and a row takes the first pattern that matches. A decided row needs only its evidence written. A proposed value is where the classifier starts: it checks section 3's test for that value and for the values before it in section 2's order, then keeps or replaces it. The counts are of today's 1,888 data rows, with the patterns applied in this order.

1. `NOT_TRANSLATED`, decided (222 rows): `file` and `line` fall in a unit of not-translated.tsv (a `files` entry equal to `file`, or `file:a-b` with `a <= line <= b`), or `construct` contains `[vendored]` and no `inputs` entry of manifest.tsv or core-manifest.tsv covers `file`. This gives section 1's split: 206 island rows, 10 dropped, 4 dead, 2 vendored.
2. `REPLACED`, decided (6): `file` is src/oblib/lib/hash/ob_hashmap.h or src/oblib/lib/hash/ob_hashset.h, and `symbol` is `ObHashMap::get_refactored`, `ObHashMap::get`, `ObHashSet::get` or `ObHashSet::exist_refactored` (const-cast.tsv:358-363).
3. `REPLACED`, proposed (39): `file` is under src/oblib/lib/alloc/, src/oblib/lib/allocator/, src/oblib/lib/lock/ or src/oblib/lib/objectpool/; or `symbol` starts with `ObPxTreeSerializer::` or matches `OB_DEF_(DE)?SERIALIZE(_SIZE)?\((ObExprFrameInfo|ObPx\w*Args)\)`; or the last two parts of `symbol` are the same name containing `Guard` (a guard's constructor) and `text` matches `\b\w+_\s*\(\s*const_cast<` (a member initializer). The classifier checks that the rule's words cover the function; a guard class that does other work under the lock is translated, `LOCK_OR_ATOMIC` (a) (const-cast.tsv:568).
4. `ADDS_CONST`, decided (11): every `; `-separated entry of `construct` ends in `(adds const only)`, and every target type has exactly one `*` or `&`.
5. `ADDS_CONST`, proposed (8): the same with a two-level target (`const T **`). The classifier reads the operand's declaration (section 3; const-cast.tsv:1134 is not `ADDS_CONST`).
6. `IR_ID`, proposed (166): every target type is `T *` or `T &`, with `T` a class `IR_ID`'s test names or one declared `: public` such a class under src/sql, directly or through another. The classifier reads the operand first (a non-const operand makes the row `NO_CONST_DROPPED`), then records the writes and the arena owner.
7. `LOCK_OR_ATOMIC`, proposed (15): a target type matches `(const\s+)?((oceanbase::)?(common|lib|share)::)?(ObLatch|ObLatchMutex|TCRWLock|SpinRWLock|ObSpinLock|ObRLock|ObWLock|MemtableMgrLock|ObRecursiveMutex|LockType)\s*[*&]`. The classifier checks that every write through the result is (a); a guard class's constructor or destructor that only locks and unlocks is `REPLACED` (const-cast.tsv:1841-1842).
8. `FREE_OR_HANDOFF`, proposed (13): `text` matches `\b(free|ob_free|OB_DELETE\w*)\s*\(\s*([^()]*,\s*)?const_cast<`. The classifier checks that nothing reads the object after the free and names its owner.
9. `NO_WRITE`, proposed (216): `text` casts a string literal, matching `const_cast<\s*(unsigned\s+)?char\s*\*\s*>\s*\(\s*"` or `\(\s*(unsigned\s+)?char\s*\*\s*\)\s*"`. The classifier greps the name the literal is stored in, or follows the callee it is passed to, for a write: a write into a literal crashes the C++, but only on a path that runs.
10. `OWN_BATCH` or `UNKNOWN` (Q3), proposed (38): a target type is `ObBatchRows *`. Telling them apart needs the batch pointer traced on every path.
11. `NO_WRITE`, `LOCK_OR_ATOMIC` or `UNKNOWN` (Q2), proposed (68): a target type is `ObSQLSessionInfo *` or `ObBasicSessionInfo *`, with or without `sql::`. Telling them apart needs every use of the session, and of what is reached through it, read.
12. `UNKNOWN` (Q1), proposed (3): `text` joined with the next source line contains `const_cast<...>(this)->F(` or `const_cast<...>(static_cast<const ...>(*this).F(`, where F is the last part of `symbol`. The row is `PARAM_TO_MUT` or Q4 instead when the twin writes (Q1).

The other 1,083 rows need the code read before any value is proposed, because their values have no pattern in the site text: `NO_CONST_DROPPED` needs the operand's declaration and the overload a call resolves to; `NO_WRITE` needs every use and callee followed; `PLAN_FIELD`, `DATUM_BYTES`, `NEW_BYTES`, `ALREADY_MUT`, `LOCAL_COPY` and `PARAM_TO_MUT` need the owner of the written memory and its other readers; `UNKNOWN` needs a trace that ends at an open question. A cast to `ObExpr` is never `IR_ID` (section 3, plan expressions).
