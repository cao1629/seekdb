# ret-compare: classification vocabulary

How to write one inventory row (the seven columns of templates/inventory.tsv) for each site of migration/inventory/sweep/ret-compare.tsv: an OB error code from ob_errno or parse_define.h compared with `==` or `!=`, or used as a `case` label (definition and counts: migration/inventory/sweep/summary.tsv, row `ret-compare`). A classifier who reads this file, the rules it cites and the site can decide every value. Rows go to the shard the orchestrator names; section 11 gives the check every shard must pass, and section 13 the values a script may propose before a classifier reads a row.

## 1. What a row decides

RULEBOOK section 5 gives this list's rows two answers: what the compared code means at the site ("end of data, lookup outcome, buffer too small, retry, becomes a warning, ignored, renamed"), and whether a code-holding field is `ObResult` or `i32` (RULEBOOK 2.1). s2-errors.md 2.13 asks for the same (items 1 to 3). So:

- `classification` is what the code means at the site (section 4).
- `target_translation` gives the holder's Rust type (section 6), the row's own test in the one form s2-errors.md 2.3's table allows, so a reviewer can hold it against the site, and what the code's branch must keep (section 5). It does not re-derive the rest of the function, which follows from the rulebook (RULEBOOK section 5, last item).
- `evidence` shows where the code comes from, what the site does with it and where it goes (section 7).

## 3. Reading the site

Find four things before choosing a value.

1. **The unit.** Search the three lists for the file as a source or an input, for example `grep -nP '(^|[\t,])src/storage/ls/ob_ls_reserved_snapshot_mgr\.h([\t,:]|$)' migration/core-manifest.tsv migration/manifest.tsv migration/not-translated.tsv`. An entry may give line ranges (`file:a-b`); it covers the row only when the row's line is inside one, and one file can be split between not-translated.tsv and a manifest (src/oblib/common/timezone/ob_timezone_info.cpp is). A file on core-manifest.tsv is a core unit (section 5, "Core units").
2. **The holder**: what the code is compared with. A local, a parameter, a member, a call's result, a value assigned inside the comparison, a `switch` expression, or a tracepoint value.
3. **The producer**: what put the code in the holder on the way to this line. Usually the call inside the `OB_FAIL(...)` just above; otherwise the assignment, or for a parameter or member its writers. Read the producer's body far enough to cite the statement that sets the compared code (for an interface: the declaration and one implementation). When no statement of the producer can set the compared code (src/storage/compaction/ob_compaction_diagnose.cpp:648 tests `OB_HASH_NOT_EXIST` after `diagnose_minor_exe_dag`, which forwards to a walk of the ready list that never returns it: src/storage/scheduler/ob_dag_scheduler.cpp:4229, :2940-2961), the evidence says so with the producer's lines, the row takes the value of what the branch would do with the code, and the test stays: RULEBOOK section 0's list of statements a translation may remove does not name it.
4. **The code's branch**: what runs when the holder holds the compared code.
   - `OB_X == h`: what the comparison guards: the `if` body, the loop body, the true arm of `?:`, the rest of an `&&`.
   - `OB_X != h`: what runs when the comparison is false: the `else`, or, with no `else`, the statements after the `if`; after a loop condition, what follows the loop.
   - `case OB_X:`: the case body up to its `break`, with the case bodies it falls into.
   - Statements that every other code reaches too (after an `if` with no `else`, after the loop or the `switch`) are not done because of the code: they count only for where the code goes (still reported, reset, overwritten or copied). At src/observer/mysql/ob_sync_plan_driver.cpp:68 the two codes skip only the body at :69-72; the retry flag at :74-75 and `ret = cli_ret` at :83 run for every code, so they make the row neither `RETRY` nor `RENAMED`.

A code is **reported** when it leaves the site toward the caller: it stays in `ret` (or in the holder the function returns), is returned, or is written to the out-parameter or field through which the function reports this outcome.

A line that compares several codes: decide each code; the row takes the first value in section 4's order that any of its codes gets, and the evidence names the value of each other code when it differs.

## 5. What target_translation says for each value

Every row spells out its own Rust test in the form section 6 gives for its holder (`!matches!(ret, Err(OB_ITER_END))`, not "the table's form"), then the value's part below, with the rules cited in parentheses.

| Value | target_translation |
|---|---|
| `NOT_TRANSLATED` | `none:` and the reason, citing the entry: `none: dead (not-translated.tsv:<line>)`. For the grammar: `none: the parser's C core stays C (decisions.md Decision 13)` |
| `CODE_PREDICATE` | Over a parameter holding the code: the predicate takes `ObError` (s2-errors.md 2.1 rule 6) and answers `matches!(code, OB_X \| OB_Y)` with the C++'s codes, one pattern for an `\|\|` chain (2.1 rule 3: the constants are patterns); any other comparison is its own `matches!` or `!matches!`, joined as the C++ joins them (`OB_X != code && OB_Y != code` is `!matches!(code, OB_X) && !matches!(code, OB_Y)`, s2-errors.md 2.3's table), and a `switch` is `match code { OB_X \| OB_Y => .., _ => .. }` with its fallthrough as RULEBOOK 2.3 writes it. Add these clauses where they apply:

- **Core units.** A row whose file is on core-manifest.tsv: core units are written against the design (RULEBOOK section 0), and s2-errors.md's rules bind the core too (its opening list), so the answer is the same, given for where the core keeps the function; a core API that replaces a C++ API keeps that API's codes at its boundary, whatever it uses inside (s2-errors.md 2.4 rule 2; s3-memory.md Example E8 shows core code binding the error in a `match` arm). Add `Core unit (core-manifest.tsv:<line>): this form where the core keeps the function (RULEBOOK section 0).`
- **Tests that go with their branch.** A test inside a branch that a section-2 rule removes goes with it: the failure branch of a call that can no longer fail (s2-errors.md 2.2 rule 3; RULEBOOK section 0, "a branch that handled a general allocation failure"), or the "already failed" branch of a comparator whose every caller sees its error, which returns `ObResult<bool>` (s2-errors.md 2.4 rule 5; RULEBOOK 2.1, the comparator row). - **Macro bodies.** A row whose symbol is `#define NAME`: the test sits in the macro's Rust form, an `#[inline] fn` if the macro evaluates each argument once with fixed types, else a lowercase `macro_rules!` (RULEBOOK 2.3, the function-like macro row); a `macro_rules!` body reaches the caller's `ret` only through a parameter, which is why `ob_fail!` names it at the call (s2-errors.md 2.3). The macro's uses are not rows (summary.tsv). - **Conditional code.** A row under `#ifdef ERRSIM`, a platform `#if` or `#ifndef NDEBUG` is classified as usual and sits in `#[cfg(feature = "errsim")]`, the matching `#[cfg]` arm, or `#[cfg(debug_assertions)]` (RULEBOOK 2.3).
- **Generated code.** The `[generated]` row of src/share/system_variable/ob_sys_var_meta.cpp is written by gen_ob_sys_variables.py, whose Rust back end is in ob-schema (s6-storage.md 6.1): classify it as usual, whether or not not-translated.tsv comes to list the file as `generated`; the Rust goes into the generator's back end, never into its output (RULEBOOK 2.9, last item; finding F2).

OB_SUCCESS : ret;`) is an `if` expression written as the C++ writes it: s2-errors.md 2.4 rule 4 turns only the "`a` unless `a` is success, then `b`" merges into `and`.

## 6. The holder: its Rust type and the test's form

| Holder | Rust type | The test |
|---|---|---|
| `ret`, `tmp_ret`, `temp_ret`, and any local or parameter that holds only `OB_SUCCESS` or codes (`hash_ret`, `err`, a `ret_code` parameter) | `ObResult`; an `int &` parameter is `&mut ObResult` (s2-errors.md 2.2 rules 2 and 5) | `matches!(h, Err(OB_X))`, `!matches!(h, Err(OB_X))`; an `\|\|` chain of `==` on one holder is one `matches!(h, Err(OB_X \| OB_Y))`; any other comparison is its own `matches!` (2.3 table). ## 7. Evidence

Every row that is not `NOT_TRANSLATED` shows, in this order:

1. `sweep: ret-compare.tsv:<N> (data row <N-1>).`

## 8. Unknown rows

- The classification is `UNKNOWN`, with status `unknown`, when the tests of section 4 do not settle the value: the producer cannot be found (a virtual call whose overrides differ on the code, a holder with many writers), or a reviewer's refutation stands after one revision (prompt 02).
- The classification stays the value and only the status is `unknown` when the value is settled but the translation depends on an open question of section 9, or the holder's type cannot be decided.
- The target_translation is deterministic either way. It follows RULEBOOK 2.10's UNKNOWN rule: the local-ret form, the test in section 6's form on an `ObResult` holder (Q1's form on an integer holder), the branch exactly as the C++ writes it, and on the line before the test the marker `// TODO(port): ret-compare <Q1, Q2, Q3, Q4 or unknown>: <the question> (<C++ file:line>)`, one per site, counted in the file's trailer (RULEBOOK section 6, item 1).
- The evidence ends with `Question:` and the question in one sentence.

## 9. Open questions

The design leaves these cases undecided. Until the developer answers, each takes the conservative translation below, with status `unknown` and its `TODO(port)` marker.

**Q1. How is a code held in a plain integer tested?** s2-errors.md 2.2 rule 5 keeps a holder that is sent, stored or holds values that are not codes as an integer under its C++ name, and names two conversions, `ObError::from_code` and `code()`, without saying which a test uses. For a holder whose C++ type is an integer other than `int` that stays an integer (the `int64_t` `ObDDLTask::ret_code_`, src/rootserver/ddl_task/ob_ddl_task.h:734, if it does), it does not say which Rust type it keeps. Conservative translation: the holder keeps its C++ integer type; an `int` holder is tested as `matches!(ObError::from_code(h), Err(OB_X))`, and a `switch` over it becomes `match ObError::from_code(h) { .. }`, with `case OB_SUCCESS` as `Ok(())`; a wider holder is compared as the C++ promotes it, `h == i64::from(OB_X.code())`, and a narrower one as `i32::from(h) == OB_X.code()`. Each form gives exactly the C++ answer for every value. Recommended answer: the `from_code` form for every integer holder of `int` width, which is how the design already reads raw codes (s2-errors.md 2.2 rule 6, 2.4 rule 8) and which keeps one form for `==`, `!=` and `switch`.

**Q2. Does a caller that treats `OB_INIT_TWICE` as an outcome keep the type's init state?** RULEBOOK 2.1's `init()` row and s2-errors.md 2.2 rule 7 keep an object's not-initialized state only where a caller tests it (`OB_NOT_INIT`). They say nothing of a caller that calls `init()` again on purpose and treats `OB_INIT_TWICE` as success, which is how an object is set up on first use. Conservative translation: the type keeps `is_inited_` and an `init()` method with its `OB_INIT_TWICE` check instead of a constructor, the member stays a plain field set up on first use, and the test stays as written. Recommended answer: yes; a caller that takes `OB_INIT_TWICE` as success tests the init state as an outcome, which is the case the `init()` row's exception is written for, so the conservative translation is also the reading closest to the rule.

**Q3. What does a predicate that answers true for `OB_SUCCESS` take, when a caller can pass `OB_SUCCESS`?** s2-errors.md 2.1 rule 6 gives predicates an `ObError` and their callers `ret.is_err_and(..)`, which is false for `Ok(())`; that matches the C++ only for a predicate that is false for 0. Conservative translation: that predicate takes the caller's `ObResult` and tests `matches!(code, Err(OB_X \| OB_Y))` in the C++'s shape, so `Ok(())` gets the C++'s answer for 0, and its callers pass their `ObResult` as it is. Recommended answer: the conservative translation, which gives the C++ answer for 0 with one function and no change at the callers.

**Q4. How is a code reached through a C++ reference to another holder written?** s2-errors.md 2.4 rules 5 and 6 give a Rust form to the `int &ret = <x>ret_;` sites they list (the comparators, the schema `operator=`, the two hash-map callbacks, the SPI guards, `ObSqlArrayExpandGuard`), and RULEBOOK section 0 lets a translation add the calls that replace a guard's destructor only because rule 6 adds them. The design says nothing of `int &ret = errcode_;` (src/sql/ob_result_set.cpp:350, src/sql/das/ob_das_task.cpp:44) or of other guards that keep `int &ret_` to their creator's `ret` and read it in their destructor (src/sql/engine/expr/ob_expr_lock_func.cpp:98-104; src/storage/access/ob_global_iterator_pool.h:145-148). Conservative translation: no Rust reference is kept. A member alias is written as the member itself, `self.errcode_` wherever the C++ writes `ret`; a guard takes the SPI guards' form (s2-errors.md 2.4 rule 6): each place that reads or writes the creator's `ret` takes `ret: &mut ObResult`, and the destructor becomes a method the creator calls at each exit of its function. Both read and write the code at the moments the C++ does. Recommended answer: the conservative translation, which extends rule 6's form for the SPI guards to every guard that keeps a reference to its creator's `ret`.
