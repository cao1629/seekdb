## AREA: coupling
**What it is:** How seekdb's modules depend on each other: #include edges at module, subdirectory and file level, link-level edges (a header in one directory whose code is defined in another), and global state that ties modules together (GCTX, server_service<T> slots, get_instance singletons, GCONF, THIS_WORKER). Together these decide whether the C++-to-Rust move can go one piece at a time or must go as a whole.

**Size split:** Scope: every git-tracked file under src/ and rust/ with extension .h .hpp .cpp .cc .c .ipp .inc .y .l .rs. Total: 6,670 files, 2,783,609 lines. Hand-written C/C++: 6,546 files, 2,338,379 lines. Hand-written Rust (rust/sql-nio): 23 files, 8,448 lines. Generated code checked into git: 32 files, 88,107 lines. These are src/share/ob_errno.{h,cpp}, src/oblib/lib/ob_errno.h, src/share/mysql_errno.h, the sysvar outputs of src/share/system_variable/gen_ob_sys_variables.py (ob_system_variable_init/alias/meta, ob_sys_var_class_type.h, ob_system_variable_factory.{h,cpp}), src/oblib/grpc/standbyservice*.pb.*, src/share/geo/ob_vector_tile.pb-c.*, src/oblib/lib/codec/ob_generated_*_bp_func.cpp, rust/sql-nio/include/nio.h, and the split compile parts ob_str_datum_funcs_compilation_N.cpp and ob_expr_str_cmp_func_part_N.cpp. Data tables: 3 files, 320,504 lines (src/storage/fts/dict/ob_ik_dic.cpp 276,043; src/oblib/common/timezone/ob_timezone_info.cpp 39,989; src/oblib/lib/charset/ob_ctype_utf8_tab.h 4,472). Vendored zstd 1.3.8 (src/oblib/lib/compress/zstd_1_3_8/zstd_src): 47 files, 25,154 lines. Code that came from libeasy/libev (src/oblib/easy): 19 files, 3,017 lines. Some headers are generated at build time and are not tracked: 42 include lines point at share/inner_table/ob_inner_table_schema*.h/.ipp, which live under build/generated. Method: a python one-off over `git -C <wt> ls-files src rust` that sorted files by path regex, looked for generator markers in the first 30 lines ("DO NOT EDIT", "generated by"), and found files that lack an OceanBase/seekdb license header (that check found zstd and easy). Correction to the given facts: the 143 tracked .inc files are mysqltest include scripts (tools/obtest/include 62, tools/deploy/mysql_test 46, tools/obtest/t 35), not C++. No quoted C++ include targets a .inc file.

**Summary:** Counting only #include lines, seekdb is close to layered. Across 17 top-level modules, 25,259 resolved include lines form an acyclic graph except for 4 lines in 3 files, which tie sql, storage, rootserver and pl into one cycle. All 4 lines came from commit d51422b54 on 2026-08-31. The repo's own boundary checker reports the same 4 violations, but no CI workflow runs it. That layering is recent (Bazel/module_check work from 2026-08) and is kept by convention only. It is also partly cosmetic: the src/query/api and src/data_plane/api roots moved headers but not code. 109 classes declared under query/api are defined only in src/sql, and 74 storage files use them (the pushdown filter, ObExpr and ObEvalCtx). 59 data_plane/api classes are defined only in storage, and 87 sql files use them (ObTxReadSnapshot, ObDatumRow). So at link level sql and storage call each other, and the table-scan parameter carries raw sql::ObExpr and filter-executor pointers into storage. One level down, each big module is a single cycle: 18 of 19 subdirectory groups in src/sql and 30 of 33 in src/storage. At file level, include cycles are small (29 cycles covering 73 files), because 5,556 forward declarations hide the real dependencies. Every .cpp is heavily tied to the base libraries: the median .cpp pulls in 557 project headers, 443 headers reach at least half of the 2,936 .cpp, and lib/ob_define.h reaches 2,856. Global state is widespread: 1,224 server_service<T>() lookups over 122 types (MTL is gone), 892 GCTX uses, 683 GCONF uses and 623 ::get_instance() calls. Lower layers also call back into the SQL engine at runtime through inner SQL (ObMySQLProxy/ObISQLClient/ObMySQLTransaction). Only a few narrow, C-like seams exist: the Rust sql-nio C ABI (33 functions plus 4 callbacks), the extern "C" parser boundary (ParseNode), logservice (its code reaches only oblib and share), and inner SQL as a SQL-text boundary. My conclusion: base libraries, logservice, parser and network could move piece by piece. The sql+storage+query/data_plane+pl group (about 1.83M lines, including the 276k-line dictionary) has to move as one unit, or its scan and filter boundary has to be redesigned first.

**Structure call (surveyor):** Redesign at one boundary, and module-level translation elsewhere. Rust crates must not depend on each other in a cycle, while modules inside one crate may. The subdirectory cycles inside src/sql (18 of 19 groups) and src/storage (30 of 33) therefore do not force a redesign by themselves: each module can become one crate with modules that mirror its directories. Three things do force a choice. (1) sql and storage call each other at link level through the api roots (C4). The table-scan parameter passes raw sql::ObExpr, ObPushdownOperator and ObPushdownFilterExecutor pointers into storage, and storage evaluates them (C5). So the two can be separate crates only after that boundary is redesigned, for example by passing storage a filter description instead of the SQL engine's objects. The alternative is one large crate of about 1.83M lines. (2) The global service slots (server_service<T>, 1,224 uses over 122 types) and GCTX (892 uses) map mechanically onto Rust statics (OnceLock), but that keeps the nullable, lifecycle-guarded pattern (151 null checks, 113 SERVER_MODULE_SCOPE). Removing it means passing a context struct, which touches every call site. (3) The oblib/lib containers are header-only templates (C16), so no C ABI can hand them to the remaining C++. A bottom-up start must keep the C++ versions alive until the last C++ caller is gone. Files that force the call: src/data_plane/api/data_plane/access/ob_tablet_scan.h, src/query/api/query/engine/basic/ob_pushdown_filter.h with src/sql/engine/basic/ob_pushdown_filter.cpp, src/share/rc/ob_server_runtime.h, src/share/ob_server_struct.h.

**Structure call check (verifier):** I partly agree. Parts I agree with: (1) The subdirectory cycles inside src/sql (18/19) and src/storage (30/33) do not by themselves force a redesign, because a crate's internal modules may form cycles. (2) Storage really does run SQL-engine code. Non-virtual ObPushdownFilterExecutor::execute_skipping_filter (sql/engine/basic/ob_pushdown_filter.cpp:1451) is called from storage/access/ob_sstable_index_filter.cpp:76. ObExpr::eval is OB_INLINE in query/api/query/engine/expr/ob_expr.h:1039, calls through the eval_func_ function pointer (:657) and reads SQL struct fields directly. 544 of 688 storage .cpp transitively include query/api headers. So sql and storage cannot become separate crates as they are. (3) GCTX and the server_service slots map onto statics mechanically; the slots are plain non-atomic pointers (ob_server_runtime.h:127-148). Parts I disagree with or would widen: (a) The group that must move together is larger than stated. Link-level edges also run from sql/storage/rootserver/pl into observer through query/api declarations implemented in src/observer: the vector index code (src/observer/vector_index, 25,210 lines, used by e.g. sql/das/iter/ob_das_hnsw_scan_iter.cpp and storage/ddl/ob_ddl_pipeline.cpp) and ObInnerSQLConnectionAccess (static functions in observer/ob_inner_sql_connection.cpp, used by 12 sql, 3 storage and 4 rootserver files). So observer is not a clean top layer, and 'unit 12 = observer' does not stand at link level. (b) The redesign choice is not only 'pass storage a filter description'. Storage can own a trait or function-pointer interface that sql implements, and eval_func_ already works this way. The cheap-looking alternative, pulling the expression/filter runtime into a lower crate, is costly: ob_pushdown_filter.cpp's include closure holds 230 sql headers and ob_expr.cpp's 124. (c) The bottom-up start is better supported than the survey shows. By the same heuristic, share, oblib/common, oblib/rpc and logservice have 0 classes whose member definitions live only in a higher module, and oblib/lib's single hit (ObArrayHashMap) is a same-name class in storage/fts. It is also harder than the survey shows, because upper modules subclass base-layer classes (ObTimerTask 72, ObDLinkBase 72, ObIKVCacheKey/Value 16/17, ObITask 24 and ObIDag 9 in data_plane, ObIReplaySubHandler 14, ObICheckpointSubHandler 15, AppendCb 8, ObFuncExprOperator 313). A base class moved to Rust cannot be subclassed from C++, so every such class needs a vtable bridge or must stay in C++. That is a larger drag than header-only templates alone.

**Units of work:** At module level, after the 4 violating include lines are fixed, 17 modules form a DAG. At link level these units remain: (1) oblib/easy, (2) oblib/lib, (3) oblib/common, (4) oblib/rpc together with the existing rust/sql-nio, (5) oblib/grpc, (6) objit, (7) share, (8) logservice, (9) one group of sql + storage + query + data_plane + pl (1,833,562 lines) that stays together unless the scan/filter boundary is redesigned, (10) standby, (11) rootserver, (12) observer. That is 12 units, one of which holds about 66% of the code. The parser (src/sql/parser plus parse_node.h) and the sql-nio network layer can move separately because they already have C boundaries. Inside a unit, the natural translation unit is a group of files sharing a path stem (header + .cpp + .ipp): 3,825 groups in 326 directories (sql 1,301, storage 801, share 426, oblib/lib 392, observer 267). They must be matched by class/basename across directories, not by path, because 73 api headers and ObPL are implemented in another directory. The 29 file-level include cycles (73 files) each have to move as one batch.

**Public-surface tests:** All 793 .test files are mysqltest scripts that drive the server through SQL, so they test the whole process, not one module. tools/deploy/mysql_test has 283: test_suite/geometry 42, vector_index 22, fork_table 18, fts_index 15, subquery 11, expr 11, type_date 10, global_index 7, trx 5, storage 3, and 93 in t/. tools/obtest/t has 500, grouped by directory: primary_standby 156, storage 63, rootservice 42, trans 33, quick 29, minor_freeze 26, table_redefinition 23. Every DML or query test crosses the sql->storage scan boundary (C5), and the storage, minor_freeze and trans groups also exercise storage/logservice/transaction together. Only 3 tracked gtest files exist (2 in deps/oblib/unittest, 1 in tools/ob_error). No test imports internals, so changing module boundaries cannot break a test. It also means no test can check one migrated module in isolation: a hybrid C++/Rust build can only be checked through the full server.

**Hard parts:**
- SQL expression objects cross into storage as raw pointers. ObVTableScanParam in src/data_plane/api/data_plane/access/ob_tablet_scan.h holds const sql::ExprFixedArray*, sql::ObPushdownOperator* and sql::ObPushdownFilterExecutor*, and storage calls methods on them (src/storage/access/ob_sstable_index_filter.cpp:76 -> src/sql/engine/basic/ob_pushdown_filter.cpp:1451). Storage and sql alias the same objects, so there is no single owner, and lifetimes span both modules.
- Global service slots: template<typename Service> struct ObServerServiceSlot { inline static Service *service_; } in src/share/rc/ob_server_runtime.h. They are bound and unbound at runtime by src/observer/omt/ob_server_runtime_controller.cpp (83 BIND_SERVICE) and src/standby/standby_module.cpp. Rust needs either OnceLock/ArcSwap statics per type or explicit context passing through 1,224 call sites.
- GCTX (src/share/ob_server_struct.h) is a zero-initialized singleton (MEMSET(this, 0, ...)) of raw pointers to the schema service, SQL proxies, config manager and SQLite pool, used 892 times. It has no clean equivalent in safe Rust without redesign.
- Inner SQL goes back up the stack: ObMySQLProxy/ObISQLClient (src/oblib/common/mysqlclient) -> ObInnerSQLConnection (src/observer/ob_inner_sql_connection.cpp) -> sql -> storage, called from rootserver, share and storage. A migrated lower module still needs a way to call up into whichever language the SQL engine is in at that time.
- Header-only template containers and hash maps in src/oblib/lib/container and src/oblib/lib/hash (ObSEArray, ObIArray, hash maps; 25,749 header lines against 1,042 .cpp lines) are the common types in every api signature (ObIArray appears 290 times in the api headers). They cannot sit behind a C ABI, so every FFI seam needs its own conversion layer.
- Macro frameworks used in every module: OB_FAIL (100,009), USING_LOG_PREFIX (2,347 files), OB_UNIS_VERSION/OB_SERIALIZE_MEMBER (1,991 uses, which fix on-disk and wire formats), TO_STRING_KV (2,676). A per-file translation has to reproduce these before any file compiles.
- Unity builds (216 groups over 2,804 sources; cmake/Utils.cmake:84, and :119 to undef USING_LOG_PREFIX): a file may compile only because an earlier file in its group included what it needs. Translating file by file has to rebuild each file's real imports.
- Classes are split across directories: 73 api headers have their .cpp in sql or storage, and ObPL (src/sql/pl/ob_pl.h) has members defined in both src/pl and src/sql. File-based work units must be keyed by class, not by path.
- FFI conventions any seam must follow, as seen in rust/sql-nio: C++ passes an empty ObString as nullptr plus length 0, so Rust must not call from_raw_parts on it (commit 076eb309b). Reverse callbacks from Rust into C++ (ob_sql_sock_handler_on_* in rust/sql-nio/src/ffi_types.rs:53) are needed, and the crate has 186 `unsafe` in 9,074 lines. Each new seam carries a similar share of unsafe code.

**Verifier's trust note:** The survey can be trusted for its counts. I re-ran nearly every number with an independent resolver, git grep or git blame. The module cycle, the 4 offending lines and their commit, the file-level SCCs, the closure sizes, the global-state counts, the depmap_c.py resolution rate and the size split all reproduce exactly or within a few percent. The conclusions are sound in direction, but the link-level analysis was run only on the query/api and data_plane/api to sql/storage pairs. That missed the query/api classes implemented in observer (vector index and inner SQL access), which pull observer into the cycle. That inheritance makes a bottom-up, piece-by-piece start harder than the survey's 'base libraries could move piece by piece' suggests, even though the base layers are clean at link level. Use the numbers as they are. Before any migration decision, widen the 'must move together' group to include parts of observer, and add the inheritance bridging cost to the bottom-up plan.

## AREA: runtime
**What it is:** The runtime is the layer under SQL and storage that owns threads, memory accounting and allocators, disk IO, the hand-off of network requests to SQL worker threads, timers and the background DAG scheduler, the int-return-code error convention, crash and signal handling, and configuration parameters. In this branch it is already single-tenant and single-node: the TG thread-group framework, MTL tenant lookups and the RPC framework were deleted, and the MySQL network front end is the existing Rust crate rust/sql-nio (mio, no async runtime) called from C++ over a C ABI.

**Summary:** The runtime is about 94k hand-written lines plus 31k generated, 3k data and 3k vendored, and recent commits have already made it simple: the TG thread-group framework (8d49c42e7), multi-tenancy/MTL (03b513560, 3609383cd) and the RPC framework (ee560bb45) are gone. What is left is a plain single-process design: every thread goes through lib::Thread, a Rust sql-nio reactor pushes requests into one priority queue served by a pool of blocking ReqWorker threads, 58 ObTimer objects share one ObTimerService, one DAG scheduler runs compaction/DDL work, and disk IO uses libaio on Linux with condvar waits. That thread and IO model maps directly onto Rust std threads, Mutex/Condvar and channels; nothing in it needs async, and the existing sql-nio crate already uses mio with plain threads. Memory is the part that does not keep its shape: ob_malloc returns NULL at the server or per-ctx hard limit (after first trying to evict KV cache), callers turn that into OB_ALLOCATE_MEMORY_FAILED at 4,976 sites, every container insert returns int (7,135 push_back calls), and most objects live in ObArenaAllocator arenas whose free() is a no-op. Stable Rust collections abort on OOM and the Allocator trait is nightly-only, so a port has to choose between try_reserve-style fallible APIs with custom arena-aware collections, or a global allocator that blocks like today's glibc malloc hook (which already retries forever every 10ms). The sql-nio crate already takes the try_reserve route. Per-thread ambient state (THIS_WORKER, the CURRENT_CONTEXT stack of Flow objects, thread-locals in 126 files, and context macros that read and write the caller's local ret) plus 122 global service slots bound at runtime are what make a line-by-line translation non-idiomatic; in Rust these become explicit context arguments or scoped guards. The error convention is the easiest part: 80,001 `if (OB_FAIL(...)) {` blocks, 89% with empty bodies since 8a8d6f5a8 removed 55,206 LOG_WARN lines, become `?`. But about 6,000 uses of error codes as normal outcomes (OB_ITER_END, OB_ENTRY_NOT_EXIST, OB_HASH_NOT_EXIST, OB_EAGAIN) should become Option or enum results, and the 1,546 codes must stay stable because 142 of 283 CI tests check errors. Two-phase init (is_inited_ in 1,071 files) and locks declared next to the data they guard (at least 546 declarations in 284 files) are defensive patterns Rust would remove, but moving fields under Mutex<T> is a per-class restructuring. Intrusive lists, manual refcounts, raw parent/child DAG graphs, hazard-version reclamation and siglongjmp-based crash recovery need unsafe code or a redesign. The bug history has fixes of exactly the kinds Rust's ownership and Send/Sync rules prevent: a worker list changed without its lock, a worker double free, and arena-lifetime use-after-frees. All CI tests are end-to-end mysqltests, so they survive an internal rewrite as long as error codes, parameter names and DEBUG_SYNC point names are preserved.

**Structure call (surveyor):** Split verdict. The process/thread model, timers, IO manager thread layout, signal threads, configuration table and the network hand-off can keep their structure: they are OS threads, queues, condvars and a parameter table, and map onto std::thread, Mutex/Condvar, channels and a declarative macro (or build script) for the 289 parameters, with no need for an async runtime (sql-nio already runs on mio with plain threads). The error convention also keeps its structure mechanically (the OB_FAIL chains become `?`), though error-codes-as-outcomes should become Option/enum. Memory management and the ownership model built on it force a redesign: fallible allocation everywhere (NULL -> OB_ALLOCATE_MEMORY_FAILED, int-returning push_back), polymorphic ObIAllocator where free() may be a no-op, arena-owned object graphs, a thread-local stack of memory contexts driven by macros that write the caller's ret, per-thread THIS_WORKER state, 122 mutable global service slots, locks separate from data, intrusive lists, manual refcounts and a raw-pointer DAG graph. Translating these one-to-one gives unsafe-heavy Rust with raw pointers everywhere; idiomatic Rust needs an explicit context/allocator parameter, arena lifetimes or index-based graphs, Mutex<T>-wrapped state, and a decided OOM policy (fallible try_reserve-style APIs and custom collections for query memory, plus a global allocator that blocks or aborts for everything else). Files that force the call: src/oblib/lib/rc/context.h, src/oblib/lib/allocator/page_arena.h, src/oblib/lib/alloc/ob_malloc_allocator.cpp with src/oblib/lib/resource/ob_resource_mgr.cpp, src/oblib/lib/worker.h, src/share/rc/ob_server_runtime.h, src/data_plane/api/data_plane/scheduler/ob_dag_scheduler.h, src/share/io/ob_io_define.h.

**Structure call check (verifier):** I agree with the split verdict, with three changes. (1) The memory half still forces a redesign, but for a partly different reason. The survey's central example (ob_malloc returning NULL at a server-wide limit enforced in ObMemoryMgr::update_hold) is not the default runtime. Linux and macOS builds default to jemalloc (CMakeLists.txt:213-214, deps/external/CMakeLists.txt:17-19, ob_malloc.cpp:147-151), and there ob_malloc/ObMallocAllocator/the malloc hook call je_malloc directly with no limit check (ob_malloc.h:118-125, ob_malloc_allocator.cpp:67-70, malloc_hook.cpp:163-164).
