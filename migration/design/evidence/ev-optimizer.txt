## AREA: sql-optimizer
**What it is:** This is the middle of the SQL compiler. src/sql/rewrite applies 34 query transformations to the resolver's statement objects (ObDMLStmt, ObRawExpr) and also holds the code that extracts query ranges. src/sql/optimizer enumerates join orders and access paths, costs them with a selectivity and cost model, and builds a tree of ObLogicalOperator nodes that the code generator turns into a physical plan; it also contains the DBMS_STATS statistics subsystem (src/sql/optimizer/stat).

**Size split:** Hand-written: 100% of the counted lines. Generated: 0. Vendored: 0. Data: 1 file.
- src/sql/optimizer: 205 .h/.cpp files (105 .h, 100 .cpp), 155,780 lines. Split by subsystem:
  - stat/ (DBMS_STATS, stat caches, gather tasks): 64 files, 26,638 lines
  - plan classes *_log_plan.*: 14 files, 28,678 lines
  - operator files ob_log_* plus the two factories: 69 files, 22,938 lines
  - ob_logical_operator.*: 2 files, 7,742 lines
  - join order and conflict detector: 4 files, 22,448 lines
  - cost, selectivity and dynamic sampling: 19 files, 21,736 lines
  - table location, route and physical location: 4 files, 6,711 lines
  - driver, context, util and misc: 29 files, 18,889 lines
  Plus the data table ob_join_property.map (363 lines, a hand-written C bool array included by ob_conflict_detector.cpp:26), BUILD.bazel and README.
- src/sql/rewrite: 95 .h/.cpp files (48 .h, 47 .cpp), 97,268 lines:
  - ob_transform_* (rules, rule base, transformer driver, utils): 74 files, 79,986 lines
  - query range (ob_query_range_*, ob_range_*, ob_expr_range_converter, ob_key_part): 11 files, 12,364 lines
  - other helpers (stmt comparer, predicate deduce, equal analysis, union find, expand aggregate): 10 files, 4,918 lines
  Plus README.

**Summary:** Almost everything here is hand-written C++: about 253K lines in 300 files, with no generated or vendored code. The algorithms are layered clearly: 34 rules applied in a fixed order, 17 named plan-tree passes, 30 direct ObLogicalOperator subclasses and 8 Path subclasses. The hierarchies are shallow (depth 3 at most) and use no multiple inheritance, so they map naturally onto Rust enums or traits.

What resists a one-to-one port is the data model, not the class shapes:
- Plans, paths and expressions are raw-pointer graphs placed by placement new into per-query arenas, and some destructors are only run by hand.
- Operators hold child_, parent_ and my_plan_ back-pointers, and candidate plans share child subtrees.
- ObRawExpr nodes are shared across statements, operators and the runtime (rt_expr_). They are identified by address in hash maps (34 reinterpret_cast<uint64_t> key sites) and replaced in place through ObRawExpr*& parameters (488) and ObRawExprPointer, which stores ObRawExpr** slot addresses.
- Statements and expressions point at each other (ObQueryRefRawExpr::ref_stmt_, ObExecParamRawExpr::outer_expr_, TableItem::ref_query_).

Rewrite and the optimizer depend on each other. Eight rule files call accept_transform (13 calls; the base rule's evaluate_cost is in a ninth file), and that path runs the full optimizer on deep copies of statements and then restores shared counters by hand. So the two directories, and the resolver's ObRawExpr and ObDMLStmt types they share, have to move together.

Deep recursion depends on SMART_CALL stack switching (617 call sites), which matters because worker stacks were cut to 256K.

The test surface is mysqltest only; no C++ unit tests exist for this area. CI runs 272 configured cases. 40 of them pin 658 EXPLAIN tables, and 568 of those tables in 33 files pin EST.ROWS and EST.TIME, computed as ceil() of doubles. The masking in the tests covers only table ids and plan signatures, never the cost columns. So a port must reproduce the cost arithmetic exactly (to the ceil boundary). It must also reproduce the tie order of std::sort at 34 unstable-sort sites and the iteration order of OB's own hash maps at 3 sites.

History already shows platform-dependent plan output and aliasing bugs. Commit 0dca2a5d3 fixed a NaN sort key that ordered filters differently on macOS. Commit 71e2b595b fixed a shared-subtree copy bug that caused error 4016. Only a redesign of expression ownership (immutable or copy-on-write expressions with IDs) would remove that second class of bug; a straight Rc<RefCell> translation would keep it.

**Structure call (surveyor):** Split verdict. The algorithm layer maps closely onto Rust:
- 34 rule classes applied in a fixed order (ob_transformer_impl.cpp:455-487)
- 17 named plan-tree passes (ob_optimizer.h TraverseOp)
- 30 operator subclasses that could become an enum or trait
- shallow, single-inheritance hierarchies, few templates (55 lines) and no macro framework beyond X-macros and OB_FAIL chains

These could be ported one file stem at a time while keeping names, pass order and cost formulas, and pass order and cost formulas have to stay the same anyway to keep the pinned EXPLAIN output. The data model does not translate:
- per-query arenas with placement new and destructors run by hand
- operators with parent_, my_plan_ and void* back-pointers, and candidate plans sharing child subtrees
- expressions shared across stmts, operators and the runtime, identified by address and rewritten in place through ObRawExpr*& and ObRawExpr** slots
- stmt and expression cycles
- rewrite running the optimizer on deep copies and then undoing global counters by hand

In idiomatic Rust this becomes typed-ID arenas (ExprId, StmtId, OpId, PathId) with explicit copy and replace operations. That is a redesign of ObRawExpr and ObDMLStmt, which live in src/sql/resolver and are read by the code generator, so it cannot be scoped to the optimizer alone. A literal port on raw pointers would compile only as wall-to-wall unsafe code and would bring nothing Rust offers.

Files that force the redesign: src/sql/resolver/expr/ob_raw_expr.h, src/sql/resolver/dml/ob_dml_stmt.h, src/sql/optimizer/ob_logical_operator.h, src/sql/optimizer/ob_join_order.h, src/sql/optimizer/ob_join_order.cpp, src/sql/rewrite/ob_transform_rule.cpp.

**Structure call check (verifier):** I agree with the split verdict. Porting the algorithms file by file is feasible: the rule list is really fixed in code (ob_transformer_impl.cpp:455-487, 33 APPLY_RULE_IF_NEEDED plus pre/post process), there really are 17 TraverseOp passes (ob_optimizer.h:38-90), and the area's own classes are single inheritance and at most 3 deep. The data model does force a redesign that crosses areas: ObRawExpr/ObDMLStmt in src/sql/resolver (ob_raw_expr.h:2226-2234, 2786, 2892, 3128; ob_dml_stmt.h:278), address-keyed copier and replacer in resolver/expr, and the code generator reading ObLog* nodes (ob_static_engine_cg.h, 95 ObLog*& parameters). Three things make the redesign bigger than the survey says. (1) Identity-by-address is not limited to 34 hash-map sites. ObOptimizerUtil::find_item (ob_optimizer_util.h:265-287) is documented as 'based on pointer comparison to determine if two expressions are the same'. It and the set helpers built on it (append_array_no_dup, remove_item, intersect, is_subset) appear at about 580 call lines in the area, and there is a whole pass, ADJUST_SHARED_EXPR, for shared expressions. Any ExprId design has to reproduce these equality semantics exactly, or plans change. (2) 'File by file, keeping names' and 'typed-ID arenas' conflict. With 488 ObRawExpr*& parameters and 18,618 OB_FAIL lines, the redesign changes the signature of nearly every function, so this is a rewrite of every file against a new model, not a translation. (3) Rewrite builds ObOptimizer at 5 sites in 3 files, not one, so the requirement to switch rewrite and optimizer over together is firmer than stated. A literal raw-pointer port would indeed be mostly unsafe code.

**Units of work:** The natural unit is a file stem (.h plus .cpp pair). There are 153 stems: 105 in src/sql/optimizer (73 outside stat/, 32 in stat/) and 48 in src/sql/rewrite. They fall into about 10 groups:
1. Logical operators: 33 ob_log_* operator stems plus the operator and plan factories, about 22.9K lines.
2. Plan classes: 7 *_log_plan stems, 28.7K lines.
3. ObLogicalOperator base: 1 stem, 7.7K lines.
4. Join order and conflict detector: 2 stems plus the .map file, 22.4K lines. ob_join_order.cpp alone is 17.7K lines and has to be split internally.
5. Cost, selectivity and dynamic sampling: about 10 stems, 21.7K lines.
6. Location, sharding and partition-wise join: about 5 stems, shared with the executor.
7. Driver, context and utils: about 15 stems, 18.9K lines.
8. stat/ DBMS_STATS subsystem: 32 stems, 26.6K lines. It is loosely coupled: inner SQL, KV cache and timer tasks.
9. Transform rules: 34 rule stems plus rule base, transformer driver and ob_transform_utils (14.2K lines), 80K lines in total.
10. Query range: 6 stems, 12.4K lines, shared with the executor and plan cache; plus 5 helper stems.

Ordering constraint: groups 1-7 and 9 cannot start until the ObRawExpr, ObDMLStmt and ObRawExprFactory data model in src/sql/resolver has been redesigned (46K lines in resolver/dml, 35K in resolver/expr, another area). Rewrite and the optimizer then have to switch over in the same step because of evaluate_cost. The stat/ group and parts of cost and selectivity can go earlier behind a narrow interface.

**Hard parts:**
- Shared, mutable expression graph with pointer identity. Hash maps are keyed on reinterpret_cast<uint64_t>(expr) at 34 lines, e.g. ObAllocExprContext in src/sql/optimizer/ob_logical_operator.cpp:255-313. ObRawExprPointer stores ObRawExpr** slot addresses (src/sql/resolver/expr/ob_raw_expr.h:5137-5150). There are 488 ObRawExpr*& in-out parameters, and ObRawExprCopier and ObRawExprReplacer run everywhere: 264 replace_expr calls and 85 ObRawExprCopier references in the area.
- Cycles between stmts and expressions, and expressions pointing into the runtime: ObQueryRefRawExpr::ref_stmt_, ObExecParamRawExpr::outer_expr_ and ObColumnRefRawExpr::dependant_expr_ (src/sql/resolver/expr/ob_raw_expr.h), TableItem::ref_query_ (src/sql/resolver/dml/ob_dml_stmt.h:278), and ObRawExpr::rt_expr_, which the code generator fills in.
- Operator graph with back-pointers. ObLogicalOperator has child_, parent_, my_plan_ and a void* traverse_ctx_ that is cast back to OpCtx* (ob_logical_operator.h:1674, 1742, 1863, 1871; ob_log_exchange.cpp:589). Candidate plans share child subtrees (ob_select_log_plan.cpp:830-855), and set_child overwrites parent_.
- Arena lifetimes with manual destruction. Placement new is used in ob_log_operator_factory.cpp and ob_log_plan_factory.cpp. ObLogPlan::destory is not the destructor (ob_log_plan.cpp:135). The ~ObRawExprFactory cleanup depends on the thread type (ob_raw_expr.h:5018-5025). JoinPath objects are recycled with placement new over reused memory (ob_join_order.cpp:5435-5446, 11037-11050, 11077), relying on a hand-written reuse() that resets every field (ob_join_order.cpp:8153).
- Rewrite and the optimizer call each other. evaluate_cost deep-copies stmts, runs ObOptimizer inside a temporary memory context, then restores query_ctx and transformer counters by hand (src/sql/rewrite/ob_transform_rule.cpp:346-420; ObEvalCostHelper and ObTryTransHelper in ob_transform_rule.h:237-290). There are 42 and 23 cross-includes between the two directories.
- Deep recursion over stmt, expression and plan trees relies on SMART_CALL stack switching: 617 sites, implemented in src/oblib/lib/utility/ob_smart_call.h:100-138 with jump_call onto a heap stack, under 256K worker stacks (commit a5b53834c). Rust needs stacker-style stack growth or explicit work stacks.
- Exact numeric reproduction for the pinned EXPLAIN. EST.ROWS and EST.TIME are ceil() of doubles (src/sql/optimizer/ob_logical_operator.cpp:1189-1192). Libm calls appear in ob_opt_est_cost_model.cpp, ob_join_order.cpp and ob_opt_selectivity.cpp (about 35 call lines). Summation order and possible clang FMA contraction on arm64 must be matched.
- Tie order of unstable sorts. There are 34 lib::ob_sort sites wrapping std::sort (src/oblib/lib/utility/ob_sort.h:28-41), e.g. ob_log_join.cpp:794 (sort by table name) and ob_join_order.cpp:4553 (sort by index_). Rust's sort_unstable uses a different algorithm, so every comparator needs a full tie-breaker, and that alone may change the pinned plans.
- Iteration order of OB's own hash containers leaks into output at src/sql/optimizer/ob_join_order.cpp:16662 and :16727 (full-text tokens) and src/sql/rewrite/ob_range_generator.cpp:1799 (GIS cell ids). A Rust HashMap would change that order.
- Structures shared with the executor. ObTableLocation (src/sql/optimizer/ob_table_location.cpp, 30 serialization macro uses) and the query-range graph (src/sql/rewrite/ob_query_range_define.*, ob_key_part.*) are stored in ObPhysicalPlan, ObPlanSet and ObTableScanOp, so their layout and serialization cross the optimizer boundary.
- Volume of the error-code style: 18,618 OB_FAIL( and 7,713 OB_ISNULL in the area. The change to Result and ? is mechanical but touches almost every line, and most OB_ISNULL checks exist only because every link is a nullable raw pointer.

**Pain instances:**
- Commit 0dca2a5d3 ("fix gis and sort problem in macos"). reorder_filters_exprs ranked security filters with -NAN, which breaks the strict weak ordering std::sort requires, so filter order differed between platforms. The fix swapped in -infinity and an original_pos tie-breaker (src/sql/optimizer/ob_logical_operator.h ObExprRankPair / ObExprRankPairCompare). In Rust f64 is not Ord, so NaN handling must be written out explicitly.
- Commit 71e2b595b (SEEK-545). The ObRawExprCopier cache left a CASE subtree shared between the index-lookup filter and other parents; later virtual-column expansion then pulled an unavailable column into the index filter, giving error 4016. This bug class comes from shared mutable expressions. A redesign with immutable or copy-on-write expressions would remove it; a literal Rc<RefCell> port would not.
- src/sql/optimizer/ob_logical_operator.cpp:394-408. set_child() returns void and throws away a failed child_.push_back, but still calls child_op->set_parent(this), leaving a half-linked tree after an allocation failure. With Rust's ? or an aborting Vec push this cannot go unnoticed.
- src/sql/optimizer/ob_log_operator_factory.h:119. The bound check is `idx <= sizeof(dist_algo_str) / sizeof(ObString)` on a 25-entry array, which is off by one. It is latent today: the highest DistAlgo bit is 1<<23, so idx is at most 24. Rust indexing would panic instead of reading past the array.
- src/sql/resolver/expr/ob_raw_expr.h:5018-5025. ~ObRawExprFactory calls destory() only when THIS_WORKER has no req flag, and the comment says this avoids ObSEArray leaks. Whether cleanup runs depends on the thread type, which Drop plus arenas would make unnecessary.
- src/sql/optimizer/ob_log_plan_factory.cpp:34-37. The destructor has '//destroy();' commented out, and ObLogPlanFactory::destroy calls ObLogPlan::destory() (ob_log_plan.cpp:135-146) instead of ~ObLogPlan. So the ObLogOperatorFactory member destructor, the one that runs the operator destructors, is not reached on that path. Whether this leaks depends on memory-context reclamation; see open questions.
- src/sql/rewrite/ob_transform_rule.cpp:377 and src/sql/rewrite/ob_transform_late_materialization.cpp:436. Both carry the comment 'jinmao TODO: defensive code, remove it later' on a formalize_stmt re-run.
- src/sql/optimizer/ob_join_order.cpp:8153 JoinPath::reuse(). Recycled join paths are reset field by field by hand before placement new; any field added later and left out of this list carries state across recycled paths.

**Open questions:**
- Do the 568 pinned EST.ROWS and EST.TIME tables pass unchanged on both x86-64 Linux and arm64 macOS builds today, given clang's floating-point contraction? This needs running mysqltest on both platforms.
- For the small test tables, where do the EST.ROWS values come from: storage-layer row estimation (ob_storage_estimator.cpp calls storage estimate_row_count), default statistics, or dynamic sampling (inner SQL)? The answer decides how strongly the optimizer port's pinned output depends on the storage port.
- Are ~ObLogPlan and the ObLogicalOperator destructors ever reached on the normal path, or is ObSEArray heap memory (ModulePageAllocator falls back to ob_malloc) reclaimed by an enclosing memory context? This needs a runtime memory trace.
- Is each shared child subtree's parent_ pointer fixed up after the final candidate plan is chosen and before code generation, or do later passes rely on get_parent(root, ...) searches? Tracing the plan finalisation passes in ob_log_plan.cpp would settle it.
- How much of the optimizer and rewrite code do the 272 CI cases actually reach? No coverage data exists in the tree, so it is unknown how many of the 34 rules and 30 operator types have pinned plan coverage.
- Is tools/obtest (886 more pinned plan tables in 'EST. ROWS|COST' and basic formats) still run anywhere, or is it dead OceanBase history?
- Could a differential oracle work: running the C++ and Rust optimizers on the same resolved stmt and comparing plan-item info or the EXPLAIN text? That needs a shared, serialisable stmt and expression representation, which does not exist today.

**Missed by the survey (verifier):**
- Expression identity is pointer equality almost everywhere, not only in the 34 address-keyed hash maps. Array membership, dedup, intersection and subset checks all compare raw pointers. So an ID or copy-on-write redesign must preserve exactly which nodes are 'the same object', or plan shapes and the pinned EXPLAIN text will change. (evidence: src/sql/optimizer/ob_optimizer_util.h:265-287 (find_item compares items.at(i) == item; its doc says 'Based on pointer comparison to determine if two expressions are the same'); git grep counts 243 find_item( call lines and 339 lines of append_array_no_dup/remove_item/intersect/is_subset in optimizer plus rewrite; the ADJUST_SHARED_EXPR plan pass in ob_optimizer.h's TraverseOp enum; address-keyed maps in src/sql/resolver/expr/ob_raw_expr_copier.cpp:112-234 and ob_raw_expr_replacer.cpp:335-338.)
- Part of the optimizer already lives outside the surveyed directories, in the src/query/api layer. sql/optimizer headers are now forwarders to it. This moves the size count and also offers a boundary a Rust port could reuse (or has to respect). (evidence: src/query/api/query/optimizer holds 10 headers and 3,195 lines: ob_optimizer_algo_defs.h (the DistAlgo enum used throughout join order and the operator factory), ob_optimizer_location_defs.h, stat/ob_stat_define.h (1,090 lines), ob_opt_column_stat.h, ob_opt_table_stat.h and others. 7 headers under src/sql/optimizer are 18-19-line '#pragma once / #include "query/optimizer/..."' forwarders. src/query/api/query/resolver/ob_raw_expr_traits.h is a similar layer for expressions.)
- The transformer is a fixed-point loop, not one pass in a fixed order. It repeats the 33-rule sequence up to max_iteration_count_ times and changes the enabled-rule set after rules fire, to avoid rules undoing each other. A port has to reproduce the iteration count, the convergence test and the disable logic exactly, because the final stmt shape decides the pinned plan. (evidence: src/sql/rewrite/ob_transformer_impl.cpp:213, 320-362 (loop over iteration_count, and 'transformer ends without convergence' at 362); 447-450 (the comment says cur_enable_types may be updated after each rule to avoid rewrite ping-pong between PREDICATE_MOVE_AROUND and CONST_PROPAGATE / SIMPLIFY_EXPR); commit dcf7be667 'Fix the non-convergence issue in the transformation' added 115 lines to ob_transformer_impl.*.)
- The expression classes that the optimizer downcasts into are neither shallow nor single-inheritance. This weakens the 'maps naturally onto Rust enums' framing for the part of the model that matters most. (evidence: src/sql/resolver/expr/ob_raw_expr.h:4675 'class ObWinFunRawExpr : public ObRawExpr, public ObWindow' (multiple inheritance); depth 5 through ObRawExpr > ObNonTerminalRawExpr (3270) > ObOpRawExpr (3298) > ObSysFunRawExpr (3868) > ObUDFRawExpr / ObCollectionConstructRawExpr (4087, 3934); the optimizer and rewrite hold 493 static_casts to Ob*RawExpr subclasses (C4).)
- The pinned numbers are checked on only one platform, but the C++ build targets five toolchain and libm combinations. Differences in libm results, not only FMA, can move a value across a ceil() boundary. There is also evidence that macOS already diverges. (evidence: cmake/Env.cmake:143-144 (clang++-17 on Linux), 159 (Android NDK clang), 188 (Apple clang), 206-207 (clang-cl on Windows); .github/workflows/seekdb.yml runs mysqltest only on arc-runner-k8s-ci-org (Linux); commit 0dca2a5d3 changed geometry plan tests for macOS; about 27 lines of log/exp/pow/sqrt calls in the area plus 22 ceil( in the optimizer; EST.ROWS also comes from storage estimation (src/sql/optimizer/ob_storage_estimator.cpp:87-148), and several mysql_test includes force major or minor freezes (include/majorfreeze.inc, minor_merge_tenant.inc), which change what storage reports.)

**Verifier's trust note:** The survey can mostly be trusted. Every size count and nearly every code citation I opened reproduced exactly: the file and line totals, the group splits, the inheritance table, the 488 ObRawExpr*& parameters, SMART_CALL 617, ob_sort 34, the ceil() in get_plan_item_info, the placement-new factories and ObLogPlan::destory, the shared child subtrees in hash group-by, and the 820/658/568 EXPLAIN table counts. The errors are in secondary counts and in scope. The accept_transform count is wrong (10 calls in 6 files, not 13 in 8), and the survey missed the 4 other ObOptimizer sites in late materialization and temp table. 4 of the 34 'address-keyed' lines are really pointer values. ob_transform_utils.h is included by 18 files, not 20. Masking is in 12 of the 40 CI plan tests, not 18. The churn counts include the bulk-import commit. The hash-iteration list misses ob_key_part.cpp:289/305. The open questions quote 886 obtest tables where the survey's own claim gives 498. The '264 replace_expr calls' in hard_parts is really 264 lines mentioning replace_expr* names, which include declarations. None of these errors changes the conclusion. The bigger omissions push the same way the survey already points. Pointer-equality identity through find_item and the set helpers is much more widespread than the 34 map sites. The transformer is a fixed-point loop. The expression hierarchy has multiple inheritance and is 5 deep. And 3.2K lines of optimizer types already sit in src/query/api. So the survey's main verdict stands: the algorithms port cleanly, but the expression and stmt data model needs a redesign that crosses areas, and exact EXPLAIN output makes the cost arithmetic and tie orders part of the specification. I would treat its figures as accurate within a few percent and its list of hard parts as incomplete rather than wrong.
