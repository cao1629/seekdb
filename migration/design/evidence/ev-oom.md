## AREA: gap-oom-policy-conflict
**What it is:** This area is the allocation-failure policy of seekdb: which allocators can hand a NULL (or a memory-limit error) back to a caller in the default jemalloc build, and which of the roughly 4,700 `ret = OB_ALLOCATE_MEMORY_FAILED` sites guard a failure that can actually happen. It covers the ob_malloc/jemalloc glue and malloc hook, the obmalloc context allocators, the module budgets (ObBlockAllocMgr and the FIFO allocators), the SQL work-area manager, the TxShare throttle, the KV cache store, and the existing Rust crate rust/sql-nio.

**Size split:** Hand-written C++ directly in scope: 129 files / 34,491 lines (src/oblib/lib/alloc 33 files / 8,436; src/oblib/lib/allocator 36 / 8,320; src/oblib/lib/resource 5 / 1,635; src/oblib/lib/rc 4 / 1,005; src/storage/throttle 9 / 1,811; src/storage/allocator 14 / 2,098; src/share/cache 22 / 8,356; SQL mem mgr + processor 4 / 2,685; sql/executor/ob_memory_tracker.* 2 / 145). Of these, 26 files / 8,490 lines are obmalloc-only (block_set, object_set, object_mgr, abit_set, ob_ctx_allocator, ob_context_allocator, memory_dump, alloc_struct, alloc_failed_reason, achunk_mgr, ob_resource_mgr, ob_allocator_v2, ob_page_manager), plus the malloc hook (malloc_hook.cpp + malloc_hook_extended.cpp, 674 lines). Generated: the error-code tables that define -4013/-4030/-4080/-11049/-7603 (src/share/ob_errno.cpp, src/share/ob_errno.h, src/oblib/lib/ob_errno.h, 18,824 lines total, 'DO NOT EDIT ... generated from ob_errno.def'; ob_errno.def is 1,914 lines). Data: none. Vendored: jemalloc is not in the tree; it is built from the Cargo crate seekdb-jemalloc-sys =0.2.2 (deps/external/Cargo.toml:10, deps/external/cmake/Jemalloc.cmake). deps/oblib holds 3 files / 308 lines (an out-of-date copy of ob_jemalloc.h plus 2 allocator unit tests). Existing Rust: rust/sql-nio 24 .rs files / 8,464 lines. Commands: `git ls-files -- <dirs> | grep -E '\.(h|hpp|cpp|cc|c|ipp|inc)$' | xargs cat | wc -l` per directory, and `git ls-files <obmalloc file list> | xargs wc -l`.

**Summary:** In the default build (bundled jemalloc on Linux and macOS without ASAN), ob_malloc, ob_realloc and ObMallocAllocator call je_malloc/je_realloc directly and ignore ObMemAttr. The per-context limits, the label accounting and the global limit, all of which live in the obmalloc ObMemoryMgr/ObCtxAllocator path, are never checked. The setters for the global limit have zero callers, so the only failure left under the general allocator is jemalloc itself returning NULL. The memory_limit parameter is documented as deprecated and ignored, memory_budget only sizes things, and no system_memory parameter exists. The real fail points are a short list of module budgets. The clog slice allocators (30% of budget) return -4013 at 5 log_engine.cpp sites. The replay budget (min 5%, 512MB) is turned into OB_EAGAIN back-pressure. The IO allocator budget ends in -4013 for request/result objects and in a retry-until-timeout for IO buffers. The KV cache store has a fixed budget that runs its own synchronous wash and then fails with -4013, and that error can reach a read through put_cache_block. The vector module limit returns NULL/-7603. Four more budgets use their own error codes: the query memory tracker (-11049), the memstore-full check on DML (-4030), the temp-file write buffer pool (OB_ALLOCATE_TMP_FILE_PAGE_FAILED), and SQL work areas, which spill to disk instead of failing. The TxShare throttle for tx-data and MDS only sleeps, and their ObBlockAllocMgr stays at INT64_MAX. About 14 FIFO allocators carry large fixed caps (128MB to 10GB) that are practically unreachable. By my scripted classification, roughly 40 of the 4,737 `ret = OB_ALLOCATE_MEMORY_FAILED` sites (under 1%) sit behind one of these budgets; the rest check a NULL from arenas or ob_malloc that only comes from jemalloc. No mysqltest .result/.test, init SQL or bindings test expects 4013/HY001 (or -4030/-11049/-4080/-7603) or sets a limit low enough to trigger one. Allocation-failure injection (errsim EN_4) exists only on the obmalloc path, and no script selects that backend, so the 4013 handling code is effectively untested. On Linux the malloc hook sends every libc allocation, and so every Rust allocation, to jemalloc; on macOS the jemalloc zone is promoted to the default zone. rust/sql-nio already works the way I recommend: no global_allocator, panic=abort, handle_alloc_error, and try_reserve only where a client or peer controls the size. Recommendation: abort on OOM, plus explicit typed budget checks at 8 named budget owners (clog, replay, IO allocator, KV cache store, vector module, query memory tracker, memstore-full check, temp-file write buffer pool), plus the existing spill protocol for SQL work areas and the sleep-only throttle. Fallible collections everywhere would carry over about 4,700 checks for a failure that does not occur in the default build.

**Structure call (surveyor):** This area does not call for a 1:1 translation. A 1:1 translation would turn about 4,700 `ret = OB_ALLOCATE_MEMORY_FAILED` checks and about 6,470 `OB_FAIL(push_back)` checks into fallible collections. In the default build nearly all of them guard a jemalloc NULL that does not come back, and allocation-failure injection cannot test them. The error model should be redesigned. General allocation aborts on failure (Rust's default, already used by sql-nio with panic=abort and handle_alloc_error). The code that can really run out gets explicit typed budget checks: clog, replay, the IO allocator, the KV cache store reservation, the vector module, the query memory tracker, the memstore-full check, and the temp-file write buffer pool. SQL work areas keep their spill protocol, and the throttle stays sleep-only. try_reserve is kept only where a client, peer or data controls the size, as sql-nio does today. Push-style calls that can fail for non-memory reasons (ObFixedArray capacity, deep-copy assign) stay Result-returning, but as capacity or copy errors, not OOM. The obmalloc backend (26 files, 8,490 lines) and the obmalloc branch of the malloc hook should not be translated. The large fixed FIFO caps (128MB to 10GB) become plain allocations, or bounded queues where the cap is really a queue bound. Files that force the call: src/oblib/lib/allocator/ob_malloc.h, src/oblib/lib/alloc/ob_malloc_allocator.cpp, src/oblib/lib/alloc/malloc_hook.cpp, src/oblib/lib/resource/ob_resource_mgr.cpp, src/oblib/lib/allocator/ob_block_alloc_mgr.h, src/logservice/ob_log_allocator.cpp, src/share/io/ob_io_struct.cpp, src/share/cache/ob_kvcache_store.cpp, src/storage/allocator/ob_vector_allocator.cpp, src/sql/executor/ob_memory_tracker.cpp.

**Structure call check (verifier):** I agree with the direction: abort on OOM for general allocation, explicit typed budget checks at the few real budget owners, and no 1:1 carry-over of ~4,700 NULL checks and ~6,470 push_back checks. The code supports it. On the default Linux/macOS build every general path ends in je_malloc (ob_malloc.h:118-125, ob_malloc_allocator.cpp:62-70, malloc_hook.cpp:161-165). Uncaught std::bad_alloc from operator new already terminates the process (malloc_hook_extended.cpp:215-231, only 5 catch sites). sql-nio already aborts on OOM. Even the obmalloc path has no enforced limit, because limit_bytes_ is written while hard_limit_bytes_ is what update_ctx_hold checks (ob_resource_mgr.cpp:157-165 vs 229-240). Four corrections are needed before this goes into the rulebook. (a) The IO allocator entry is backwards. Request and result objects retry until the IO timeout, and data buffers fail with -4013, because try_alloc_buf_until_timeout has no callers (ob_io_define.cpp:866, 1129, 1189; ob_io_manager.cpp:722-770). (b) The named list misses -4013 sources that are not allocator NULLs, which a 'delete the NULL check' rule would not cover and which must stay as typed errors: hash-partition depth in hash join (ob_hash_join_op.cpp:837-842, ob_hash_partitioning_infrastructure_op.h:1699-1700), KV cache mb-handle pool exhaustion (ob_kvcache_store.cpp:1029-1030), the IVF cache vector limit (ob_vector_index_ivf_cache_mgr.cpp:163-164) and vsag NO_ENOUGH_MEMORY (ob_vsag_adaptor.cpp:61-62). (c) The micro block cache's 4GB FIFO is a real budget with a 3-try sleep loop. It reaches reads through generic allocator references (ob_micro_block_cache.cpp:396-402, 1115-1118). (d) The recommendation only holds for builds with bundled jemalloc. Windows x64 and Android arm64 (build.sh:46-47), and Bazel non-sanity builds, default to obmalloc with no malloc hook. On Windows there is no overcommit, so abort-on-OOM turns a recoverable query error into a process abort. That needs an explicit decision, or a platform policy.

**Units of work:** 1) The allocator glue: ob_malloc.h/.cpp, ob_jemalloc.h and the malloc hook, 2 hook files plus 3 glue files. This becomes one small unit that keeps a single jemalloc shared by C++ and Rust; no port of the obmalloc branch. 2) The obmalloc backend, 26 files / 8,490 lines: leave it out (keep the C++ while it exists, then delete). 3) General-purpose allocator primitives in src/oblib/lib/allocator (36 files): arenas, slice/vslice/FIFO allocators and the qsync/hazard helpers. **Hard parts:**
- The ObIAllocator trait object is the receiver at about 2,500 OOM sites (receiver names 'allocator'/'allocator_'/'alloc'/'get_allocator()'). Arenas that hand out memory tied to a query or statement lifetime (src/oblib/lib/allocator/page_arena.h, src/oblib/lib/rc/context.h) need a Rust arena design (lifetimes, or bump arenas with explicit reset) because allocator_api is unstable.
- Lock-free slice and FIFO allocators built on hazard pointers and quiescent-state reclamation: src/oblib/lib/allocator/ob_slice_alloc.h (541 lines), ob_vslice_alloc.h (294), ob_qsync.h, ob_hazard_ref.h, ob_retire_station.h. This is unsafe-heavy code, intrusive block headers included.
- The memstore arena with reference-counted pages retired by quiescent state: src/storage/allocator/ob_fifo_arena.cpp (ObFifoArena::alloc/free, WaitQuiescent).
- The KV cache store: a fixed budget reserved with CAS, a synchronous wash under wash_out_lock_, hazptr-protected handle scans and a qclock retire station (src/share/cache/ob_kvcache_store.cpp:849-1000).
- One allocator shared across the language boundary. C++ and Rust must keep freeing each other's pointers through the same jemalloc. On Linux that works today only because src/oblib/lib/alloc/malloc_hook.cpp and malloc_hook_extended.cpp interpose libc symbols; on macOS it depends on zone promotion in src/observer/main.cpp:645-653. A Rust #[global_allocator] with a different jemalloc prefix would break cross-frees during a mixed period.
- Per-context memory accounting (ObMemAttr ctx_id and label; TrackedAllocator headers in src/oblib/lib/allocator/ob_malloc.h:222-359; MemoryUsageTracker resolvers in ob_malloc.cpp:195-211). Rust's GlobalAlloc receives no attributes, so accounting has to come from explicit allocator handles or a thread-local context.
- Variadic-template throttle framework with macro-generated units: src/storage/throttle/ob_share_resource_throttle_tool.ipp and ob_throttle_unit.ipp (ACQUIRE_THROTTLE_UNIT, DEFINE_CUSTOM_FUNC_FOR_THROTTLE).
- The vsag third-party C++ library allocates through ObVsagMemContext (src/storage/allocator/ob_vector_allocator.cpp). The vector budget check must stay reachable from C++ through FFI, and a NULL returned to vsag is handled inside vsag.

**Pain instances:**
- Retry loops on -4013 that spin waiting for memory that the default build never withholds: src/share/cache/ob_kvcache_store.cpp:405-407 and 642-644 (do/while around hazptr protect until the result is not OB_ALLOCATE_MEMORY_FAILED); src/storage/meta_mem/ob_storage_meta_mem_mgr.cpp:374-409 (retries up to 1000 times with 100ms sleeps); the same code duplicated in src/storage/meta_mem/ob_tablet_meta_mem_mgr.cpp:371-404; src/storage/throttle/ob_throttle_unit.ipp:236-248 (sleep 10ms and retry).
- The obmalloc malloc hook's ob_malloc_retry loops forever until allocation succeeds (src/oblib/lib/alloc/malloc_hook.cpp:75-86), so every NULL check behind libc malloc is dead code on that path too.
- Configuration knobs that do nothing in the default build: _storage_meta_memory_limit_percentage becomes set_ctx_limit (src/storage/meta_mem/ob_meta_memory_limit.h:28-35), and _ctx_memory_limit is applied by a duty task (src/observer/ob_server_duty_task.cpp:60-80). Neither limit is read on the jemalloc path. memory_limit is documented as ignored (ob_parameter_seed.ipp:81-84) but is still set and tested by the seekdb-bindings tests.
- Dead limit plumbing: ObMallocAllocator::set_allocator_limit and set_allocator_hard_limit have zero callers (ob_malloc_allocator.cpp:172-196). The ObFixedSizeBlockAllocator template, with its -4080 path, has no users outside its header (src/oblib/lib/allocator/ob_fixed_size_block_allocator.h:293-301).
- ObRADatumStore::need_dump reads the ctx allocator's limit and hold (src/sql/engine/basic/ob_ra_datum_store.cpp:1233-1256). Under jemalloc the hold is never updated (update_hold is reached only from ObMemoryMgr::alloc_chunk/free_chunk, ob_resource_mgr.cpp:55-105), so its 80% trigger never fires.
- Zero-size requests are reported as OOM: ob_malloc on the jemalloc path returns NULL and logs OB_ALLOCATE_MEMORY_FAILED for nbyte <= 0 (src/oblib/lib/allocator/ob_malloc.h:118-125).
- The 4013 handling paths cannot be exercised in the default build, because errsim EN_4 injection exists only in obmalloc (src/oblib/lib/alloc/ob_ctx_allocator.h:427, ob_context_allocator.h:454) and no tracked script sets MALLOC_BACKEND.
- An out-of-date duplicate header: deps/oblib/src/lib/allocator/ob_jemalloc.h lacks the ENABLE_SANITY branches present in src/oblib/lib/allocator/ob_jemalloc.h (diff of the two files).

**Open questions:**
- Whether any production deployment runs with vm.overcommit_memory=2 or a single request large enough to make je_malloc return NULL. That is the only case where abort-on-OOM would turn a query error into a process abort; it cannot be settled read-only.
- Whether anyone runs MALLOC_BACKEND=obmalloc in production. If obmalloc must be kept, the ctx limits (META_OBJ_CTX_ID, _ctx_memory_limit) become real fail points again and join the list of named budgets.
- Which allocator is behind the 6 allocator_-> sites in src/storage/blocksstable/ob_micro_block_cache.cpp (around lines 399-402, 500-503, 681-683, 697-699): the 4GB cache FIFO or a per-query unbounded ObFIFOAllocator.
- Whether a -4013 from the KV cache reservation reaching a read through put_cache_block (ob_micro_block_cache.cpp:442-446) happens in practice, and whether the Rust design should fall back to an uncached copy instead of failing the read.
- On macOS, whether allocations made before inner_main promotes the jemalloc zone (static constructors, early Rust code) end up freed through a different zone, and whether je_zone_register alone already makes jemalloc the default zone.
- How vsag behaves when ObVsagMemContext::Allocate returns NULL after the vector limit is hit (a third-party library, not in this tree).
- Whether ObStorageMetaMemMgr and ObTabletMetaMemMgr are both live; the files are near-duplicates, each with its own 4GB meta_cache_io allocator.
- Whether the memory virtual tables (__all_virtual_memory_info, ctx memory info) must stay meaningful. Under jemalloc the ctx hold is never updated, so a Rust port must decide whether to rebuild per-ctx accounting (MemoryUsageTracker) or drop it.
