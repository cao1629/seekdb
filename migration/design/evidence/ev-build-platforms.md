## AREA: build-platforms
**What it is:** The CMake and Bazel build graph, the code generators that run at configure/build time or whose outputs are checked in, the per-platform dependency sets and platform-specific C++ (Linux el7/8/9/al8 x86_64+aarch64, macOS arm64, Windows x64, Android arm64, and WebAssembly on a side branch), the Rust integration (rust/sql-nio, deps/external jemalloc crate), and the CI that verifies the result. Production builds use CMake in Unity mode, but CMake reads its source lists and Unity groups from Bazel .bzl inventories; GitHub CI builds only Linux and runs mysqltest against the binary.

**Size split:** Tracked .h/.hpp/.cpp/.cc/.c/.ipp/.y/.l: 2,777,368 lines (2,774,622 under src/, 2,746 elsewhere: bazel/probes, deps/oblib, include/, tools/ob_error, tools/codestyle). Commands: `git ls-files -z -- '*.h' '*.hpp' '*.cpp' '*.cc' '*.c' '*.ipp' '*.y' '*.l' | xargs -0 cat | wc -l`, the same with 'src/*' and ':!src'.

**Summary:** Production seekdb is built by CMake in Unity mode (RelWithDebInfo only, via build.sh and build.ps1). Its source lists and the exact Unity groups come from Bazel .bzl inventories (37,668 lines of Bazel). Bazel itself is not run by any GitHub workflow. The build compiles 216 Unity groups covering 2,789 files plus about 135 standalone files, which is 364 compile commands instead of about 2,936 separate .c/.cpp files. It links one 193 MB binary (91.5 MB of machine code) from a 523 MB static archive.

The most important finding for the migration: the C++ module layering holds only at the #include level (5 include lines break bazel/architecture/module_policy.bzl). At link level it does not hold. nm over the built objects shows 12 cross-module edges against the policy, carrying 743 symbols (sql to storage 271, sql to pl 156, storage to sql 100, storage to observer 33). src/data_plane and src/query work as header-only modules whose functions are defined in storage, sql and observer: 264 of 265 data_plane symbols and all 145 query symbols are defined outside their own directories. The executable link holds this together with --start-group/--end-group on Linux and /FORCE:MULTIPLE on Windows. Cargo crates cannot form cycles, so the module graph must be redesigned (traits or registration at startup) rather than copied one module to one crate.

About 87k lines of generated C++ are checked in, and about 279k more (bison/flex parsers and inner-table schemas) are generated at configure time, some of them into the source tree. Every generator needs a Rust back end, or its output has to stay in C behind an FFI. The largest is an 18,723-line bison 2.4.1 SQL grammar with C actions. About 329k lines are data tables, 276k of them the IK dictionary, which in Rust become data files.

Platform code is spread thin, not isolated. There are 577 _WIN32 lines in 248 files, about 6.3k lines under Windows conditionals, 152 __APPLE__ lines in 67 files, and 41 __ANDROID__ lines in 19 files. WebAssembly exists only on the feature/webassembly-shell branch, and it already needs nightly Rust with -Zbuild-std for sql-nio. Rust support tiers cover the matrix: Linux, macOS arm64 and Windows are Tier 1; Android and wasm32-unknown-emscripten are Tier 2 without host tools. Each platform also has its own set of 19 to 31 prebuilt C/C++ dependencies, including vsag, s2geometry, boost, ICU and grpc, which have no drop-in Rust versions.

Verification is cheap per run but narrow. GitHub CI compiles in 2 to 3 minutes with a warm ccache, or about 14 minutes when the cache restore was near-instant (probably a miss). It then runs 272 mysqltest cases in 4 slices of 6 to 10 minutes, all on Linux x86_64. macOS, Windows, Android and wasm have no CI. The Windows packaging path in build.ps1 has been dead since a merge on 2026-08-27. The C++ unit-test tree (330 files, 107k lines) was deleted on 2026-08-21, so the only remaining tests are public-surface SQL tests plus 3 Rust #[test]s.

The current Rust integration is one 8.4k-line crate built by a CMake custom command with lto=thin and codegen-units=1. Its unit tests are not run by any active workflow, and rust/Cargo.lock is gitignored even though CI passes --locked. The C++ side uses clang 17 while rustc 1.98.1 uses LLVM 22, so cross-language LTO and the custom Sanity LLVM pass cannot cover Rust code during a mixed period.

**Structure call (surveyor):** The build graph cannot be translated one-to-one. It forces a redesign. Unity groups are compile batches, not meaningful units. The CMake/Bazel module list looks like a clean DAG at the #include level, but the linked program depends on cycles and on functions declared in one module and defined in another. src/data_plane and src/query declare functions and classes whose bodies live in storage, sql and observer (264 of 265 data_plane symbols and all 145 query symbols); PL headers sit in src/sql/pl while their bodies are in src/pl; sql and storage call each other both ways. The final link holds all this together with --start-group on Linux and /FORCE:MULTIPLE on Windows. Cargo crates must form a DAG, so each of these links has to become a trait object or function registered at startup, or the modules have to merge into crates too large to compile in parallel.

The platform layer maps onto Rust fairly directly: #[cfg] instead of #ifdef, std/mio/socket2 instead of ob_platform_utils.h, and every target is Tier 1 or Tier 2. The cost there lies in the prebuilt C++ dependencies (vsag, s2geometry, boost, ICU, grpc), and in wasm needing nightly Rust. The code generators all need new Rust back ends, or their C output kept behind an FFI.

Files that force the call: src/data_plane/api/data_plane/report/ob_tablet_report.h + src/observer/ob_tablet_runtime_meta_updater.cpp, src/sql/pl/ob_pl.h + src/pl/ob_pl.cpp, src/observer/CMakeLists.txt (--start-group and /FORCE:MULTIPLE), bazel/architecture/module_policy.bzl, src/sql/parser/sql_parser_mysql_mode.y.

**Structure call check (verifier):** I agree the build graph cannot be copied one-to-one, and the main evidence holds up. **Hard parts:**
- Link-time cycles and functions declared in one module but defined in another. data_plane and query APIs are defined in storage, sql and observer (src/data_plane/api/data_plane/report/ob_tablet_report.h:66 is defined in src/observer/ob_tablet_runtime_meta_updater.cpp:760); PL headers are in src/sql/pl/*.h, bodies in src/pl/*.cpp; sql and storage call each other both ways (271 and 100 symbols). Rust crates cannot form cycles, so each link needs a trait or a registration point, or a merged crate.
- Crate sizing and compile parallelism. src/sql is 983,706 lines and src/sql/engine alone 351,853 lines in 1,379 files; src/storage is 760,249. They need a split much finer than the 12 module roots in bazel/architecture/module_policy.bzl, or type checking becomes a serial bottleneck.
- The SQL grammar: src/sql/parser/sql_parser_mysql_mode.y (18,723 lines) and .l (1,853) are pinned to bison 2.4.1 (src/sql/parser/gen_parser.sh:31-37), with C actions that build ParseNode trees (src/sql/parser/parse_node.h). Also src/pl/parser/pl_parser_mysql_mode.y (2,976) and the FTS grammar. Rust has no drop-in bison-compatible generator at this size, so the options are a rewrite or keeping the C parser behind an FFI.
- SIMD with per-target ISA flags and generated intrinsics: src/oblib/lib/codec/ob_generated_unalign_simd_bp_func.cpp (7,200 intrinsic lines, generated by generate_simd_bitpakcing.py); AVX-512 flags on ob_sql_simd and ob_storage_simd (src/sql/CMakeLists.txt:13-14, src/storage/CMakeLists.txt:21-22); the hand-made src/oblib/lib/codec/ob_sse_to_neon.h and src/storage/blocksstable/encoding/neon/. These become #[target_feature] functions with runtime dispatch, and the generators need Rust output.
- Prebuilt C++ dependencies with no drop-in Rust version: vsag, s2geometry, boost, abseil, ICU, grpc, plus OpenMP/openblas/diskann on Android (deps/init/*.deps; src/oblib/lib/CMakeLists.txt:55-70). Their template-heavy C++ APIs need handwritten C shims or cxx bridges on every platform.
- The allocator and memory-checking stack: ob_malloc + jemalloc from the Cargo crate seekdb-jemalloc-sys (deps/external), malloc_hook on Linux only (src/oblib/lib/CMakeLists.txt:24-40), and the Sanity build, which adds a custom LLVM pass through -fpass-plugin (src/oblib/CMakeLists.txt:177-185) plus 17 -Wl,--wrap libc wrappers (CMakeLists.txt:264-281). Rust code built with LLVM 22 is not instrumented by a clang 17 pass plugin.
- The mixed-language period: panic=abort is required at the FFI (rust/Cargo.toml profile.release and profile.cmake-debug); build.rs writes the cbindgen header rust/sql-nio/include/nio.h (534 lines) into the source tree; clang 17 and rustc's LLVM 22.1.8 differ, so FFI calls cannot be inlined across the language boundary through cross-language LTO.
- Configure-time and checked-in generators that emit C++: src/share/inner_table/generate_inner_table_schema.py (103k generated lines), src/share/inner_table/sys_package/syspack_codegen.py, src/share/gen_errno.pl, and src/share/system_variable/gen_ob_sys_variables.py, which also writes into src/sql/session/. Each needs a Rust emitter (build.rs or checked-in output) and a plan for the mixed period, when both languages consume the same definitions.
- The platform matrix with no CI beyond Linux: Windows (clang-cl, vcpkg, /FORCE:MULTIPLE, 57 files including windows.h, build.ps1 already rotting), Android NDK API 28 cross-builds (build.sh configure_cmake, cmake/Rust.cmake:55-100), and wasm, which requires nightly Rust with -Zbuild-std and +atomics (feature/webassembly-shell tools/wasm/rust-build-env.sh). Every Rust crate must build for all of them, and only Linux is checked automatically.

**Pain instances:**
- e66776e2d (2026-08-20): the Sanity memory-checking build found use-after-free in Plan Cache/PS Cache (an object accessed after its last node reference was released; a destroyed ps item dereferenced after the schema expired) and a wrong buffer length in skip-index output. Ownership and bounds checks in Rust remove this class of bug. The Sanity build mode itself (CMakeLists.txt:215-290, with a custom LLVM pass) exists to catch these.
- src/observer/CMakeLists.txt:71: /FORCE:MULTIPLE on the Windows link (added in 34e0af1af) accepts duplicate symbol definitions. That is an ODR hazard, and Rust's per-crate symbol mangling does not allow it.
- 22b7c24db ('Fix compilation in non-unity build (#932)') and e45b8ae5c ('fix compile in non-unity'): Unity batching hid missing includes and declarations, so the non-Unity build broke without anyone noticing. Rust modules compile only one way.
- cmake/Utils.cmake unity_after: the Unity build must #undef USING_LOG_PREFIX after every included .cpp because 2,324 .c/.cpp files define it, and the macro leaks between files batched into one Unity translation unit. Rust has no preprocessor-level leak of this kind.
- src/oblib/CMakeLists.txt:110-172: every C++ target is compiled with -fno-strict-aliasing and with -Wno-class-memaccess, -Wno-invalid-offsetof, -Wno-maybe-uninitialized and -Wno-reinterpret-base-class (52 warnings disabled on clang, 141 on the Windows clang-cl path). These are build-level defenses against memory patterns that are undefined behavior or depend on how compilers handle aliasing; safe Rust does not allow those patterns.
- e2b7c7a8f: duplicate template instantiations across translation units made one Unity translation unit take 455 s, fixed by hand with extern template and ALONE splits. Rust removes the header-driven duplication, but generic instantiation across crates has a similar cost, so Rust only partly removes this.
