### A1-1: ids for plan and execution objects, and `ObTempExpr`

- **Status:** applied 2026-09-25; revised after review 2026-09-27.
- **Files:** design/s4-sql-front.md 2.2 (the `ObExpr`, `ObTempExpr` and `ObTempExprCtx` rows; the paragraph "Plan and execution objects"); design/s5-execution.md 3 (rule 3.10, new in the revision; the `EvalFrame` comments); design/ARCHITECTURE.md §4.1 (the sentence listing what the id scheme covers); RULEBOOK.md 2.4 (the id row) and section 0 (the list of statements a translation may add now names "a copy of an expression added to the run's frame and removed at the end of its C++ scope"); migration/inventory/vocabulary/const-cast.md (the `IR_ID` test).
- **Before.** s4-sql-front.md 2.2's table listed parse nodes, raw expressions, statements, table items, optimizer objects, `ObRangeNode` and PL objects, and no plan or execution object. ARCHITECTURE §4.1 said the scheme covers "query-range nodes and the tables of a cached plan", a phrase defined nowhere.
- **After.**
  - The same test (compared by address, keyed by address, packed into an integer, or pointed to from more than one place) decides for plan and execution objects. A plan object that gets an id lives in an arena of the plan-owned object that holds it. A per-execution object that one object holds, and only that object reaches, lives in the holder's arena, whatever allocator the C++ uses; only one that no object holds gets its id in an arena of the exec context or of the frame, whichever owns the memory the C++ allocates it in.
  - `ObExpr` (the runtime expressions the code generator makes, in the table of a plan, an `ObPreCalcExprFrameInfo` or an `ObTempExpr`) → `ExprIdx`, the position in the expression table the frame reads; not an `Id<T>`, no arena.
  - An `ObExpr` the C++ builds outside every table at run time follows s5-execution.md rule 3.10. A copy of a plan expression on the stack or in an expression context (the values operators' `real_src_expr`, `ObExprColumnConvCtx::expr_`) is an owned `ObExpr` value that keeps its original's slot and whose `args_` are `ExprIdx` into the same table. The datum caster's two cast expressions, and a copy the caster stores a pointer to, are held by the run's `FrameState` in a list after the table, so an `ExprIdx` at or past the table's length names them; the caster adds its two where it builds them and removes them at `destroy`, a copy is added where the C++ builds it and removed at the end of its C++ scope, and a function that stores the pointer it receives (`ObDatumCaster::to_type`, `setup_cast_expr`) takes the `ExprIdx`. The caster evaluates through the run's `EvalFrame`, with the batch size and index its C++ context sets, under rule 3.8's guard.
  - `ObTempExpr` → `TempExprId`; the fields that point to one hold `Option<TempExprId>`; the arena is an `Arena<ObTempExpr>` in the holder: the `ObTableLocation`, the `ObPreRangeGraph` whose range map holds it, or LOAD DATA's `ObShuffleTaskHandle`. A temporary expression that no object holds, a local that lives for one function, goes into an arena of the exec context. A copy of the holder makes one new id per `ObTempExpr::deep_copy`, in the copy's arena.
  - `ObTempExprCtx` → `TempExprCtxId`, naming a `FrameState` (A1-5), in an arena the exec context owns; `temp_expr_ctx_map_` is `IdHashMap<TempExprId, Option<TempExprCtxId>>`.
  - ARCHITECTURE §4.1 lists these objects in place of "the tables of a cached plan"; the const-cast vocabulary's `IR_ID` value now says `ObExpr`'s `ExprIdx` is not an id, so `ObExpr` is not `IR_ID`.
- **Reason.**
  - The exec context keys its cache by a temporary expression's address and stores the context's address in the value (src/sql/engine/ob_exec_context.cpp:525-554, the casts at :535, :541-542, :546); the map is iterated only to run destructors at teardown (:373-382). That is RULEBOOK 2.4's test, so both get ids.
  - A temporary expression is reached through exactly one holder: `ValueItemExpr::expr_`, `PartProjector::se_virtual_column_exprs_` and `ObTableLocation`'s four `se_*_expr_` fields (src/sql/optimizer/ob_table_location.h:74, :419, :1144-1147), `ObRangeMap`'s `temp_expr_` (src/sql/rewrite/ob_query_range_define.h:238), and `ObShuffleTaskHandle::calc_tablet_id_expr` (src/sql/engine/cmd/ob_load_data_impl.h:482), which gets the expression `build_calc_partid_expr` makes (src/sql/engine/cmd/ob_load_data_impl.cpp:1817-1824) at :2004. Every copy of a holder makes a new object (`ObTableLocation::assign`, src/sql/optimizer/ob_table_location.cpp:674, :755-764; `ValueItemExpr::deep_copy`, :4163-4170; `ObPreRangeGraph::deep_copy_range_map`, src/sql/rewrite/ob_query_range_define.cpp:521, :551; `ObTempExpr::deep_copy`, src/sql/engine/expr/ob_expr_frame_info.cpp:619-632). The C++ allocates most of them on the exec context's allocator (ob_table_location.cpp:918, :961; src/sql/code_generator/ob_static_engine_expr_cg.cpp:1484-1510), which outlives the holder, but only the holder can reach them, so the holder's arena keeps each one exactly as long as it is reachable. The expressions no object holds are locals allocated at src/sql/engine/cmd/ob_kill_session_arg.cpp:89, src/sql/engine/cmd/ob_partition_executor_utils.cpp:508, :594 and src/sql/resolver/ob_resolver_utils.cpp:6714.
  - The code generator's runtime expressions are positions already: each `ObExprFrameInfo` holds them in `rt_exprs_` (src/sql/engine/expr/ob_expr_frame_info.h:128-134), and the C++'s own `expr_pos_` and `expr_idx_` are positions in it (:210, :231). s5-execution.md 3 writes `args_: Box<[ExprIdx]>` over `exprs: &'r [ObExpr]`.
  - Not every runtime `ObExpr` is in a table, as the first version claimed. The datum caster allocates two `ObExpr`s of its own and an `ObEvalCtx` whose frames are the run's frame pointers plus one frame of its own (src/sql/engine/expr/ob_datum_cast.cpp:12847, :12855, :12862-12864, :12869-12899), stores its source's address in `args_[0]` (:13070) and evaluates plan expressions through that context (:12928, :12933). LEAST and GREATEST (src/sql/engine/expr/ob_expr_least.cpp:196-199) and NULLIF (src/sql/engine/expr/ob_expr_nullif.cpp:254-257, :280-283) reach it through `ObEvalCtx::init_datum_caster` (src/sql/engine/expr/ob_expr.cpp:82-96); the two values operators own one each (src/sql/engine/basic/ob_expr_values_op.h:93; src/sql/engine/basic/ob_values_table_access_op.h:75) and pass it a stack copy of a plan expression with its metadata changed (src/sql/engine/basic/ob_expr_values_op.cpp:486-489; src/sql/engine/basic/ob_values_table_access_op.cpp:203-206). `ObExprColumnConvCtx` keeps a copy with rewritten arguments in an expression context (src/sql/engine/expr/ob_expr_column_conv.cpp:764-776). These paths run on the judge's path (LEAST/GREATEST, NULLIF, INSERT ... VALUES on a cached plan), so rule 3.10 decides them now rather than sending them to the UNKNOWN rule.
  - `build_temp_expr_ctx` places the context on the exec context's allocator (ob_exec_context.cpp:556-580, the allocation at :559).
- **Review (2026-09-27).** A.3 applied (rule 3.10). A.4 applied: (a) the holder rule now wins over the allocator rule in "Plan and execution objects"; (b) the const-cast vocabulary's `IR_ID` test was corrected directly; (c) the no-holder rows cite the allocation lines, and LOAD DATA's holder is named.

### A1-2: the block manager's per-block reference count

- **Status:** applied 2026-09-25; revised after review 2026-09-27.
- **Files:** design/s3-memory.md 3.4 (R1, the paragraph after it, the paragraph closing Example E4) and 3.9 check 10; design/ARCHITECTURE.md §3.1 rule 9; RULEBOOK.md 2.2 (the `inc_ref`/`dec_ref` row); migration/inventory/vocabulary/const-cast.md (`LOCK_OR_ATOMIC`'s translation (c)).
- **Before.** R1: "No hand-written count fields remain outside the named crates." E4: "Macro-block references stay a separate owner inside `ObTablet` whose `Drop` releases them." ARCHITECTURE §3.1 rule 9: "`inc_ref`/`dec_ref` becomes `Arc`".
- **After.**
  - A count of references to an on-disk object named by an id is data and stays a count: `BlockInfo::ref_cnt_` stays an `i64` in the block map under the bucket lock, with the C++ codes of `inc_ref` and `dec_ref`. No hand-written count that decides when memory is freed remains outside the named crates (R1; A1-11 (b) adds the other kind of count that stays).
  - The objects that take these references release them where the C++ releases them: an explicit release stays a call (`ObSSTable::reset()` on the failure paths of `init` and `copy_from_old_sstable`, `inc_macro_ref`'s rollback, `ObMacroBlocksWriteCtx::clear`, `ObStorageObjectHandle::reset_macro_id`), and a destructor that releases them becomes `Drop`.
  - E4: the tablet's macro-reference owner's `Drop` runs `ObTablet::dec_macro_ref_cnt`, which the C++ calls just before it destroys a tablet, with its `hold_ref_cnt_` check, its release order (sstable blocks before tablet-meta blocks) and its blocking read of the macro info. A temporary sstable's own `Drop` runs `~ObSSTable`'s `reset()` → `dec_macro_ref`, the blocking meta read and its retry loop included.
- **Reason.**
  - The count is garbage-collection state for disk blocks, not a memory lifetime. `inc_ref` and `dec_ref` change it under the bucket write lock, with `OB_ERR_UNEXPECTED` for a count at 0 while mark-and-sweep is on and `OB_ERR_SYS` for a decrement at 0 (src/storage/blocksstable/ob_block_manager.cpp:622-690). The marker reads it for every block and takes a block at 0 as a free candidate (`GetPendingFreeBlockFunctor`, :787-800; `is_free`, :523), so an entry stays in the map at 0 until the marker takes it. An `Arc` per block would free its handle at 0 and lose both the entry and the codes; a map of `Weak` scanned for dead handles is a second design of the same count.
  - A tablet does not release its references in `~ObTablet`: `dec_macro_ref_cnt` does, called by the handle's temporary branch before the destructor (src/storage/meta_mem/ob_tablet_handle.cpp:101) and by `ObTabletMetaMemMgr::release_tablet` (src/storage/meta_mem/ob_tablet_meta_mem_mgr.cpp:774). It does nothing when `hold_ref_cnt_` is false (src/storage/tablet/ob_tablet.cpp:2129-2132), releases sstable blocks before tablet-meta blocks, an order its comment says must not change (:2147), and may read the macro info from disk (`load_macro_info`, :2162). Dropping the tablet at those two points runs the same steps at the same time.
  - A temporary sstable releases its blocks in its destructor: `~ObSSTable` calls `reset()` (src/storage/blocksstable/ob_sstable.cpp:218-221, :276-293), which calls `dec_macro_ref` (:1127-1185); that re-reads the meta in a `do ... while (ignore_ret(ret))` loop over -4013, `OB_TIMEOUT` and `OB_DISK_HUNG` (:1122-1125, :1138-1141) before calling `dec_ref` for each block. RULEBOOK 2.3 makes such a destructor a `Drop`, section 0 keeps the loop, and there is no async runtime that would forbid blocking in `Drop`.
  - The explicit releases run in mid-life, not at destruction (ob_sstable.cpp:250, :267, :1266-1301; src/storage/blocksstable/ob_macro_block_struct.cpp:36-48; src/storage/blocksstable/ob_storage_object_handle.cpp:72-82), so moving them into `Drop` would change when a block becomes free.
- **Review (2026-09-27).** A.10 applied: E4 no longer says the tablet's `Drop` runs what `~ObSSTable` runs, and R1's paragraph no longer reads as moving explicit releases into `Drop`.
- **Pilot rows.** Settles both questions of row 19: the counter stays, and `Drop` may run the blocking read with its retry loop. Row 19 is re-classified `ON_DISK_COUNT`, confirmed.
- **Lists affected:** refcount (the block manager's definitions, refcount.tsv:672-673, and the sstable's calls, refcount.tsv:703-714; any other count of references to on-disk objects).

### A1-3: `ObRecursiveMutex`

- **Status:** applied 2026-09-25; revised after review 2026-09-27.
- **Files:** design/s8-numerics-platform.md 5 (the `sync` module's code block, rule 8, the reviewer checks); RULEBOOK.md 2.7 (the `ObRecursiveMutex` row); design/ARCHITECTURE.md §11 (the Locks bullet).
- **Before.** s8 rule 8: "`ObRecursiveMutex` (6 declarations) → `parking_lot::ReentrantMutex<T>` or a restructured site, per its row of lock-guards.tsv." RULEBOOK 2.7: "`ReentrantMutex<T>` or a restructured site, per its row".
- **After.**
  - `ObRecursiveMutex` (7 declarations) → the `sync` module's own `ObRecursiveMutex`: a `Mutex` over the holder's `ThreadId` and `lock_cnt_` plus a `Condvar`, holding no data, with the C++ API: `lock()`, `trylock()` (`Err(OB_EAGAIN)` while another thread holds it), `unlock()` from any thread, and `ObRecursiveMutexGuard`. Every C++ lock site stays where it is, re-entries included.
  - The fields the lock guards go into a `Mutex<T>` beside it; a field with locking of its own stays outside (`ObMajorMergeInfoManager::global_merge_mgr_`). Each access takes the inner mutex with a guard bound to a named local (rule 6). The guard is dropped before any call that can take the reentrant lock again and taken again after. It stays across a call that cannot reach the same `ObRecursiveMutex`, as the lock's lock-guards.tsv row shows: a method called on a guarded field without a lock of its own (`freeze_info_mgr_.reload(..)`), or a callee given guarded fields by reference, which gets them as `&mut` borrows through the guard (`store_query_string_`). A C++ access that skips the reentrant lock takes only the inner mutex, for that one access.
  - parking_lot's `ReentrantMutex` is not used, and no site is restructured. `ObGlobalFreeList::lock_` goes with its pool. The reviewer check exempts `ObRecursiveMutex` from "no lock guards data it does not own" and checks the inner guard instead.
- **Reason.**
  - `ReentrantMutex<T>` hands out only `&T`, so the data needs a `RefCell` or a lock inside, and its guard cannot express how the C++ uses these locks. The C++ takes the session's `query_mutex_` in one function and releases it in another, in other objects: `ObPxSqcHandler::init_env` locks it and `destroy_sqc` unlocks it (src/sql/engine/px/ob_px_sqc_handler.cpp:262, :318), and `ObInnerSQLConnection` takes it at :443 and releases it at :282 and :1408 (src/observer/ob_inner_sql_connection.cpp:311-331). A parking_lot guard can neither outlive its function's borrow nor move to another thread (`send_guard` is off). `try_lock_thread_data` returns with `thread_data_mutex_` held and `unlock_thread_data` releases it (src/sql/session/ob_basic_session_info.h:728, :730; called at src/sql/session/ob_sql_session_mgr.cpp:516, :546), which a guard could only do by changing both signatures.
  - The re-entry is real, so a plain `Mutex` would deadlock: `ObSnapshotGcScnRenewer::try_renew` → `need_renew_` (src/rootserver/freeze/ob_snapshot_gc_scn_renewer.cpp:112, :165); `ObMajorMergeInfoManager::set_freeze_info` → `try_reload` → `reload` (src/rootserver/freeze/ob_major_merge_info_manager.cpp:88, :59, :70); `ObSQLSessionInfo::kill_query` → `update_last_active_time` (src/sql/session/ob_sql_session_info.cpp:1291-1292; src/sql/session/ob_basic_session_info.h:649-653); the session sweep's `trylock`s (ob_sql_session_mgr.cpp:510, :516) → `kill_session`'s guards (:432-433).
  - Restructuring into `Mutex<T>` with the data passed down would split every re-entered function that is also called without the lock (`update_last_active_time`, `set_session_state`, `set_query_start_time`, `get_current_query_string`) into two, against RULEBOOK section 0's one Rust function per C++ function.
  - "One statement and never across a call", the first version's rule for the inner mutex, cannot be followed where the locked code calls a method on a guarded field: `ObMajorMergeInfoManager::lock_` guards `freeze_info_mgr_` (src/rootserver/freeze/ob_major_merge_info_manager.h:93-95), and every use of it under the lock is a call (ob_major_merge_info_manager.cpp:60, :76, :123, :127, :162, :220, :246, :254, :260, :300, :328), `reload` running inner SQL (src/share/ob_freeze_info_manager.cpp:122-128); `ObFreezeInfoManager` has no lock of its own (src/share/ob_freeze_info_manager.h:76-78). Nor where the session passes three guarded fields by reference to `store_query_string_`, which frees and regrows the buffer (src/sql/session/ob_basic_session_info.cpp:4209-4219, :4221-4250). Holding the inner guard across a call that cannot re-enter adds no deadlock: the inner mutex is always taken after the reentrant lock or alone, and the callee never takes the reentrant lock. `global_merge_mgr_` has its own `SpinRWLock`s (src/rootserver/freeze/ob_global_merge_manager.h:70, :132).
  - The latch lets any thread unlock (src/oblib/lib/lock/ob_latch.cpp:605-630), which the new `unlock()` keeps; `lock`, `unlock` and `trylock` follow src/oblib/lib/lock/ob_recursive_mutex.h:52-90.
  - The count is 7, not 6: `grep -rnE '^\s*(mutable\s+)?(common::)?ObRecursiveMutex\s+\w+' src --include='*.h'` (ob_global_factory.h:384; ob_major_freeze_service.h:113, :119; ob_major_merge_info_manager.h:95; ob_snapshot_gc_scn_renewer.h:98; ob_basic_session_info.h:1686, :1687). `ObTCFactory` and `ObGlobalFactory` are instantiated nowhere (`grep -rn 'ObTCFactory<\|ObGlobalFactory<' src` finds only src/oblib/lib/objectpool), so `ObGlobalFreeList` and its lock are dead with the pool (s3-memory.md R3).
  - The inner mutex adds no critical section the C++ lacks for the fields' own accesses: the writers that skip the reentrant lock (`reset_query_string`, src/sql/session/ob_basic_session_info.cpp:4288-4294; `destroy`, :254-258) lock only the one field access.
- **Review (2026-09-27).** A.5 applied: the inner guard's rule, the field with its own locking, fields passed by reference, rule 6's named local and the reviewer check.

Row 5 is re-classified `OWNED`, confirmed: `thread_data_mutex_: ObRecursiveMutex` and `thread_data_: Mutex<MultiThreadData>` beside it, the writers that skip the C++ lock taking only the inner mutex, and `store_query_string` holding the inner guard across `store_query_string_`. ### A1-4: hash-map ports: `get()`, callbacks and the copy-back

- **Status:** applied 2026-09-25; revised after review 2026-09-27.
- **Files:** design/s4-sql-front.md 2.1 rule 4 (the paragraph after the `IdHashMap` block: the `get` bullet, a new bullet on elements whose address escapes, the callbacks bullet, the copy-back bullet); RULEBOOK.md 2.5 (the `ObHashMap` row) and section 0 (the list of statements a translation may add names "a slot or a hash-map value copied out and written back"); migration/inventory/vocabulary/const-cast.md (notes under Q1 and Q8).
- **Before.** s4-sql-front.md 2.1 rule 4 gave the ports `get_refactored` with `V: Clone` (a copy out), `set_refactored`, `exist_refactored` and `erase_refactored`, and said nothing about the C++ `get()` that returns a pointer into the node, the callback methods, or a write through a pointer the C++ got from the container.
- **After.**
  - `get_refactored` copies the value out, as the C++ does.
  - `ObHashMap::get` is two methods in header order: `get(&self, key) -> Option<&V>` (the `const` overload) and `get_2(&mut self, key) -> Option<&mut V>`; a write through the pointer is a write through the `&mut V`, used before the next call on the map or its owner. `ObHashSet::get` is `get(&self, key) -> Option<&K>`: a stored key is never written in place.
  - An element whose address the C++ stores outside the statements up to a write-back (in an intrusive list, a member, another container, or a caller that keeps it) is held by the container as an `Arc` or an id, the other holders get clones of the `Arc` or the id, and it is never copied.

- **Status:** applied 2026-09-25; revised after review 2026-09-27.
- **Files:** design/s8-numerics-platform.md 4 rule 5; design/s3-memory.md 3.4 R1 and 3.9 check 10; design/ARCHITECTURE.md §3.1 rule 9; RULEBOOK.md 2.2 (the `inc_ref`/`dec_ref` row) and 2.7 (the row on reference counts, lock words and list links); design/s6-storage.md 2.5 (a note under the estimator example); migration/inventory/vocabulary/const-cast.md (`LOCK_OR_ATOMIC`'s translation (c)).
- **Why rules, not classifier guidance.** Each decides a whole class of rows (atomic-fields, refcount, lock-guards), and two classifiers could answer it differently without a rule, which is what RULEBOOK's meta-rule says belongs in the design.
- **(a) "Replace lock-free links with a lock; do not retype them as atomics."** Before: s8 4 rule 5, "Reference counts, lock words, list links and reclamation clocks are replaced, not retyped", did not say whether an atomic integer holding an id counts as retyped. After: an atomic integer holding an id, an index or a row number in place of a pointer the C++ reads and writes with `ATOMIC_*` is a retyped link when that pointer links a structure (a list's or version chain's head and `prev_`/`next_`, a hash bucket's row pointer or chain link, a tree's root and child links); the link moves inside the lock of its structure, and a reader the C++ lets skip that lock takes it for each step, marked `PERF(port)`, until a gate measurement asks for ob-epoch. A single published pointer that links no structure (a lazily created object, one replaced as a whole) follows s8 4 rule 8: an `ArcSwap`, or an arena id in an atomic. Reason: ids replace pointers (RULEBOOK 2.4), so without the sentence an `AtomicU64` over a `TransNodeId` passes for "replaced"; rows 10 and 13 took the lock form for the shared hash join's buckets (src/sql/engine/join/ob_hash_join_op.h:485-529) and `ObMvccRow::list_head_` (src/storage/memtable/mvcc/ob_mvcc_row.h:293); the tree root is `ObKeyBtree::root_` (src/storage/memtable/mvcc/ob_keybtree.h:321); the single published pointers are `ObLogAllocatorMgr::allocator_` (src/logservice/ob_log_allocator_mgr.h:54, set by `ATOMIC_BCAS` at ob_log_allocator_mgr.cpp:118) and `ObPersistentLobApator::meta_table_param_` (src/storage/lob/ob_lob_persistent_adaptor.h:142), for which the first version's sentence and rule 8 gave different answers. s6-storage.md 2.5's example reads `get_list_head()` without the latch, as the C++ does (ob_mvcc_row.h:380-382); a note there says the head is read under the row latch, in the form the core API sessions fix.
- **(b) "Try `Arc::get_mut` and `Arc::into_inner` before keeping a hand-written count."** Before: R1 and R2 named `Arc` clone and drop and `Arc::into_inner`, not `Arc::get_mut`. After: a release acting at 0 becomes `Arc::into_inner`; a test that the caller holds the only reference left becomes `Arc::get_mut` where no `Weak` of the type ever exists. Where a `Weak` can exist, or where the C++ tests the count inside the object, the C++ count stays beside the `Arc`: an `AtomicI64` changed where the C++ changes it, with its `SeqCst` operations, read by the test and deciding no free. R1's sentences and 3.9 check 10 now say the same: the counts that stay are those test counts and the on-disk counts of A1-2, and none decides when memory is freed. Reason: row 18 replaced `1 != get_replay_ref()` (src/logservice/replayservice/ob_replay_status.cpp:1187-1189) with `Arc::get_mut`, which synchronizes with the other clones' drops, so the other queues' work comes before the barrier's replay as the C++ count's `SeqCst` operations order it. But `get_mut` also answers `None` while any `Weak` lives (the pinned Rust 1.98.1's library/alloc/src/sync.rs:2639-2640, :2785-2789: `get_mut` calls `is_unique`, which requires the weak count to be 1 and the strong count to be 1), and the design hands out `Weak` for timer tasks' owners and back-pointers (RULEBOOK 2.8; s3-memory.md E4's `t3m_`), so a test the C++ repeats until it passes would never pass there. Some tests run inside the object, which holds no `Arc` of itself: `ObITmpFile::can_remove` (src/storage/tmp_file/ob_i_tmp_file.cpp:910-914), polled at src/storage/tmp_file/ob_i_tmp_file_manager.cpp:180, and `ObIOService::destroy` (src/share/io/ob_io_manager.cpp:610-615). The reviewer's other fallback, `Arc::strong_count` followed by an Acquire fence, is not used: `strong_count` is a relaxed load, and s8 4 rule 8 bans fences outside the named crates.
