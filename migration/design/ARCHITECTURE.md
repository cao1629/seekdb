1. 2. A trait in the lower crate, implemented higher and handed down through the server context, as the C++ already does with `ObIRootCommandService` (src/query/api/query/command/ob_root_command_service.h:36) and `ObITabletScan` (src/data_plane/api/data_plane/access/ob_tablet_scan.h:493).

4. A trait in sql-exec for SQL's calls into PL (224 symbols), implemented in pl.
5. Inside the core the new API decides: sstable below transactions below tablet.

A downward edge to a crate not on the row is fixed by adding that crate to the row, which can never make a cycle: the rows above already hold every such edge the include and link graphs show (the command above reports them as `listed`). Three kinds of edge are not on any row because they disappear by design: seekdb's includes of share, sql and storage headers go through observer or are dropped with signals 49, 59 and 63 (s1-crates-core.md 4.1 rule 4); resolver and PL calls of `parse_malloc` become `ParseTree` methods (s4-sql-front.md 1.2 rule 5); and kept C that includes a frozen C++ header, such as the parser's src/share/schema/ob_priv_type.h, is compiled against the header and makes no Rust edge. The Step 1 exit's "acyclic crate graph" holds when check_crate_graph.py passes on this table and the scripts above, rerun on the design map, leave no upward edge without a ledger row; Step 2a's survey `cargo check` confirms it on Rust code. Rejected: a crate per Bazel target (sql and storage are one runtime library each, R01 §1.4); a crate per module root (sql and storage are 5-9 times the cap, and the storage↔sql, sql↔pl and sql↔observer link cycles stay).

### 1.3 The core's scope

The hand-designed core is the report's narrow rows (about 352K lines) plus the schema object model (88,602) and the storage entry points the SQL tier calls (storage/access, tx_storage and ls, about 55K): about 500K lines, built first and exercised by Step 2a (493,211 live hand-written lines by s1-crates-core.md 2.1's `core_scope.py`). Rejected: the narrow 352K (Step 2a would need stand-ins for what the core must design) and the wide 600-650K up front (off the narrow path).

This document fixes the storage and transaction core only where the judge sees it (section 6, s6-storage.md) and where PLAN §3's outline decides it; s6-storage.md section 10 lists those rules, what crash recovery must reproduce for families 9 and 15, and the parts the core API sessions design before Step 2a's stubs are written: the tablet and table-store API, memtable MVCC and the transaction context, callback order, MDS, the WAL, checkpoints and replay, and ob-epoch's API.

## 2. Errors

**Decision.**
- **One error type,** in ob-errno: `pub struct ObError(i32)` (`Copy`, `Eq`, `Hash`, never 0) and `pub type ObResult<T = ()> = Result<T, ObError>`. Each catalog code is a `pub const` under its C++ name, usable as a `match` pattern; `OB_SUCCESS` is `Ok(())`. Any non-zero `i32` is accepted, because codes outside the catalog occur: init.sql sets a tracepoint with `error_code = 4` (tools/deploy/init.sql:26), PL `SIGNAL` carries user numbers (src/pl/ob_pl_interpreter.cpp:133). The 24 predicates of src/share/ob_define.h:71-265 become methods (`awk 'NR>=71 && NR<=265 && /^inline bool is_/' src/share/ob_define.h | wc -l`). The error carries no message, and has no `Display`, `std::error::Error` or `From` conversion, so no second error type can grow around it (s2-errors.md 2.1).
- **Codes used as values stay values:** `Err(OB_ITER_END)` wherever the C++ returns and tests `OB_ITER_END`. A core API replacing a C++ API keeps that API's codes (hash-map lookups, row and batch iterators, `databuff_printf`'s `OB_SIZE_OVERFLOW`); `Option`-returning APIs come after parity (default, for the developer to confirm).
- **Output parameters stay `&mut`** in the C++ order, so a value the callee wrote before it failed stays visible (s2-errors.md 2.2 rule 2); only hand-designed core APIs return `ObResult<T>`. A call whose only C++ failure was a general allocation failure becomes a plain statement (Decision 12).
- **One form per construct** (s2-errors.md 2.3's table): `?` only where, from every point where `ret` can first become an error, nothing but a log runs before the function returns; otherwise a local `ret` with every C++ statement in the C++ order and no `?`. `OB_SUCC(ret) &&` guards become `ret.is_ok() &&`; `OB_X == ret` tests become `matches!` or `match` arms; renames and resets are written as the C++ writes them; `COVER_SUCC` becomes `ret = ret.and(tmp)`; `CK`, `OX`, `OZ` and `OV` stay `macro_rules!` whose expansions are exactly those forms. R02 §5.2's rows that rename through `map_err`, reset through `if let Err(e)` or expand the check macros by hand are not used, since they break the rule above. Comparators holding `int &ret = ret_;` return `ObResult<bool>` and are called only by the port's sort, heap and binary-search functions (section 10), which stop at the first error, or directly by code that tests the result at once, such as the top-N check (src/sql/engine/sort/ob_sort_op_impl.cpp:434-466, its error read at :2420, :2432); `operator=` recording `error_ret_` becomes a fallible `assign`. Log macros take the error as an argument, instead of reading a local named `ret` (src/oblib/lib/oblog/ob_log_module.h:261-262), and print `ret=<code>` as today (default, for the developer to confirm).
- **Messages** stay in a Rust `ObWarningBuffer` with the C++ limits (a 512-byte message, a 64-item ring; src/oblib/lib/oblog/ob_warning_buffer.h:51, :141), one per session as `Arc<Mutex<_>>`, reached through a per-thread slot that the request entry sets as `ObMPBase::setup_wb` does (src/observer/mysql/obmp_base.h:122-128) (default, for the developer to confirm). `log_user_error!(OB_X, ...)` records the message and evaluates to `OB_X`. One function builds the error packet as src/observer/mysql/obmp_packet_sender.cpp:527-700 does and hands it to sql-nio's `encode_error_payload`; SHOW WARNINGS keeps the rule of src/sql/session/ob_sql_session_info.cpp:660-672.
- **One generator replaces gen_errno.pl,** reading ob_errno.def and mysql_errno.h unchanged. It writes the constants, the table, the eleven lookups of src/share/ob_errno.cpp:15530-15633 with their fallbacks, the ob_error tool's data, typed argument lists for the 468 formatted messages, and a check that pins the 19 values copied into src/sql/parser/parse_define.h:26-44 (`OB_PARSER_SUCCESS`, 13 values equal to catalog codes and 5 that the catalog lacks: -9644, -9646, -9650, -9605, -9670). It writes no C header for the islands: geo and vsag keep the frozen src/share/ob_errno.h their kept code includes, and a gate compares every value in it and in src/oblib/lib/ob_errno.h with ob-errno's (s7-islands-unsafe.md 7.2 rule 5). It keeps each oddity: the duplicate name (src/share/ob_errno.def:1868, :1872), the malformed lines :575 and :702, the OB name used as a MySQL number (:792), and the client numbers of codes outside the catalog: 0 for a code in (-65535, 0) with no entry, `-code` for a code at or below -65535 and the value itself for a positive code, each cut to 16 bits (src/share/ob_errno.cpp:15614-15625; src/observer/mysql/obmp_packet_sender.cpp:651). Messages are printed with C semantics (byte precision, the 511-byte cut), never with `format!`.
- **Every C-format text goes through one formatter,** ob-errno's `cfmt`: user messages, and the printf family that prints plan text and overflow messages, `databuff_printf` (1,995 lines in src, `grep -rE '\bdatabuff_printf\(' src --include='*.cpp' --include='*.h' --include='*.ipp' | wc -l`), `BUF_PRINTF` (923 lines in src/sql) and `snprintf`, among them the `%08X` query-block names (src/sql/resolver/dml/ob_sql_hint.cpp:389) and the `'(%e + %e)'` overflow text (src/sql/engine/expr/ob_expr_add.cpp:712). `cfmt` implements every conversion the printf sweep finds (s2-errors.md 2.9), and the core build tests it against the reference libc's `vsnprintf` for every format and argument type that sweep lists.

**Why.** 5,718 lines compare `ret` with a specific code; 347 codes are compared, the top 10 covering only 64.6% of comparisons (R02 §2.4); and about 45% of core and SQL-tier lines run under no case (coverage README), so a one-for-one form that reviewers check against the source beats reshaping each site. SHOW WARNINGS keeps a message recorded under another code while the synchronous packet drops it (R02 §2.3), and the asynchronous end-of-transaction callback sends the session buffer's message whatever code recorded it (src/observer/mysql/ob_mysql_end_trans_cb.cpp:254-272), so the message cannot travel inside the error; keeping the callers as written keeps both.

**Rejected.** A 1,545-variant enum (it still needs `Other(i32)`); errors carrying messages; an error enum per crate (storage codes are tested in SQL); `anyhow` (loses the code); passing the warning buffer explicitly (changes every function on the way to 2,799 `LOG_USER_ERROR` calls in 393 files, with no change in behavior). The core build checks every lookup against C++ for all codes and every format against `vsnprintf`.

## 3. Memory

### 3.1 Every allocation has one owner

The owner is the server context, a session, a cached plan, a statement's compilation, a plan execution, a batch, a budget owner, or a receiver (thread, task, timer, queue, channel, cache); each inventory row names it. Rules (R03 §4.1):
1. Compilation: IR objects in typed-id arenas (section 4) in the compile stores, which the statement attempt's exec context owns until the result is sent, as the C++ exec context owns the factories (s4-sql-front.md 2.3 rule 5); names, literals and parameter values in one per-statement bump arena (bumpalo) borrowed as `&'q`; lists inside IR objects are std `Vec`s the object owns, whose heap bytes -11049 does not count (default 9); no `Rc` or `Arc` in the IR.
2. A cached plan owns all its memory, is `Send + Sync + 'static` and is shared as `Arc`; code generation copies out of the statement arena.
3. Execution: rows live in column batches written by the producing operator and are borrowed until its next call (the frame owns the slots, the producing operator is their only writer and owns its skip vector, s5-execution.md rules 2.6 and 4.3); an operator that keeps rows copies them into a store charged to the work area; expression temporaries go into a per-execution arena reset between batches through `&mut`.
4. A scan holds its source (an `Arc` of the tablet snapshot or cached block, or a memtable reference), and its views borrow from it.
5. Handoff is owned data (`Vec<u8>` or `Box<[u8]>`, `Arc` for several receivers); the spawn, queue, timer, channel and cache-insert APIs require `T: Send + 'static`; scoped threads where the caller waits.
6. One thread per arena: the 29 `ObSafeArenaAllocator` lines become per-task arenas.
7. Long-lived owners keep collections that free item by item; nothing with a destructor goes into a bump arena.
8. No implicit current context: `CURRENT_CONTEXT`, `WITH_CONTEXT` and `ObArray`'s binding at its first allocation (src/oblib/lib/container/ob_array.h:484-492) become an argument or a field.
9. `inc_ref`/`dec_ref` becomes `Arc`; a release into a pool or budget becomes a handle whose `Drop` uses `Arc::into_inner` (s3-memory.md R2). Pools that only reuse memory go; a pool stays only when Decision 12 names its limit: the KV-cache handle pool (src/share/cache/ob_kvcache_store.cpp:979-1032).
10. The schema guard's getters hand out `Arc<T>` through `&mut Option<Arc<T>>` out-parameters, and the guard keeps an `Arc` of each schema it handed out, as `put_to_local_cache` pins a KV-cache handle today (src/share/schema/ob_schema_getter_guard.cpp:2264-2290); full schemas stay in the KV-cache-backed schema cache (src/share/schema/ob_schema_cache.h:194), so a caller holds several schemas from one guard at once (s3-memory.md R4; default 38).

`ObIAllocator&` for statement data becomes `&'q Bump`, and an owned value where the callee keeps the data; `ObString` becomes `&[u8]`, `&'q [u8]` or owned bytes; placement new and explicit destructor calls become constructors and `Drop`; engine code has no generic `A: Allocator` parameters. Values that live both inside a statement and in stores that outlive it hold their bytes as `Cow<'q, [u8]>`: `RawExpr`'s byte fields (s4-sql-front.md 2.3 rule 1) and `ObObj`, which `ObConstRawExpr` holds, so a PL package, a PL cache object or another long-lived owner keeps its expressions with `'q = 'static`.

**Why.** The report's bug table (report §2) is this class, and rules 4-6 make each case a compile error: bc31e03f4 (a PX buffer in a closure), eda242c9a (request-arena memory in an async task), 9d24b8807 (shallow strings in a queued task), dd899675c (an arena reset under a reader), 9e2b6ba16 (pointers outliving their iterator), 62b9d1a81 (one arena shared by parallel tasks). **Rejected:** `Rc`/`Arc` IR nodes (the IR has cycles through `ref_stmt_` and `outer_expr_`); owned values everywhere (an allocation per row against the 1.2x gate); shared arenas; allocator-generic code (a compiled copy per allocator).

### 3.2 Out-of-memory: Decision 12, exactly

- A general allocation failure aborts the process. The 4,737 assignments of `OB_ALLOCATE_MEMORY_FAILED` get no Rust counterpart outside the owners below (R03 §1.8).
- Typed errors stay only at Decision 12's owners and logical limits, each with its C++ formula, parameter, check point, code, message and behavior: clog and replay (replay turns -4013 into `OB_EAGAIN`, src/storage/tx/ob_tx_replay_executor.cpp:696-703); the IO allocator (objects retry until the IO timeout); the KV cache store (one wash under a lock, src/share/cache/ob_kvcache_store.cpp:915-961) and its handle pool; the micro block cache (-4013 at once: the 3-retry loop at src/storage/blocksstable/ob_micro_block_cache.cpp:396-400, inside `alloc_data_buf` at :387-408, has no caller, since the only `alloc_data_buf` calls, src/storage/tmp_file/ob_tmp_file_cache.cpp:698, :739 and :769, reach the tmp-file cache's own override defined at :654); the vector module (-7603 stays inside src/storage/allocator/ob_vector_allocator.cpp:142; vsag's `NO_ENOUGH_MEMORY` is -4013) and the IVF cache; the query memory tracker (-11049); memstore full (-4030); the temp-file write buffer pool (-9124); the work-area spill; hash-join partition depth (-4013, src/sql/engine/join/ob_hash_join_op.cpp:838-843).
- Counting is by explicit charges: a budget is a limit and an atomic counter with `ObBlockAllocMgr::alloc_block`'s add, compare, undo (src/oblib/lib/allocator/ob_block_alloc_mgr.h:38-50); a charge returns its bytes when dropped; a request's total is its arenas' bytes, each as of its last report, plus its charges. Engine crates implement neither `GlobalAlloc` nor `Allocator`. An owner whose C++ formula differs keeps it: the vector module checks every 20th allocation or one of 2 MiB or more (src/storage/allocator/ob_vector_allocator.cpp:131-155). `ObMemTracker` moves down to ob-base (1.2 fix 1).
- Budgets trip by the same formulas at the same check points, not at the same byte counts (default, for the developer to confirm), with one exception: the SQL work area counts the C++ figures (stored-row headers, 12 bytes per cell, hash-table buckets), so sorts and hash group-by dump at the same rows and their ties and group order stay (s5-execution.md rules 4.4 and 6.9). A dump at another row would change unmasked output, and family 12 checks spilling.
- The eleven other finite limits the C++ keeps (the 1 GiB LS allocator, async-task, dedup-queue, DDL scheduler and DDL task queues, the 10 GiB DDL redo replayer, the 4 GiB storage meta cache IO, the 512 MiB and 128 MiB meta persister and checkpoint writer, `ObResourceMap`'s and the IO manager's own allocators) and the large-tablet buffer pool's -4013 are dropped: their memory becomes plain allocation (s3-memory.md 3.7.5; default, for the developer to confirm).
- `try_reserve`-style calls appear only at those owners and in client-sized buffers, as sql-nio does today; SQL functions keep their own size checks first.
- The global allocator is the reference's jemalloc 5.3.1 (seekdb-jemalloc-sys =0.2.2, deps/external/Cargo.toml:10) with its `je_malloc_conf` (src/oblib/lib/allocator/ob_malloc.cpp:38-42), so the 1.2x comparison measures no allocator change.
- Memory virtual tables are filled from the Rust counters (default, for the developer to confirm); no test reads their rows (R03 §1.9).
- Family 12: the -11049 message prints `mem_hold` (src/share/ob_errno.def:1880), which no Rust build matches byte for byte. Replacing the number in that scenario's text would hide a difference in output, which makes it a third mask, and Decision 6 lists exactly two ("Nothing else is tolerated", PLAN §4, "The masks"). So default 10 is a proposed amendment of Decision 6 for the developer, not a design choice (section 17); until it is recorded, the scenario's -11049 line differs and is documented at the final gate. -7603 stays internal, and the family records what the C++ returns.
- On later platforms a general out-of-memory ends the host, so these owners are where sizing keeps it rare; wasm limits come from its 2 GiB heap when wasm returns.

**Rejected** (R03 §3.4-3.5): a counting global allocator (an `unsafe impl` and a header per allocation); allocators that refuse over a limit (`Allocator` is an `unsafe trait`); per-context jemalloc arenas (jemalloc only, so no wasm).

## 4. IR ids and the ParseNode mirror

### 4.1 One id scheme

Every object the C++ identifies by address gets a typed id `Id<T>` (ob-base) of 64 bits: an arena number in the high 32, from one process-wide counter that skips any number a live arena still holds, so ids are unique among live arenas as addresses are, even after the 32-bit counter wraps while PL cache objects keep their arenas; and an index in the low 32 into a `Vec`-backed `Arena<T>` owned by its context. A lookup that picks among several arenas by number aborts in every build when no live arena has the number; a lookup in one arena checks the number under debug assertions, which is the stale-id check (s4-sql-front.md 2.1). It covers parse nodes (`NodeId`), expressions (`ExprId`), statements, table items, optimizer objects (operators, plans, paths, join orders), query-range nodes and the tables of a cached plan. Rules (R04 §4.3):
1. One id per C++ allocation, made where the C++ makes the object (`create_raw_expr`, `ObRawExprCopier`'s copies included; the statement, table-item, operator and plan factories); a proxy factory uses its target's arena. An in-place edit keeps the id.
2. Equality is id equality; `find_item` (src/sql/optimizer/ob_optimizer_util.h:264-286) and the set helpers keep their bodies.
3. Address-keyed maps become id-keyed maps with a fixed hasher, iterated in insertion order (the C++ order changes from run to run); debug builds can reverse it to expose a hidden dependence.
4. `ObRawExpr*&` on a local or field becomes `&mut ExprId`; a slot inside an expression is read, computed and written back; `USELESS_POINTER` becomes `Option`.
5. Reused memory keeps its order and its id: the `JoinPath` recycle list becomes a stack of ids popped from the back (src/sql/optimizer/ob_join_order.cpp:5435-5448, :11037-11051), and `ObStmtFactory` builds a new select statement in the oldest freed one's slot, first in, first out, so it gets that statement's old id as the C++ statement gets the old address (src/sql/resolver/ob_stmt.cpp:207-253, freed through `ObTransformUtils::free_stmt` on eight lines of cost-based rewrite). `evaluate_cost`'s temporary factory is a temporary arena of the compilation's expression store, pushed and popped where the C++ scope begins and ends (src/sql/rewrite/ob_transform_rule.cpp:379-398; s4-sql-front.md 2.3).
6. The C++'s own ids (`stmt_id_`, `table_id_`, column ids, operator numbering) stay separate fields; arena ids are never printed or sorted on.
7. Back-pointers become context (`rt_expr_` a code-generator table indexed by `ExprId`); cycles (`ref_stmt_`, `outer_expr_`) are id fields; marks stay on the object; `RawExpr` is the common fields plus an enum of 27 variants: the 29 classes declared in src/sql/resolver/expr/ob_raw_expr.h less the abstract bases `ObTerminalRawExpr` (:2528) and `ObNonTerminalRawExpr` (:3270), whose fields sit in their subclasses' `base`.

**Why.** Identity reaches output: the output pass counts references per address (src/sql/optimizer/ob_logical_operator.cpp:246-322, :1836-1866), which decides the 4,005 pinned `output(...)` lines, and the code generator makes one `ObExpr` per distinct raw expression (src/sql/code_generator/ob_static_engine_expr_cg.cpp:190). The C++ mixes factories, and PL packs addresses into `int64_t` (src/pl/ob_pl_build.cpp:1062), which 64-bit ids fit (64 bits for every IR type: default, for the developer to confirm). **Rejected:** arena references with `RefCell` (a lifetime in every signature, borrow failures at run time); `Rc<RefCell<_>>` (cycles leak); copy-on-write expressions (they change which nodes are the same object); 32-bit ids (they collide across the factories the C++ mixes).

### 4.2 The ParseNode mirror

The C tree is converted once, when `parse_sql` returns, into `ParseTree<'q>` (sql-parse-tree): one node per C node in an arena (a map from C address keeps a node with two parents one node), built with an explicit stack. Fields keep `ParseNode`'s C names (src/query/api/query/parser/parse_node.h:129-195): `flag_` a `u32` with an accessor per bit field, `value_` an `i64` with lane helpers, `str_value_` and `raw_text_` as `Option<&'q [u8]>` borrowed from the statement arena where `parse_malloc` put them (`None` for a NULL pointer: the C++ tells `""`, non-NULL and empty, from `X''`, NULL, in `parsenode_hash`, `parsenode_equal` and 52 NULL tests outside the parser, s4-sql-front.md 1.1), `children_` as `Option<NodeId>` (an index at or past `num_child_` aborts). Parameterization and resolvers edit through `&mut ParseTree`; the Rust `ObFastParser`, translated keeping its lexer statement for statement and checked against the C++ fast parser in the core build (s4-sql-front.md 1.4), builds in the same type; `parsenode_hash` and `parsenode_equal` keep the C field order (src/sql/parser/parse_node.c:650-720).

**Why.** Resolvers read children by position (2,672 `children_[` lines in 77 files) and parameterization edits the tree in place (src/sql/plan_cache/ob_sql_parameterization.cpp:583-585), so the 93 registered statement resolvers keep their shape, and `unsafe` stays in one converter. **Rejected:** a typed syntax tree (resolvers lose their shape); handles over the C tree (`unsafe` on each access), kept as the fallback if Step 2a's parse time misses 1.2x (default, for the developer to confirm); a Rust parser now (Decision 13).

## 5. The column batch and the storage filter trait

**Decision** (R05 §4.1-4.2):
- ob-values: `ObDatum` is a 12-byte value with 4-byte alignment and no `packed` attribute, `loc: [u8; 8]` (the value when it is not null, has no flag and is at most 8 bytes long, otherwise a `BufId` and an offset as two little-endian `u32`) and `desc: u32` (length, flag and null bit exactly as the C++ `pack_`, src/oblib/common/datum/ob_datum.h:134-165). 12 is the C++ size (asserted at src/sql/engine/basic/ob_pushdown_filter_simd.cpp:46), which stored-row sizes and batch-size formulas use; a `u64` field would make 16 bytes, or need `packed`, under which a short value cannot be lent in place. `DatumVec`, `ObBitVector` (moved from share/vector, 1.2 fix 1), and a `BufTable` of the buffers a batch refers to (`Arc`'d blocks, arena chunks, plan constants). The datum API is the only access.
- sql-exec: each run has an `EvalFrame` with one slot per expression. The plan, with its evaluation functions as plain `fn` values, is immutable and shared by PX workers, which build their own frames. The `ObOperator` trait keeps the C++ names: `get_next_batch(&mut self, frame, max_row_cnt) -> ObResult` is the wrapper of src/sql/engine/ob_operator.cpp:1016-1157, written once as a provided method in the C++ step order, and each operator implements `inner_get_next_batch`. The wrapper fills the operator's own `brs_` (size, end flag, skip vector) as the C++ does, and a parent reads it through `child.brs()` at each use instead of keeping a borrow, since operators and their helpers keep a pointer to a child's batch across their own calls on 11 members (`grep -rn 'const ObBatchRows \*[a-z_]*_;' src/sql/engine --include='*.h'`; s5-execution.md rule 4.3); datums stay valid until the producer's next batch.
- storage-api: storage owns the filter tree (AND, OR, white including the JSON-path white filter, black, dynamic, sample, and the truncate-partition filter storage adds itself, src/storage/truncate_info/ob_truncate_partition_filter.cpp:279), white filters on encoded data, the skip index, `ObWhereOptimizer`'s reordering and where batches end. Black filters, row filters and generated columns call SQL through a `ScanHost` trait passed into every scan call, at the granularity the C++ calls into SQL today (per batch, per decoded row, per block bound; s5-execution.md rule 5.2). Aggregate pushdown keeps the C++ protocol (src/share/aggregate/ob_pushdown_aggregate_protocol.h) as traits, with one change: `emit` takes the output columns, since a Rust program cannot keep a borrow of the frame. Storage fills caller-owned `DatumVec`s and registers block handles in a caller-owned `BufTable`: no copy at the scan, as today (src/storage/access/ob_vector_store.cpp:306-352), and no SQL type in storage. Every datum storage hands to SQL, in a per-row filter call or a block bound too, refers to a buffer it registered in that table first, memtable rows included (s5-execution.md rule 5.11).
- The `ObIVector` formats stay out of the query batch; since cbcea2b91 only the DDL write path uses them.

**Why.** Frames are untyped memory at generated offsets (src/query/api/query/engine/expr/ob_expr.h:364-386), which Decision 14 keeps out of the SQL and storage crates. Storage and SQL call each other in a loop today (src/sql/engine/basic/ob_pushdown_filter.cpp:1370-1449 into src/storage/blocksstable/ob_micro_block_row_scanner.cpp:2122-2131); one trait call per batch splits the crates at the C++'s own cost. **Rejected:** offset frames (`unsafe` everywhere); copying at the scan (the C++ copies nothing); `ObIVector` or Arrow formats (rewrites 528 expression bodies); storage depending on `ObExpr`; per-row callbacks (they change which failing row is reported). The fallback, if Step 2a measures the handle datum outside 1.2x, is a raw-pointer datum crate added to the named list (default, for the developer to confirm).

## 7. The server context and the binary crate

### 7.1 Context structs

**Decision** (R07 §4): no engine singletons. One context per layer, each holding an `Arc` of the one below and dereferencing to it: `RuntimeContext` (ob-runtime: absolute directories, config, budgets, timers, the thread spawner, IO, the KV cache), `StorageContext` (storage-tablet), `SqlContext` (sql-exec), `ServerContext` (observer). There is no fifth context. `Server::open(ObServerOptions) -> ObResult<Server>` in observer builds them bottom-up in the C++ module order (src/observer/omt/ob_server_runtime_controller.cpp:1182-1547); `Server` holds the `ServerContext` and offers `request_stop` and `wait_stop_request`. Constructors take dependencies, replacing `init()` and `is_inited_`. Upward traits and the two real cycles (the log service and the LS service; SQL and PL) are `OnceLock<Weak<dyn Trait>>` cells, filled in one binding step whose `check_bound()` fails on an empty cell. Threads start in two groups: `RuntimeContext`'s own threads (the timer service, the log writer, IO) start when it is built, before the server slog replay, as the C++ starts them before replay at src/observer/ob_server.cpp:1155 (the timer service at :682, the async logger at :687, the IO manager at :1125), and they read no cell; every other thread starts after the binding step. The runtime controller's two timers, which the C++ schedules before replay (:1150; src/observer/omt/ob_server_runtime_controller.cpp:199-230), are scheduled after the binding step, so their first run comes later, which no case observes (assumption). Functions that reach process state take `ctx` after `self`, typed as the lowest context that holds everything they reach (the declaration index records it). A service is a field of the lowest context whose crate may name it, so the storage-api traits (the estimator, the optimizer storage service) are `StorageContext` fields that `SqlContext` reaches by deref. `server_service<T>()` (1,224 uses), `GCTX` (891), `GCONF` (682) and `get_instance()` (623) become those fields. A lookup from a crate that can name no context holding the service (443 of 1,195 lookups outside standby, mostly storage-tx looking up its own services and rootserver looking up `ObLocalManagementService`; s1-crates-core.md 3.4 rule 4) goes through an `Arc` or `Weak` that the owning object received at construction, or a parameter; never a `static`. The 149 null checks and 112 `SERVER_MODULE_SCOPE` guards go, unless the site can run before the module graph exists; `getcwd()` paths become `ctx.base_dir().join(..)`; each `ObTimer` stays one Rust `ObTimer` of the same name, each `ObTimerTask` subclass an `impl ObTimerTask` holding `Weak<Owner>`, whose method keeps the name `runTimerTask`.

Allowed process-wide state, and nothing else: tables filled once (expression registry, error catalog, charsets, system-variable metadata); the logging facade; the `DEBUG_SYNC` and tracepoint registries under their C++ names; hooks third-party libraries hold per process (vsag's logger, CRoaring's memory hook); counters that only hand out unique numbers (arena numbers); the thread-locals of section 11.

**Why.** Today's slots are raw pointers bound at run time (src/share/rc/ob_server_runtime.h:126-148), every lookup already goes to the caller's module or a lower one (R07 §1.2), and Decision 8's guideline wants the engine usable as a library. **Rejected:** `static` services (one engine per process, no reopening); a registry keyed by type (failures at run time); trait bounds on every function.

### 7.2 Threads and timers

One thread spawner starts every engine thread with its C++ name, the configured stack (section 11) and, on macOS, the USER_INITIATED QoS of src/oblib/lib/thread/thread.cpp:341-345. sql-nio's reactor threads are the one exception: sql-nio may use only ob-platform, so it keeps its own `Builder::spawn` (RULEBOOK section 1), and since observer reaches it only through its `mysql` feature, a library host that brings its own threads does not run it. It is an object-safe trait in ob-runtime, `ThreadSpawner::spawn(&self, name, stack_size, body: Box<dyn FnOnce() + Send + 'static>) -> ObResult<JoinHandle<()>>`; seekdb builds ob-runtime's native spawner and passes it in `ObServerOptions`, so a library host can pass its own. `ObTimerService` is a `RuntimeContext` field, not a process static. The C++ timer behavior is a contract (src/oblib/lib/task/ob_timer_service.cpp:477, :534-548): one task at a time per timer, the next run at completion plus the delay, cancel lets a running task finish, a stopped timer returns `OB_CANCELED`, intervals copied unchanged. ### 9.3 ABI rules for geo and vsag (R08 §4.7)

1. One header per island (`obgeo.h`, `obvsag.h`), generated by cbindgen from the Rust declarations, checked in and diffed at gates; the C++ shim includes it, so drift fails the C++ compile. Rejected: R01's hand-written headers, two copies with no compiler between them.
2. C++-implemented entries `<tag>_<verb>`, Rust callbacks `<tag>_rs_<verb>`, structs `<Tag><Name>`; tags `obgeo` and `obvsag` (`vsag_` belongs to vsag's own C API).
3. Only fixed-width integers, `float`, `double`, `bool`, views `(const T *, int64_t count)` over those (vsag passes `float *` vectors, `int64_t *` ids and `uint32_t *` sparse dimensions, src/oblib/lib/vector/ob_vsag_adaptor.h:122-160), `#[repr(C)]` plain structs and opaque handles cross.
4. Every entry mirrors exactly one call the SQL tier makes today, and returns an OB code as `int32_t`, taken from the frozen src/share/ob_errno.h the kept code includes; messages are formatted in Rust.
5. Every C++ entry is `noexcept` with a catch-all; the existing catch lists keep their mappings, `std::bad_alloc` included (src/share/geo/ob_geo_dispatcher.h:1314-1366) (default, for the developer to confirm); an entry whose call path has no handler today logs and aborts, as the C++ ends in `std::terminate` there (default 33).
6. Each side frees what it allocated; island objects sit behind handles destroyed once, from the Rust `Drop`.
7. Receivers come first, never globals; callbacks may run on vsag's threads, so they use only the `Send + Sync` receiver.
8. No re-entry, and no `longjmp` over a Rust frame.
9. Islands build with the reference compiler, SDK and flags (section 13) and link the same archives.

The geo API is bytes in and bytes out, about 76 entry points and 10 callbacks; MVT and GeoJSON-to-JSON-binary move to Rust (R08 §4.2). MVT's tile building and protobuf packing (src/share/geo/ob_geo_mvt.cpp, whose only user is `ST_AsMVT`'s aggregate in src/sql/engine/aggregate/ob_aggregate_processor.h) move to sql-engine with a hand-written protobuf writer that reproduces protobuf-c's packing of the vector-tile messages, checked by known-answer bytes from the C++; the protobuf-c code (ob_vector_tile.pb-c.{c,h}) is generated and not translated, and no protobuf crate is added. The three geometry steps stay island entries: building the geometry, the 3D-to-2D conversion and the command-encoding visitor (ob_geo_mvt.cpp:67-69, :112-115; s7-islands-unsafe.md 7.1).

### 9.4 The kept oblib subset and island memory (PLAN §8 item 19)

The islands compile against the unchanged headers they reach (196 files and 77,558 lines for geo; 118 and 38,448 for vsag) and link a few replacement .cpp files defining the 124 and 38 out-of-line symbols they need: logging forwards to Rust, allocation calls a Rust function, `SMART_CALL` reads the stack bounds Rust records (section 11), charset and dtoa forward to Rust, so their behavior matches by construction; small leaves are copied (R08 §4.3). ## 10. Determinism: numbers, sorting, hashing, overflow and profiles

**Decision** (R09 §5; R05 §4.3):
- **Numbers:** ob_dtoa.cc, ObNumber (both live families, `_v2_` and `_v3`, each caller keeping its own) and the decimal-int library (the default for DECIMAL, src/share/parameter/ob_parameter_seed.ipp:302) are translated line by line into ob-values; murmur_hash (murmurhash64A, murmurhash2, `fnv_hash2`) is translated line by line into ob-base's `hash` module, since `ObHashMap` in ob-base hashes `ObString` keys with it (src/oblib/lib/hash/ob_hashutils.h:773-779). No output text comes from Rust's float formatting; doubles are parsed only by the translated `ob_strtod`; callers pass the C++ widths.
- **No FMA:** no `mul_add`, no `algebraic_*` method (stable since 1.98.0, they let the compiler fuse and reorder) and no FMA intrinsic, since the C++ calls none on arm64. Float code keeps the C++ order, types and lane order; libm maps one to one (`rint` to `round_ties_even`); float comparisons are ported literally (NaN last, -0.0 equal to 0.0, DOUBLE(M,D)'s tolerance, src/share/datum/ob_datum_cmp_func_def.h:139-171).
- **Overflow:** `wrapping_*` where the C++ relies on wraparound (hash mixing, the add-then-test operators of src/sql/engine/expr/ob_expr_add.cpp:229-238, `fnv_hash2`); every C++ check kept with its code and text; every guard before `/` and `%` kept, since Rust panics on zero and on `MIN / -1` in all profiles, and every other integer division by a non-constant divisor goes through ob-base's `arm64_div`/`arm64_rem`, which return what arm64's `sdiv`/`udiv` (and `msub` for `%`) give: `a / 0` is 0, `a % 0` is `a`, `MIN / -1` is `MIN` and `MIN % -1` is 0 (default 37; RULEBOOK 2.6), since the overflow sweep reaches only value and expression code and a division elsewhere would otherwise panic where the C++ returns; `char` read as a number is `i8`, `long` is `i64` everywhere.
- **Encodings kept and free:** ObNumber's and decimal-int's binary forms and the JSON binary (`ObJsonBin`) are kept byte for byte, since SQL functions print their sizes (`JSON_STORAGE_SIZE`, `JSON_STORAGE_FREE`, which family 5 runs over every expression); `OB_UNIS` serialization and every on-disk and log format are free (Decision 11), and an encoding whose bytes or size a SQL function returns is kept (s6-storage.md 4.5).
- **Sorting:** ob-base holds a transcription of `std::sort` and the heap functions from the SDK 26.2 libc++ (`_LIBCPP_VERSION` 200100, without the branchless partition), with its license notice (default, for the developer to confirm), used at every `lib::ob_sort`, `std::sort` and heap site; `std::stable_sort` becomes `sort_by`; `ObAdaptiveQS`, `ObBinaryHeap` and OB's other sorts are translated, with the rule that picks among them (`check_can_encode_sortkey`, tracepoint 1200).
- **Hashing:** bit-exact murmurhash64A, murmurhash2, `fnv_hash2`, the datum and collation hashes, and their seeds (16777213 for hash join keys and its NULL-key counter, recursive CTE search and `ObExprHash`; 99194853094755497 for hash group-by, window functions, `ObHashCols` and the hash partitioning code; 0 for `ObString` keys of OB hash maps, KEY partitioning and NDV; s5-execution.md rule 7.2); `ObHashMap` and `ObHashSet` ported with their bucket arithmetic (src/oblib/lib/hash/ob_hashtable.h:1139; ob_hashutils.h:677-689); the hash-join table's layout; first-seen group order. Exact hash order is the rule everywhere, with the mask as a safety net (default, for the developer to confirm).
- **Batches:** `detect_batch_size` (src/sql/code_generator/ob_code_generator.cpp:85-170) is translated exactly and sets both `rowset=` and the run.
- **Banned** in engine crates through clippy: `sort_unstable*`, `select_nth_unstable*`, `BinaryHeap`, std `HashMap`/`HashSet`/`RandomState`, `mul_add`, `algebraic_*`, `powi` and `total_cmp` (the full list is s8-numerics-platform.md 7.4's clippy.toml); each `#[allow]` cites an inventory row.
- **Profiles:** `release` (the product and family 14): opt-level 3, thin LTO, overflow checks and debug assertions off, `panic = "abort"`. `judge` (every parity run): the same semantics at opt-level 2, no LTO, 256 codegen units, incremental; Step 2a may move the opt-level (default, for the developer to confirm). `checked`: `judge` with overflow checks and debug assertions on, run weekly from Step 5, diagnostic only (default, for the developer to confirm). The reference's `-DNDEBUG` makes `OB_ASSERT(x)` `(void)(x)` (src/oblib/lib/utility/ob_macro_utils.h:707-708), so it becomes `ob_assert!(x)`, which evaluates `x` in every profile and then applies `debug_assert!` to the value; a plain `debug_assert!(x)` would skip `x` when assertions are off.
- **Every platform follows the macOS arm64 reference's numbers** (default, for the developer to confirm).

**Why.** 770,711 of 912,659 configured result lines come from four matrices that pin three formatters and 365 overflow messages (R09 §2.1). Ties, scan order, `rowset=`, KEY-partition placement, NDV values and the `%08X` query-block names (src/sql/resolver/dml/ob_sql_hint.cpp:389) are unmasked, and a std sort may panic on DOUBLE(M,D)'s non-transitive comparator. **Rejected:** Rust's sorts, hashers or float formatting with normalization (a third mask, which Decision 6 does not allow); overflow checks in the judge profile (the C++ wraps on purpose); tie-breakers added to comparators. ## 11. Concurrency and the stack

**Decision** (R10 §4):
- **Atomics:** a field shared between threads is an `Atomic*` or sits in a lock; every operation is `SeqCst` except the 29 `ATOMIC_*` calls the C++ names weaker (`ATOMIC_LOAD_ACQ`, `_LOAD_RLX`, `_STORE_REL`, `_STORE_RLX`), which keep their order. The 75 lines in 17 files that pass a weaker `std::memory_order_*` to `std::atomic` become `SeqCst` too, which is never less correct; they join the 29 only if Step 2a's sysbench shows a cost (s8-numerics-platform.md rule 4.2). Reference counts, lock words, list links and reclamation clocks are replaced, not retyped. `SCN`, `ObTxSEQ` and LSN become `Copy` types with atomic wrappers. No 128-bit atomics (palf's `LSNAllocator` keeps its 16 bytes under a `Mutex`); no `AtomicPtr` outside named crates.
- **Locks:** parking_lot through a `sync` module in ob-base; `Mutex<T>` and `RwLock<T>` own their data; timed locks keep each site's error code; no pure spin locks; latch ids go; guards never cross threads; callbacks run after the guard drops. What each lock guards, the functions called with it held, its nesting order and its kind come from a lock sweep, lock-guards.tsv, one row per lock declaration (479 declarations, R10 §1.2; RULEBOOK section 5).
- **Lock-free code:** hand-written reclamation (QClock, the retire station, hazard versions) is replaced; structures start behind locks, and ob-epoch serves only where the gate needs lock-free reads, tested with loom; no nightly Miri or ThreadSanitizer job (default, for the developer to confirm).
- **Thread-locals:** state that changes results is a parameter. `thread_local!` holds only a closed list of const-initialized `Copy` values (request deadline, trace id, thread name, diagnostics, caches that change no result, the current stack bounds), plus two slots set and cleared by a scope guard: the warning-buffer slot of section 2, and sql-parser-sys's per-call parse slot, which points the receiver-less C callbacks (`try_check_mem_status`, src/sql/parser/parse_node.c:178) at the current parse's arena and memory tracker for exactly the duration of one C parse call (9.2).
- **Stack:** every `SMART_CALL` site (1,136 lines: 1,130 `SMART_CALL` and 6 `SMART_CALL_LARGE`) calls `smart_call!` or `smart_call_large!` in ob-base, which runs the closure when `stacker::remaining_stack()` covers the reserve, returns `OB_SIZE_OVERFLOW` when one more extension would pass the total cap (as src/oblib/lib/utility/ob_smart_call.h:82-83 does), and otherwise calls `stacker::grow`. The cap counts extension bytes only: the C++ also counts the thread's own stack (ob_smart_call.h:80-81), which safe Rust cannot read, and the firing depth is no contract. Starting values, fixed by the Step 2a probe: 256 KiB and 1 MiB reserves, 128 KiB for plain `check_stack_overflow` calls, 8 MiB extensions, a 64 MiB cap, 8 MiB threads; `stack_size` keeps its name and range and becomes a lower bound (default, for the developer to confirm). The C++ API keeps its names (`smart_call!`, `check_stack_overflow`, `get_stackattr`, `set_stackattr`); the no-argument overload of `check_stack_overflow`, second in src/oblib/lib/utility/ob_common_utility.h:31-44, is `check_stack_overflow_2` under the overload rule of section 14. The depth where `OB_SIZE_OVERFLOW` fires is not a contract; no case expects it.
- **The wasm depth limit is adopted now:** on wasm the same wrapper counts nesting instead of growing.
- **Islands share the stack bounds:** geo's `get_stackattr`/`set_stackattr` read and write the bounds Rust records through two geo-sys functions, and the parser cores' checks call the same check.

**Why.** 724 of 966 member fields touched by `ATOMIC_*` are also accessed plainly (R10 §1.1): data races in C++, compile errors in Rust. Workers get 224 KiB on macOS (src/observer/ob_server.cpp:1966-1974), and the stack switch ran under the 272 cases (R10 §1.7). PLAN §8 item 20: by reading stacker 0.1.25, `remaining_stack` starts from `pthread_get_stackaddr_np` minus `pthread_get_stacksize_np`, the bounds the C++ reads (src/oblib/lib/utility/ob_common_utility.cpp:111-119), and `grow` maps a guarded stack; stacker has no total cap, which the wrapper adds, and Step 2a runs the test. **Rejected:** weaker orderings chosen per field; porting `ObLatch`; translating 17K lines of lock-free code (the 54123f13e bug class would stay); keeping all thread-locals; rewriting recursions as loops.

## 14. Naming rules for the manifest

From R12 §9, made exact in s1-crates-core.md section 5:
1. A translated stem goes to `rust/<crate>/src/<dir>/<stem>.rs`: `<crate>` is the crate of the longest crate-map prefix that matches the unit's source file; `<dir>` is the source's directory below that prefix's directory (for a prefix that names no directory, below its parent), preceded by the row's `dir` value if it has one; `<stem>` is the C++ stem unchanged; a class declared in query/api or data_plane/api goes where its .cpp is. A directory named after a Rust keyword is declared with `r#` (`mod r#static;`), and a stem named `lib`, `main` or `mod` takes a trailing `_`. No two targets may be the same, core targets and generated files included; a moved map row whose target would collide carries a `dir` value (src/share/ob_define has `share`, apart from src/oblib/lib/ob_define), and the manifest script checks it. The map places Step 3 units; a core unit goes to the crate the design names, which overrides the map (RULEBOOK section 4).
2. A file of 4,000 lines or more splits at class or function boundaries into `<stem>_p01.rs`, `<stem>_p02.rs`, in source order; `<stem>.rs` holds the types; members of a split type are `pub(crate)`.
3. Identifiers stay as in C++ (default, for the developer to confirm); macros become lowercase `macro_rules!`; a Rust keyword becomes a raw identifier (`r#type`), and `self`, `Self`, `super` and `crate` take a trailing `_`. A nested type `Outer::Inner` becomes `Outer_Inner` in `Outer`'s file. Overloads in one scope are numbered in header order: the first keeps the name, later ones take `_2`, `_3` and on, and constructors are `new`, `new_2` and on; the declaration index assigns the numbers once, so every unit agrees. A core type that replaces one C++ type keeps its name (`ObDatum`, `ObHashMap`, `ObWarningBuffer`, `ObTimer`, `ObTimerTask`, `ObServerOptions`), and its fields that stand for C++ members keep the members' names, trailing `_` included, so translated code reads them unchanged; a type, field or function with no single counterpart gets a plain name (`ParseTree`, `EvalFrame`, `ScanHost`, `ThreadSpawner`, `RuntimeContext`, `ObExpr::slot`). Rejected: Rust-style names, which need a rename table every unit applies alike, and dropping `ob_` already collides twice (R12 §1.4).
4. Manifest columns: `source`, `target`, `unit_id` (the map's key; `.pNN` for split pieces; `core/<crate>/<module>` for core units), `kind` (`stem`, `split` or `subsystem`), `inputs` (files, with line ranges for pieces); migration/core-manifest.tsv uses the same five and adds `units`, the map unit ids a core module replaces, which the completeness check reads.
5. A script writes every lib.rs and mod.rs from the manifest, so an existing target means done. Generator output goes to `rust/<crate>/src/generated/`, and the generators' Rust back ends live in migration/scripts/gen/ (1.4).
6. Imports use full paths from migration/decl-index/<unit_id>.txt; no glob imports. Exported macros are imported with `use` like any other item and invoked by their bare name.
7. Home modules in ob-base: logging, `log_user_error!`, the check macros, `smart_call!`, `sync`, the hash maps and functions, the sorts, tracepoints and `DEBUG_SYNC`, the scope guard, `Id<T>` and `Arena<T>`, the `allocator` module (`Budget`, `Charge`, `ObArenaAllocator`, `ObMemTracker`), and `ObWarningBuffer`. ob-errno holds `ObError`, `ObResult`, the catalog, `ob_fail!` and `ob_succ!`.
8. The only comments in translated code are `// TODO(port): `, `// PERF(port): `, `// BUG(port): ` and `// SAFETY: `, each on its own line directly above its code (the first three with the C++ file:line, `SAFETY` naming the rule it relies on), and the last-line trailer `// PORT STATUS: confidence=<high|medium|low> todos=<N>`. The frozen core API's public items carry rustdoc, since Step 2b's translator B gets "public API docs only" (PLAN §6, departure 5) (default, for the developer to confirm).
9. Step 3 units write no tests; core crates keep differential tests with vectors recorded from the reference.
