# 03-ob_error-rowid-message-user-format

Family 6 (the error catalog through `ob_error`), unit 03-oberr. Patch:
`03-ob_error-rowid-message-user-format.patch` (one line of one .cpp file).

## What it changes

src/share/ob_errno.cpp:10061, the catalog entry `_error_OB_ROWID_TYPE_MISMATCH` (-5870): its
`str_error` becomes the entry's user-error format text.

| Field | 834bbee1e | Mutated |
|---|---|---|
| `.str_error` | `"rowid type mismatch"` | `"rowid type mismatch, expect %.*s, got %.*s"` |
| `.str_user_error` | `"rowid type mismatch, expect %.*s, got %.*s"` | unchanged |

This is the slip a regenerated catalog can make: `DEFINE_ERROR_EXT` entries carry two message
columns, and the plain message takes the text of the other one. Family 6 exists to catch exactly this
kind of drift once the Rust tree builds `ob_error` from its regenerated catalog (PLAN.md section 4,
family 6).

## Why the patch is in the generated .cpp, and how it maps to the generator input

- src/share/ob_errno.cpp starts with the line
  ``// DO NOT EDIT. This file is automatically generated from `ob_errno.def'.``
  The generator is src/share/gen_errno.pl: run in src/share, it reads ob_errno.def and
  writes ob_errno.cpp, ob_errno.h and ../../src/oblib/lib/ob_errno.h. The text of the message lives in
  two tracked files: the generator input (ob_errno.def:1252) and the generated ob_errno.cpp.
- The build never runs the generator: `git grep gen_errno` at 834bbee1e finds only the notes in
  ob_errno.def that tell a developer to run gen_errno.pl after editing it, and
  tools/ob_error/README.md:100; no CMake or build file. So the binaries take the text from the
  checked-in ob_errno.cpp, and a patch to ob_errno.def alone would change nothing in either binary.
  The patch therefore edits the .cpp.
- The .cpp edit is exactly what the generator produces from the equivalent one-argument edit of the
  input, the 5th argument of `DEFINE_ERROR_EXT(OB_ROWID_TYPE_MISMATCH, -5870, -1, "HY000", ...)` at
  ob_errno.def:1252 set to the 6th. Checked in a scratch directory outside the tree
  (/Users/colin/seekdb-dev/mysqltest-runs/00b/second-set/03-oberr/gen-check/): gen_errno.pl on the
  pristine 834bbee1e ob_errno.def reproduces all three checked-in files byte for byte; on the edited
  .def it changes only this line of ob_errno.cpp and neither header; the patched file is
  byte-identical to that generated file.

## Why family 6 catches it (the exact output that changes)

ob_error_test.test line 12 is `ob_error 5870`. ob_error.cpp's `print_error_info(NONE, 5870, -1)`
finds no OS entry (5870 is not below `OS_MAX_ERROR_CODE`, 135), then `add_ob_info` checks that
`ob_errpkt_str_user_error(-5870)` is not NULL (unchanged) and stores `ob_errpkt_strerror(-5870)`,
which is `ob_strerror(-5870)`, which is `get_error(5870)->str_error`, the mutated field.
`print_ob_error` prints it with `"\tMessage: %s"`, so the `%.*s` sequences are printed as text.
`add_mysql_info` adds nothing, because the entry's `mysql_errno` is -1 and no MySQL code maps to it.

Exactly one line of the 134-line output changes, line 82 of test.result (and of
expect_result.result):

```
-	Message: rowid type mismatch
+	Message: rowid type mismatch, expect %.*s, got %.*s
```

run_ob_error_test.sh then exits 1 with `status=different` in manifest.txt and this hunk in diff.txt,
and the build-against-build comparison of the two test.result files differs at line 82.

`str_error` (`git grep` at 834bbee1e: ob_errno.cpp, ob_errno.def and expect_result.result; the
header holds only the user-error text).

## Why the 272 configured cases most likely do not catch it

- Nothing raises -5870. `git grep -w OB_ROWID_TYPE_MISMATCH` over the whole tree at 834bbee1e finds
  only the catalog (the generator input src/share/ob_errno.def and the generated ob_errno.cpp and
  ob_errno.h) and tools/ob_error/test/expect_result.result. The number appears in tools/deploy only
  inside geometry coordinates (`5870.9469` and the like in
  geometry/r/mysql/st_buffer_mysql.result:1245).
- The text "rowid type mismatch" appears in no .test or .result file under tools/deploy.
- The only server path found that turns a code nobody raised into catalog text is `SQLERRM(code)`
  (src/sql/engine/expr/ob_expr_pl_sqlcode_sqlerrm.cpp:125, `ob_errpkt_strerror(sqlcode)`); the other
  callers of `ob_errpkt_strerror` and `ob_strerror` in src/ pass the code of an error that happened,
  or a fixed code such as `OB_ERR_PARSER_SYNTAX`. In AB.profdata (both coverage passes of the 272
  cases) `ObExprPLSQLCodeSQLErrm::cg_expr` and `eval_pl_sql_code_errm` have 0 hits on every line,
  and no file under tools/deploy uses SQLERRM or SQLCODE. The file is identical at 076eb309b and
  834bbee1e. Output: /Users/colin/seekdb-dev/mysqltest-runs/00b/second-set/03-oberr/coverage/sqlerrm.txt.
- What a client sees when -5870 is raised with a message, `str_user_error`, is unchanged, and
  `mysql_errno` is -1.

ob_errno.cpp is also compiled into seekdb (the ob_share unity file
unity_ob_share_ob_share_common_0_c___cxx.cxx includes it), so a seekdb built with this patch carries
the change; by the evidence above no case outside the quarantine list should fail because of it.
Family 6 does not need seekdb rebuilt.

## How to run it

The ob_error target does not exist in the CMake build on macOS at 834bbee1e (see
../../families/ob_error/README.md, "Building `ob_error`"), so the mutated tool is built with the
family's build script, which reads the reference worktree and writes only into the given directory
(a few seconds; build_release/ and the seekdb binary are not touched):

```
H=/Users/colin/seekdb-dev/migrate-to-rust
W=/Users/colin/seekdb-dev/ref-834bbee1e
P=$H/migration/judge/mutations/second-set/03-ob_error-rowid-message-user-format.patch
RUN=<a new directory>
git -C $W apply --check $P && git -C $W apply $P
$H/migration/judge/families/ob_error/build_ob_error.sh $W $RUN/build
git -C $W apply -R $P
git -C $W diff | cmp - $H/migration/judge/reference-build.patch
$H/migration/judge/families/ob_error/run_ob_error_test.sh $RUN/build/ob_error $RUN/test
```

Caught when run_ob_error_test.sh exits 1 and $RUN/test/diff.txt holds only the line-82 hunk above.
$RUN/build/build.txt records the tree status and the sha256 of the compiled sources, so a build that
picked up another patch shows it (the mutated ob_errno.cpp has a different sha256 from the clean
`fc635746903d10c84ec11d975be10de2c3b4622d111a2780f0e9cf38154ba95e`).
